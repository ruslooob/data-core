# Спецификация: помощник аналитика и виджет документации

> Этот документ описывает **что** делает помощник и виджет документации и **зачем** — на языке [глоссария](GLOSSARY.md). Реализационные детали (модель LLM, библиотеки, имена эндпоинтов, схемы данных) — в коде. Цель спеки — оставаться валидной при любом рефакторинге.

> Помощник — первая ступень к автономному исследовательскому агенту, описанному в [`drafts/SPEC_RESEARCH_AGENT_DRAFT.md`](drafts/SPEC_RESEARCH_AGENT_DRAFT.md). Тот агент — отдельная фича, эта спека к нему не относится.

---

## 1. Назначение

Аналитику нужен **собеседник**, которому можно поручить рутину: «найди мне правила исследования», «создай вот такую стратегию», «прогони её на этом окружении», «расскажи, что написано в спеке такой-то». Сейчас всё это аналитик делает руками через виджеты и редакторы; помощник — это способ выполнить ту же работу через чат на естественном языке.

Параллельно нужно место, где аналитик читает документацию проекта (методология, спецификации, глоссарий) прямо внутри приложения, не открывая редактор кода. Это **виджет документации** — простая «view» по `docs/`.

Помощник и документация — тесно связаны. Помощник умеет читать те же документы, что и аналитик; это позволяет ссылаться в чате на конкретный текст спеки или глоссарий.

---

## 2. Помощник

### 2.1. Что делает

Помощник:

1. Получает реплику пользователя на естественном языке.
2. Выполняет нужные действия теми же средствами, которыми аналитик действует через UI — читает данные и артефакты исследования через REST-API проекта, при необходимости создаёт новые правила, стратегии, окружения, запускает прогоны бэктеста.
3. Отвечает текстом, отрендеренным виджетом помощника. Ответ — markdown.
4. Промежуточные шаги (вызовы инструментов и их результаты) видны пользователю в ленте сообщений по мере выполнения — пользователь видит, что именно помощник прочитал и что собирается сделать.

Помощник опирается на **активное исследование** как на контекст по умолчанию: «создай правило» — значит правило в текущем исследовании, «покажи мои прогоны» — значит прогоны текущего исследования. Если действие требует другого исследования, пользователь указывает его явно.

### 2.2. Что не делает

- Не правит код, конфигурацию, схему БД, миграции, файлы вне каталога документации.
- Не действует автономно: не задаёт сам себе цель, не строит многошаговый план «гипотеза → бэктест → отчёт» (это область автономного исследовательского агента, см. отдельный драфт).
- Не сохраняет историю диалога — помощник не помнит прошлые сессии. Каждая перезагрузка виджета начинает чат заново.
- Не отвечает на вопросы, выходящие за пределы проекта — у него нет такой задачи. Если пользователь спрашивает о чём-то, для чего нет данных в проекте и в документации, помощник честно сообщает об этом.

### 2.3. Прерывание

Пока помощник работает над ответом, пользователь может **прервать** его — выполнение немедленно останавливается, незавершённое сообщение помечается как прерванное, ввод снова доступен. Прерывание не откатывает уже выполненные действия (например, созданное правило остаётся).

### 2.4. Ошибки

Если действие помощника не удаётся (ошибка API, недоступная база, невалидные параметры) — помощник возвращает пользователю текст ошибки **дословно** и останавливается. Никаких догадок о причине, никаких автоматических повторов: пользователь решает, что делать дальше.

## 3. Виджет помощника

### 3.1. Состав

- **Лента сообщений** — хронологический поток реплик пользователя и помощника. Каждое сообщение помощника может содержать текст и видимые промежуточные шаги (вызовы инструментов и их результаты).
- **Поле ввода** — однострочное / многострочное, отправка по горячей клавише. Поддерживает **приложение документов** через символ `@`: при наборе `@` появляется список документов, выбранный документ вставляется как токен `@имя` и его содержимое автоматически прикладывается к реплике (см. §5).
- **Кнопка прерывания** — активна, пока помощник работает; в остальное время скрыта.

### 3.2. Эфемерность

Лента сообщений живёт только в текущей сессии браузера. Перезагрузка страницы или закрытие виджета — чат начинается с нуля. История на сервере не хранится. Это сознательное упрощение первой итерации.

### 3.3. Привязка к полотну

Виджет помощника — обычный виджет полотна: пользователь добавляет его через тулбар, перетаскивает, изменяет размер, закрывает. На экране одновременно — не больше одного экземпляра (несколько параллельных чатов смысла не имеют при эфемерности и едином активном исследовании).

В **логические группы виджет не входит**: его контекст — активное исследование, а не группа.

### 3.4. Рендер ответа

Ответы помощника — markdown. Минимальный набор разметки, обязательный в первой итерации:

- Заголовки, списки, цитаты, ссылки.
- **Таблицы** — частый формат для сравнения метрик прогонов, перечня сущностей.
- **Подсветка кода** — для блоков SQL, PQL, Python.

Дополнительные форматы (формулы, диаграммы) — на будущее.

## 4. Виджет документации

### 4.1. Назначение

Дать аналитику доступ к документам проекта (методология, спецификации, глоссарий) прямо в приложении — без открытия редактора кода или внешнего просмотрщика.

### 4.2. Состав

Виджет состоит из двух панелей:

- **Дерево документов** слева — иерархический список документов и подкаталогов. Отражает реальную структуру каталога документации проекта.
- **Просмотр документа** справа — отрендеренный markdown выбранного документа.

### 4.3. Markdown

Базовый набор разметки, тот же, что у виджета помощника (см. §3.4): заголовки, списки, цитаты, ссылки, таблицы, подсветка кода. Внутренние ссылки между документами должны открываться внутри виджета, без перехода в браузер.

### 4.4. Привязка

Виджет автономен: не зависит от активного исследования, не входит в логические группы. На полотне допустимы несколько экземпляров — например, чтобы держать рядом глоссарий и спеку.

### 4.5. Что не делает

- Не позволяет редактировать документы — документация правится только разработчиком в репозитории.
- Не предоставляет поиск по тексту — в первой итерации навигация только через дерево. Поиск — будущее расширение.

## 5. Доступ помощника к документации

Помощник умеет читать те же документы, что и пользователь — это позволяет в чате ссылаться на конкретные места глоссария или спеки («поясни, что такое CAR» — помощник смотрит в глоссарий и пересказывает; «как устроены правила?» — открывает спеку бэктеста).

Доступ ограничен **каталогом документации**: помощник не видит код, не видит данные за пределами REST-API проекта, не видит файловую систему вне `docs/`.

### Два способа дать помощнику документ

1. **Явное приложение через `@`.** Пользователь набирает `@` в поле ввода, выбирает документ из списка — содержимое документа прикладывается к реплике и помощник гарантированно его учитывает. Это аналог «вкладывания файла в чат».
2. **Самостоятельное чтение.** Помощник по собственной инициативе обращается к нужному документу, если для ответа на запрос требуется заглянуть в глоссарий или спеку.

Что пользователь сейчас открыл в виджете документации — **помощнику невидимо**: если документ должен быть учтён, пользователь прикладывает его через `@`.

---

## 6. Привязка к активному исследованию

Помощник видит идентификатор активного исследования в системном контексте — это позволяет ему без лишних уточнений отвечать на формулировки в первом лице («покажи мои стратегии», «прогони X на Y»).

Виджет помощника требует активного исследования так же, как и другие виджеты артефактов исследования: пока исследование не выбрано — виджет заблокирован.

Виджет документации в активном исследовании **не нуждается** — документация общая для всех исследований.

---

## 7. Что не входит

- **Автономный исследовательский агент** — отдельная фича, описанная в [`SPEC_RESEARCH_AGENT_DRAFT.md`](SPEC_RESEARCH_AGENT_DRAFT.md). Помощник реактивен; автономный агент сам ведёт цепочку «гипотеза → выводы».
- **Сохранение истории чатов** на сервере. Эфемерные сессии — сознательное упрощение первой итерации.
- **Несколько параллельных чатов** в одном исследовании — не нужно при эфемерности.
- **Поиск по тексту документации** в виджете документации — будущее расширение.
- **Редактирование документов** из приложения — документация правится в репозитории.
- **Формулы (KaTeX), диаграммы (Mermaid)** в markdown — будущее расширение, если возникнет потребность.
- **Память помощника между сессиями** — нет долгосрочного контекста о пользователе. Возможно появится позже как явная фича.

## 8. Закрытые дизайн-вопросы

Решения, принятые при проектировании. Записаны коротко — для понимания «почему так», без полной аргументации.

1. **Терминология.** «Помощник» (`Assistant`) — реактивный собеседник по запросу; «агент» — автономный исполнитель цели (см. `BACKTEST_RUNNER_AGENT.md`, `SPEC_RESEARCH_AGENT_DRAFT.md`). Разведены, чтобы две роли не сливались в один термин.
2. **Граница доступа.** Аналитический уровень: REST-API проекта + чтение каталога документации. Не код, не схема, не файлы вне документации. Разработческий доступ исключён сознательно — слишком высокий риск незаметной поломки.
3. **Эфемерность чата.** Нет таблиц, нет CRUD, нет миграций под историю — минимальная цена первой итерации. Расширим, когда появится конкретная потребность («хочу вернуться к диалогу прошлой недели»).
4. **Стриминг ответа целиком, включая шаги.** Пользователь видит, какие инструменты вызывает помощник и с какими параметрами — это и контроль, и обучающий момент. Скрытый «спиннер» был бы быстрее в реализации, но непрозрачнее.
5. **Один экземпляр виджета помощника на полотне.** При эфемерности и единственном активном исследовании несколько чатов рядом не имеют смысла.
6. **Доступ помощника к документации — через файловую систему**, ограниченную каталогом документации. Альтернатива — выделить API для чтения документов и пускать помощника через него; решено не плодить дублирующий канал, потому что доступ всё равно нужен виджету документации (его и используют).
7. **Открытый документ виджету помощнику невидим.** Иначе появилась бы скрытая связь «вижу в одном виджете — учитываю в другом», которую пользователю было бы тяжело предсказать. Явное упоминание документа в реплике лучше неявной телепатии.
8. **Виджет документации без поиска и без редактирования.** Первая итерация — минимум: дерево + рендер. Поиск стоит добавлять, когда документов станет настолько много, что навигация по дереву станет неудобной.
