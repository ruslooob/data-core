# Бэктест стратегий — спецификация

---

## Часть 1 — Концепция

### 1.1. Что такое бэктест

Бэктест — это **симуляция**: берём стратегию пользователя и историю цен, прокручиваем её через прошлое торговый день за днём, в конце смотрим, что получилось.

**Вход:**
- `Strategy` — что делать (набор правил)
- `Environment` — окружение прогона: стартовый капитал + период (`date_start`, `date_end`)

Одну и ту же `Strategy` можно прогонять в разных `Environment`. Это позволяет проверять стратегию на разных периодах и при разных стартовых капиталах, не дублируя сами правила.

**Выход — `BacktestResult`:**
- набор метрик прогона (финальный капитал, прибыль, риски — состав финализируется отдельно)
- `TradeJournal` — полный журнал сделок прогона
- `EquityCurve` — представление поверх `TradeJournal` + `Environment.starting_capital` + рыночных данных, вычисляется при отображении (не хранится отдельным полем)

### 1.2. Главный цикл

```
для каждого тика (= торгового дня) в периоде:
    1) дать стратегии увидеть рынок и состояние портфеля
    2) спросить стратегию: «что делаем?» — получить список кандидатов
    3) исполнить кандидатов (частично, если не хватает кэша или позиции)
    4) обновить состояние портфеля на конец тика (cash, equity, лоты)
```

В конце периода — финальный отчёт. Подробности шагов — в Части 3.

### 1.3. Сущности и метрики

Определения всех сущностей бэктеста и метрик результата — в [GLOSSARY.md](GLOSSARY.md), разделы «Сущности приложения» и «Метрики бэктеста».

## Часть 2 — Анатомия правила

`Rule` состоит из четырёх полей:

- **`name`** — имя правила (для отчётности и идентификации в `trade_journal`)
- **`trigger`** — PQL-запрос «кого затронуть» (см. 2.1)
- **`action`** — конфигурация «что и сколько» (см. 2.2)
- **`priority`** — целое число (`int`) для сортировки кандидатов на одном тике (см. 2.3)

### 2.1. Trigger — поиск «кого затронуть»

PQL-запрос вида `SELECT ticker FROM ... WHERE ...`. Возвращает список тикеров, для которых правило сегодня сработало. Только поиск — никаких «сколько» и «что делать».

Видит контекст из Части 5. Подчиняется принципу no-lookahead из Части 4.

Пример (всплеск объёма):
```sql
SELECT t.code AS ticker
FROM tags t
WHERE t.type = 'company'
  AND volume(t.code, :tick - 1) / volume_sma(t.code, :tick, 20) > 1.5
```

Пример (дивиденды LKOH объявлены вчера):
```sql
SELECT 'LKOH' AS ticker
WHERE EXISTS (
  SELECT 1 FROM tagged_events te
  WHERE te.tag = 'DIVIDEND_ANNOUNCEMENT'
    AND te.date_start = :tick - 1
    AND te.event_id IN (SELECT event_id FROM tagged_events WHERE tag = 'LKOH')
)
```

### 2.2. Action — тип действия и кол-во акций

Конфигурация из двух полей:

- **`type`** — `buy` или `sell` (в MVP — только лонги)
- **`quantity`** — отдельный PQL-запрос, возвращающий **одну ячейку** — целое число акций для подставленного `:ticker`.

#### Как работает `quantity`

После того как trigger вернул список тикеров, для каждого из них движок выполняет **второй PQL-запрос** — `Action.quantity` — подставляя `:ticker`. Запрос возвращает одну ячейку (число акций).

```
trigger:    SELECT ticker FROM ...                            →  ['LKOH', 'GAZP']

для LKOH:   action.quantity, :ticker = 'LKOH'
            SELECT FLOOR(s.cash * 0.10
                       / close_price(:ticker, :tick - 1))
            FROM portfolio_state s
                                                              →  8

→ кандидат {ticker='LKOH', type='buy', quantity=8, priority=100}
```

То же повторяется для `GAZP` и для всех остальных тикеров **этого правила**. Затем движок переходит к следующему правилу стратегии. Общий список кандидатов идёт в Часть 3 (исполнение).

#### Контракт `quantity`-запроса

- ровно 1 строка × 1 колонка
- возвращает целое число ≥ 0
- доступен параметр `:ticker` — пришёл из триггера
- видит **тот же контекст**, что триггер (Часть 5)
- подчиняется тому же no-lookahead (Часть 4)
- если запрос вернул `0`, `NULL` или упал с ошибкой — кандидат пропускается, бэктест не падает

#### Примеры

```sql
-- "Купить 100 акций"
SELECT 100

-- "Купить на 50 000 рублей"
SELECT FLOOR(50000 / close_price(:ticker, :tick - 1))

-- "10% от свободного кэша"
SELECT FLOOR(s.cash * 0.10
           / close_price(:ticker, :tick - 1))
FROM portfolio_state s

-- "5% от equity"
SELECT FLOOR(s.equity * 0.05
           / close_price(:ticker, :tick - 1))
FROM portfolio_state s

-- "Продать всю позицию" (стоп-лосс) — по всем лотам тикера
SELECT SUM(quantity) FROM portfolio_positions WHERE ticker = :ticker

-- "Продать половину" (частичный выход)
SELECT FLOOR(SUM(quantity) / 2) FROM portfolio_positions WHERE ticker = :ticker

-- "Позиция, нормированная на волатильность" (Kelly-style)
SELECT FLOOR(s.cash * 0.02
           / close_price(:ticker, :tick - 1)
           / volatility(:ticker, :tick, 20))
FROM portfolio_state s
```

#### Что это даёт

Один язык (PQL) и для триггера, и для расчёта количества. Quantity-запрос отлаживается прямо в PQL-редакторе с подставленным `:ticker`.

### 2.3. Priority — порядок исполнения

`Rule.priority` — целое число, задающее порядок применения кандидатов одного тика. Чем выше значение, тем раньше кандидаты от этого правила попадают на исполнение. При равном `priority` порядок определяется позицией правила в списке `Strategy.rules` (см. Часть 3.2).

Это координационное свойство правила среди соседей по стратегии: `trigger` и `action` оперируют одним тикером и не знают о других правилах, а `priority` определяет, кто первым тратит общий кэш и существующие позиции.

### 2.4. Стоп-лосс как обычное sell-правило

Триггер ищет «когда и для кого». Action описывает «что и сколько». Один и тот же триггер можно подцепить к разным Action, и наоборот. Стоп-лосс — это просто правило с `Action.type = sell` и триггером по цене позиции; никакой специальной сущности «exit-rule» нет.

## Часть 3 — Один тик

### 3.1. Шаги движка

```
для каждого тика:
    кандидаты = []

    для каждого rule в стратегии:
        список_тикеров = выполнить rule.trigger (:tick = today)
        для t в список_тикеров:
            qty = выполнить rule.action.quantity (с :ticker = t, :tick = today)
            кандидаты += {ticker=t, type=rule.action.type,
                          quantity=qty, priority=rule.priority,
                          rule_name=rule.name}

    отсортировать кандидатов по убыванию priority
        (при равном priority — по порядку правил в Strategy)

    для каждого кандидата по порядку:
        фактическое_кол-во = cash / цена открытия (см. 3.2)
        если фактическое_кол-во > 0:
            записать сделку в trade_journal с этим количеством,
            обновить portfolio_state и portfolio_positions
        иначе:
            кандидат отбрасывается

    переоценить equity по close-ценам текущего тика:
        portfolio_state.equity = cash + Σ(quantity × close_price(ticker, :tick))
            по всем открытым лотам
        дописать строку (:tick, equity) в runtime-таблицу equity_curve
```

### 3.2. Исполнение кандидата (с частичным заполнением)

Если кандидат не может быть исполнен полностью, **исполняем частично** — сколько позволяет состояние счёта.

- **Покупка `quantity` акций по цене `price`:** реально исполняется `min(quantity, FLOOR(cash / price))`. Если получился `0` — кандидат отбрасывается; иначе в `trade_journal` записывается **фактическое** исполненное количество и в `portfolio_positions` добавляется **новый лот** с этим количеством, ценой `price` и датой `:tick`.
- **Продажа `quantity` акций:** реально исполняется `min(quantity, Σ quantity по всем лотам тикера)`. Если позиции нет — кандидат отбрасывается; иначе в `trade_journal` записывается **фактически** проданное количество. Списание из лотов — по принципу **FIFO**: сначала из самого старого лота (минимальная `buy_date`), потом следующий и т.д. Это влияет на зафиксированную прибыль/убыток (`pnl_realized`) каждой sell-сделки и на состав оставшихся лотов.

**Порядок обработки кандидатов:** по убыванию `priority`. **При равном `priority`** — в порядке, в котором правила записаны в `Strategy` (по позиции в списке правил).

Цены исполнения берутся по правилу из Части 4.

### 3.3. Корпоративные действия: дивидендные выплаты

Дивидендные выплаты — это рыночная механика. Пользовательские правила про них ничего не знают и не решают. Движок обрабатывает выплаты автоматически в составе тика.

**Когда.** На каждом тике, после исполнения кандидатов и переоценки equity (то есть в конце тика). Если стратегия купила тикер сегодня по `open`, а сегодня же дата выплаты — деньги начисляются на эти лоты тоже.

**Что начисляется.** Для каждого тикера в `portfolio_positions`, у которого `payment_date == :tick`, к `cash` прибавляется `Σ quantity_по_всем_лотам_тикера × dividend_per_share`. Источник суммы и даты выплаты — `DividendDataProvider` (поле `payment_date`), не `announcement_date`.

**Запись в журнал.** Каждое начисление — отдельная строка в `trade_journal` с `type = 'dividend'`, `quantity = Σ quantity по позициям тикера на момент выплаты`, `price = dividend_per_share`, `pnl_realized = quantity × dividend_per_share` (положительная — деньги пришли), `rule_name = '*dividend*'` (специальное системное имя). Это даёт пользователю прозрачную детализацию в журнале.

**MVP-упрощения.**
- Налогов нет.
- Шорт-позиций нет (в MVP только лонги — Q2), значит вопрос «отрицательного дивиденда у шорта» не возникает.
- Если пользователь продал часть позиции до даты выплаты — на остаток выплата начисляется естественно, через `Σ quantity` в `portfolio_positions`.
- Drop цены тикера в дату выплаты (gap «-dividend») честно отражается в рыночных данных провайдера; ничего отдельного делать не нужно.

**Контракт `:tick`.** Дата выплаты сравнивается **по календарной дате**, не по торговому дню. Если `payment_date` приходится на выходной (а в IMOEX-календаре такого тика нет) — выплата теряется. В MVP это допустимое упрощение; позже можно сдвигать на ближайший торговый день.

## Часть 4 — Главный принцип: no look-ahead bias

На текущем тике (дата = `:tick` = `run_context.current_tick`) стратегия видит только прошлое. «Сегодня» для триггера ещё не наступило.

```
Стратегия видит:    данные ≤ close(:tick - 1)
Стратегия решает:   список кандидатов на тике
Движок исполняет:   по open(:tick)
Equity фиксируется: на close(:tick)
```

Принцип обеспечен на уровне поставщиков данных: они читают session-GUC `backtest.max_date` и фильтруют любые котировки по этой дате. Движок выставляет GUC в `:tick - 1` перед триггерной фазой и в `:tick` перед исполнением/переоценкой, поэтому пользовательский запрос физически не может прочитать данные будущих тиков. Подробности — см. [`SPEC_DATA_PROVIDERS.md`](SPEC_DATA_PROVIDERS.md).

В редакторе PQL GUC не выставляется, и доступ к историческим данным открыт целиком — это нужно для пост-факт-анализа.

Сделки исполняются по `open(:tick)`, equity фиксируется на `close(:tick)`. Гэп между `close(:tick - 1)` и `open(:tick)` симулятор не сглаживает — это обычная механика рынка (см. [GLOSSARY.md → Гэп](GLOSSARY.md)), и стоп-лосс честно «пробивается» настолько, насколько прыгнула цена.

## Часть 5 — Контекст PQL-запросов

Триггер и `Action.quantity` видят **один и тот же контекст**. Описывается ниже.

### 5.1. Общие данные — `:tick` + таблица `run_context`

Сокращение `:tick`, дублирующее `run_context.current_tick` реализовано намеренно для обеспечения лаконичности большинства запросов.

- **`:tick`** — именованный параметр, `=` `run_context.current_tick`. Текущая дата.
- **`run_context`** — Содержит дополнительные поля: `index`, `date_start`, `date_end`, `starting_capital`.

Все «глобальные» поля прогона живут в одной таблице с одной строкой `run_context`:

| Колонка | Что |
|---|---|
| `current_tick` | сегодняшняя дата текущего тика |
| `index` | порядковый номер тика от старта (0, 1, 2…) |
| `date_start` | начало прогона |
| `date_end` | конец прогона |
| `starting_capital` | стартовый капитал |

Примеры:

```sql
-- текущий день в запросе
SELECT t.code FROM tags t
WHERE volume(t.code, :tick - 1) / volume_sma(t.code, :tick, 20) > 1.5

-- использование стартового капитала в запросе
SELECT FLOOR(rc.starting_capital * 0.10
           / close_price(:ticker, :tick - 1))
FROM run_context rc
```

### 5.2. Состояние портфеля

Состояние **на конец предыдущего тика** (после исполнения вчерашних сделок и переоценки по `close(:tick - 1)`). Две таблицы.

**`portfolio_positions`** — таблица **лотов**. Одна строка = один акт покупки. При докупке того же тикера — добавляется новая строка. При продаже списываются лоты по **FIFO** — сначала самые старые (см. Часть 3.2).

| Колонка | Что |
|---|---|
| `ticker` | тикер |
| `quantity` | сколько акций осталось в этом лоте (уменьшается при частичных продажах из лота; строка удаляется при `quantity = 0`) |
| `buy_price` | цена, по которой акции этого лота были куплены (не меняется) |
| `buy_date` | дата покупки лота (не меняется) |

**`portfolio_state`** — таблица из одной строки, глобальные скаляры счёта.

| Колонка | Что |
|---|---|
| `cash` | свободный кэш |
| `equity` | cash + Σ(quantity × close_price(ticker, :tick - 1)) по всем лотам |

`equity` хранится как поле — компромисс ради скорости: пересчёт по всем лотам и обращение к рыночным данным на каждом обращении триггера дороги. Движок инкрементально обновляет `equity` на каждом тике.

### 5.3. История

`trade_journal` — все исполненные сделки с начала прогона до `close(:tick - 1)`:

| Колонка | Что |
|---|---|
| `trade_date` | дата исполнения |
| `ticker` | тикер |
| `type` | `buy` / `sell` / `dividend` (см. 3.3) |
| `quantity` | фактически исполненное количество (с учётом частичного заполнения) |
| `price` | цена исполнения; у `dividend` — сумма выплаты на акцию |
| `rule_name` | имя правила-источника; у `dividend` — системное `*dividend*` |
| `pnl_realized` | зафиксированная прибыль/убыток. У `sell` — `Σ (sell_price − buy_price_лота) × quantity_лота` по списываемым лотам (FIFO). У `dividend` — сумма выплаты (положительная). У `buy` = NULL. |

Как рассчитывается зафиксированный результат:
```
pnl_realized = Σ по списываемым лотам: quantity_из_лота × (sell_price − buy_price_лота)
```

**`EquityCurve`** не хранится — это представление поверх `trade_journal` + рыночных данных (см. 1.1, 1.3).

### 5.4. TA-функции

Доступные пользователю функции технического анализа — встроенные в Postgres функции, вызываемые из PQL как обычный SQL. Видимое окно ограничивается session-GUC `backtest.max_date`, который движок выставляет в `:tick - 1` на триггерной фазе.

**Точечные функции** — аргумент-дата интерпретируется как сама эта дата, включительно. В бэктесте, чтобы прочитать данные предыдущего дня, пишется `:tick - 1`.

| Функция | Что возвращает |
|---|---|
| `close_price(ticker, date)` | цена закрытия за `date` |
| `open_price(ticker, date)` | цена открытия за `date` |
| `volume(ticker, date)` | объём за `date` |

**Оконные функции** — аргумент-дата интерпретируется как **правая граница интервала, не включая её**. Расчёт идёт по `[date - window, date - 1]`. В бэктесте можно писать просто `:tick` — функция автоматически отдаст последние `window` дней, не считая текущего.

| Функция | Что возвращает |
|---|---|
| `sma(ticker, date, window)` | простая скользящая средняя цены за `window` дней до `date` |
| `volume_sma(ticker, date, window)` | средний объём за `window` дней до `date` |
| `volatility(ticker, date, window)` | стандартное отклонение дневных логдоходностей за `window` дней до `date` |
| `return_n_days(ticker, date, n)` | накопленная доходность за последние `n` дней до `date` |

Это финальный набор для MVP. Расширение (EMA, RSI, MACD, Bollinger, high/low дня) — пост-MVP, без слома структуры.

**Учётные функции** (читают `trade_journal`):

| Функция | Что возвращает |
|---|---|
| `avg_price(ticker)` | Средневзвешенная цена входа по **открытым лотам** тикера: `Σ(quantity × buy_price) / Σ(quantity)` поверх `portfolio_positions WHERE ticker = X`. **Чистая**. Используется в стопах: `WHERE close_price(ticker, :tick - 1) < avg_price(ticker) * 0.97`. Если позиции нет — NULL. |

**События** — без новых функций, обычный SELECT по `tagged_events`:
```sql
SELECT * FROM tagged_events WHERE date_start <= :tick - 1
```

## Часть 6 — Реализация в Postgres

Всё — через стандартный psycopg API поверх той же Postgres-БД, в которой живут PQL-сущности.

| Что | Как |
|---|---|
| `:tick` | Именованный параметр через `con.execute(sql, {'tick': date})`. Стандартный механизм psycopg. Сокращение для `run_context.current_tick`. |
| `run_context`, `portfolio_state`, `portfolio_positions`, `trade_journal`, `equity_curve` | **TEMP-таблицы Postgres**, создаются в сессии прогона через `CREATE TEMP TABLE`. Видны только этой сессии, удаляются при её закрытии. Поддерживаются обычными `INSERT` / `UPDATE` / `DELETE`. Persistent-таблицы PQL (`events`, `tagged_events`, ...) видны из той же сессии без квалификатора. |
| TA-функции, `avg_price` | `plpython3u`-функции в Postgres, зарегистрированы один раз через миграции (см. [`SPEC_DATABASE.md`](SPEC_DATABASE.md)). Видимое окно котировок управляется session-GUC `backtest.max_date`, который движок выставляет на каждом тике. |
| `events`, `tags`, `event_tags`, `tagged_events` | Persistent-таблицы Postgres, общие с PQL-редактором. Используются как есть. |
| `:ticker` | Именованный параметр, биндится при выполнении `Action.quantity` для каждого кандидата (стандартный механизм psycopg). |

> Различение runtime vs persistent: `run_context`/`portfolio_state`/`portfolio_positions`/`trade_journal`/`equity_curve` — TEMP-таблицы, видны только сессии текущего прогона (эфемерные, удаляются при закрытии коннекта). Persistent-сущности (`Strategy`, `Rule`, `Environment`, `BacktestResult`, исторический `trade_journal`) — обычные таблицы в той же Postgres-БД. Подробности — Часть 6.2.

### 6.1. Процесс прогона

Каждый прогон выполняется **в отдельном дочернем процессе**. Процесс открывает собственный бд-коннект — это даёт ему приватную Postgres-сессию с приватными TEMP-таблицами движка и приватным `backtest.max_date`.

**Параллельность.** Несколько прогонов можно запускать одновременно. Лимит — только ресурсы машины (CPU, RAM, число коннектов к Postgres).

**Координация.** Веб-процесс держит синглтон-координатор всех прогонов: словарь активных прогонов, фоновый поток собирает события из очередей (`progress`, `done`, `error`, `cancelled`) и при завершении дёргает коллбэк записи в persistent. **Воркер сам в persistent-БД ничего не пишет** — это сознательная двухроли модель: писать в общую БД имеет право только веб-процесс, чтобы не плодить параллельные транзакции.

**Статусы.** Прогон проходит `running` → один из терминальных: `done` / `error` / `cancelled`. На `error` в `/progress` появляется `error_message` с текстом исключения. На `done` — `result_id` записи в `backtest_results`. Отмена — `POST /runs/{id}/cancel`, движок проверяет флаг на каждом тике.

### 6.2. Persistent-хранилище

Persistent-таблицы бэктеста живут в общей Postgres-БД проекта вместе с persistent-таблицами PQL (`events`, `tagged_events`, ...). Стандартный реляционный подход: FK работают «из коробки», транзакции, миграции через Liquibase (см. [`SPEC_DATABASE.md`](SPEC_DATABASE.md)). Просматривать содержимое — через `psql`, DBeaver или вкладку Database в PyCharm.

**Список таблиц.**

| Таблица | Назначение |
|---|---|
| `strategies` | Сохранённые стратегии. Колонки: `id`, `name`, `description`, `created_at`, `research_id` (FK, nullable — см. ниже). |
| `rules` | Сохранённые правила (переиспользуются между стратегиями). Колонки: `id`, `name`, `description`, `trigger_sql`, `action_type`, `action_quantity_sql`, `priority`, `created_at`, `research_id` (FK, nullable). |
| `strategy_rules` | Связь M2M «правило ↔ стратегия». Колонки: `strategy_id` (FK), `rule_id` (FK), `position` (порядок правила в стратегии — задаёт очерёдность исполнения при равном `priority`). |
| `environments` | Сохранённые окружения. Колонки: `id`, `name`, `description`, `date_start`, `date_end`, `starting_capital`, `created_at`, `research_id` (FK, nullable). |
| `backtest_results` | Результаты прогонов. Колонки: `id`, `strategy_id` (FK), `environment_id` (FK), `research_id` (FK, NOT NULL), `created_at`, скалярные метрики (`total_return_pct`, `annual_return_pct`, `max_drawdown_pct`, `sharpe`, `n_trades`, `profit_factor`, `win_rate_pct`). Сама equity-кривая в БД не хранится (см. размышления ниже) — восстанавливается из `trade_journal` при открытии карточки прогона. |
| `trade_journal` | Persistent-журнал сделок всех прогонов. Колонки: `id` (PK), `backtest_result_id` (FK), `trade_date`, `ticker`, `type`, `quantity`, `price`, `rule_name`, `pnl_realized`. Индекс на `backtest_result_id`. |

**Привязка к исследованию.** `Strategy`, `Rule`, `Environment` могут быть **приватными** (`research_id` указан — видны и используются только в одном исследовании, удаляются каскадно с ним) или **общими** (`research_id IS NULL` — видны во всех исследованиях, удаление разрешено только если на них не ссылается ни один прогон). `BacktestResult` всегда принадлежит ровно одному исследованию — `research_id NOT NULL` (`deleteCascade` на FK). Подробности приватных/общих сущностей — в [`GLOSSARY.md`](GLOSSARY.md), раздел «Исследования».

> **Имя `trade_journal` совпадает с runtime-таблицей** в TEMP-схеме сессии прогона. По завершении прогона runtime-журнал переносится в persistent (`public.trade_journal`) с проставлением `backtest_result_id`.

**Хранение equity-кривой.** В persistent-БД кривая **не сохраняется**. В `backtest_results` лежат только скалярные метрики, которые рассчитываются по runtime-кривой в момент завершения прогона.

Во время прогона runtime-таблица `equity_curve` (TEMP-схема сессии) ведётся как обычно — она нужна для live-стриминга клиенту по `?after_tick=N`.

**Создание сущностей.** `Strategy`, `Rule`, `Environment` создаются явно через виджет каталога (`EntityEditor`) или REST-эндпоинты `POST /api/{entity}`. Никаких ad-hoc-сущностей и автоматических Untitled-имён: пользователь сам несёт ответственность за то, чтобы перед запуском прогона нужные правила, стратегия и окружение были собраны в каталоге. Это устраняет «мусорные» Untitled-записи и заставляет относиться к сущностям как к библиотеке для переиспользования.

**Прогоны**: каждый завершённый прогон автоматически добавляется в `backtest_results` + `trade_journal`. Пользователь может удалить прогон вручную.

**Уникальность имён**: внутри одного исследования имена `Strategy`/`Rule`/`Environment` уникальны (`(research_id, name)`); среди общих сущностей (без `research_id`) — также уникальны. Одно и то же имя может одновременно существовать как общая сущность и как приватная одного или нескольких исследований. Дубль внутри своей области → ошибка.

**Повторные прогоны**: запуск той же `(Strategy, Environment)` дважды → две строки в `backtest_results` (разные `id`, разный `created_at`). В будущем это пригодится для стратегий с элементом случайности.

**Иммутабельность.** Содержание `Strategy`, `Rule`, `Environment` после создания **не редактируется**: правила стратегии и порядок их выполнения, текст триггера и `Action.quantity`-запроса, тип действия и приоритет правила, период и стартовый капитал окружения. Чтобы получить другое содержание — создаётся новая сущность. Это гарантирует, что каждый `BacktestResult` всегда ссылается на ровно ту версию данных, которая его произвела.

**Изменяемые поля.** Только `name` и `description` — текст-комментарий аналитика. Они применяются ко всем трём именованным сущностям. Ссылки идут по `id`, поэтому переименование не ломает уже сохранённые `BacktestResult` или связи `strategy_rules`. Новое имя должно быть непустым и уникальным в пределах своей области (исследование или «общая») — иначе ошибка.

**Семантика удаления.**

| Сущность | Кого удаляет | Кого НЕ трогает | Запрет |
|---|---|---|---|
| `Strategy` | свои `backtest_results` и связанные `trade_journal`-строки; записи в `strategy_rules` | сами `Rule`, сами `Environment` (они независимы) | — |
| `Rule` | — | — | удалять нельзя, пока на неё ссылается хоть одна `Strategy` (через `strategy_rules`). Сначала удалить зависимые стратегии. |
| `Environment` | — | — | удалять нельзя, пока на него ссылается хоть один `BacktestResult`. Сначала удалить зависимые прогоны (или содержащие их стратегии). |
| `BacktestResult` | свои `trade_journal`-строки | `Strategy`, `Environment` остаются | — |
| `Research` | свои приватные `Strategy`/`Rule`/`Environment` (по `research_id`) и каскадно — все свои `BacktestResult` + их `trade_journal` | общие `Strategy`/`Rule`/`Environment` (`research_id IS NULL`) | — |

### 6.3. REST-API бэкенда

Из всех модифицирующих операций над `Strategy` / `Rule` / `Environment` доступны только создание, удаление, переименование и редактирование описания. Прогон — асинхронный: `POST /api/backtest/run` сразу возвращает `run_id` (HTTP 202), дальше клиент опрашивает прогресс.

| Метод и путь | Что делает |
|---|---|
| `POST /api/backtest/run` | Запустить прогон. Тело: `strategy_id` + `environment_id` + `research_id` (все обязательны; ad-hoc нет). Ответ: `run_id`, статус `running` (HTTP 202). |
| `GET /api/backtest/runs/{id}/progress` | Текущее состояние прогона: `progress` (0..1), `current_tick`, `current_equity`, `n_trades_so_far`, `status`, `result_id` (когда `done`). |
| `POST /api/backtest/runs/{id}/cancel` | Запросить отмену. Прогон прерывается на ближайшем тике, в `backtest_results` ничего не пишется. |
| `GET /api/backtest/runs/{id}/log?after_byte=N` | Хвост лог-файла прогона начиная с байта `N`. Используется UI для live-tail во время прогона; после завершения возвращает лог целиком. |
| `GET /api/backtest/results?researchId=X` | Список всех прогонов исследования `X`. Параметр обязателен — прогоны без контекста исследования наружу не отдаются. |
| `GET /api/backtest/results/{id}` | Карточка прогона: метрики + сделки + восстановленная `EquityCurve` + ссылки на `Strategy` и `Environment`. |
| `DELETE /api/backtest/results/{id}` | Удалить прогон и связанные строки `trade_journal` (последние — через FK `deleteCascade`). |
| `POST /api/backtest/results/{id}/recompute` | Пересчитать метрики прогона из существующего persistent `trade_journal`. Применять, когда изменилась формула метрики (например `Sharpe`) или цены в `stock_candles`. Сами сделки не меняются. |
| `GET /api/strategies?researchId=X&includeCommon=true` | Список стратегий исследования `X`; флаг `includeCommon` добавляет общие (без `research_id`). |
| `POST /api/strategies` | Создать стратегию из существующих правил (только `rule_id`, без ad-hoc). Ответ — HTTP 201. |
| `PATCH /api/strategies/{id}` | Переименовать стратегию. Тело: `{ name }`. |
| `PATCH /api/strategies/{id}/description` | Изменить описание. Тело: `{ description }`. |
| `PATCH /api/strategies/{id}/research` | Сменить принадлежность: привязать к исследованию, отвязать (сделать общей) или перенести между исследованиями. Тело: `{ research_id }` (или `null`). |
| `DELETE /api/strategies/{id}` | Каскадное удаление стратегии и её прогонов. |
| `GET /api/rules?researchId=X&includeCommon=true` | Список правил исследования `X`; флаг `includeCommon` добавляет общие. |
| `POST /api/rules` | Создать правило. SQL триггера и quantity валидируются перед сохранением (см. ниже). Ответ — HTTP 201. |
| `PATCH /api/rules/{id}` | Переименовать правило. |
| `PATCH /api/rules/{id}/description` | Изменить описание. |
| `PATCH /api/rules/{id}/research` | Сменить принадлежность правила. |
| `DELETE /api/rules/{id}` | Удалить правило. Ошибка, если на него ссылается хоть одна стратегия. |
| `GET /api/environments?researchId=X&includeCommon=true` | Список окружений исследования `X`; флаг `includeCommon` добавляет общие. |
| `POST /api/environments` | Создать окружение. Ответ — HTTP 201. |
| `PATCH /api/environments/{id}` | Переименовать окружение. |
| `PATCH /api/environments/{id}/description` | Изменить описание. |
| `PATCH /api/environments/{id}/research` | Сменить принадлежность окружения. |
| `DELETE /api/environments/{id}` | Удалить окружение. Ошибка, если на него ссылается хоть один прогон. |

**Имена**: уникальность — `(research_id, name)` внутри каждой таблицы плюс отдельная уникальность среди общих сущностей (см. 6.2). Попытка создать дубль через `POST` или переименовать через `PATCH` в существующее имя в той же области → 409. Пустое имя → 400.

**Валидация при `POST /api/rules`**: SQL триггера и `Action.quantity` проходят синтаксический и контрактный контроль до сохранения. Триггер проверяется через `EXPLAIN` в отдельной Postgres-сессии с пустыми TEMP-таблицами runtime-схемы и `backtest.max_date='1990-01-01'`. Quantity дополнительно исполняется с фиктивными `:tick`/`:ticker`; результат должен быть строго одна строка × одна колонка, целое ≥ 0 либо NULL. Любая жёсткая ошибка → 400 с понятным сообщением.

### 6.4. Логирование прогона

Каждый прогон пишет подробный текстовый лог в отдельный файл `data/logs/backtest/<run_id>.log`. Файл создаётся при старте прогона, дописывается построчно по ходу, переживает завершение. При `DELETE /api/backtest/results/{id}` запись и строки `trade_journal` уходят, а лог-файл остаётся на диске и чистится вручную.

**Формат строки:**

```
<ts>  <LEVEL>  <message>
```

Где `message` — человекочитаемая фраза с парами `ключ=значение` для значимых полей. Не JSON: грепается обычным `grep`, читается глазами без декодеров.

Пример фрагмента из реального прогона:

```
2026-04-29 12:34:56.123  INFO   run start  run_id=a1b2c3 strategy='LKOH momentum' environment='Default 2020-2025' period=2020-01-01..2025-12-31 starting_capital=1000000
2026-04-29 12:34:56.135  DEBUG  tick 0001 2020-01-02  equity=1000000.00 cash=1000000.00 positions=0
2026-04-29 12:34:56.148  DEBUG  tick 0001 rule 'Volume spike entry' triggered  tickers=[LKOH, GAZP]
2026-04-29 12:34:56.152  DEBUG  tick 0001 candidate  ticker=LKOH type=buy quantity=8 priority=100 rule='Volume spike entry'
2026-04-29 12:34:56.158  DEBUG  tick 0001 trade  ticker=LKOH type=buy quantity=8 price=2300.50 fill_ratio=1.0
2026-04-29 12:34:56.163  WARN   tick 0001 rejected  ticker=GAZP type=buy reason=insufficient_cash requested_qty=12 affordable_qty=0
2026-04-29 12:34:56.170  DEBUG  tick 0001 end  equity=1018400.00 cash=981596.00 positions=1
...
2026-04-29 12:34:57.812  INFO   run complete  run_id=a1b2c3 total_return=12.34% sharpe=1.23 max_dd=4.5% trades=15
```

Все строки одного тика начинаются с `tick NNNN <date>`, чтобы блок было легко выделить глазом или `grep`.

**Уровни:**

| Уровень | Что логируется |
|---|---|
| `ERROR` | синтаксические/семантические ошибки SQL триггера или `Action.quantity` (с line/column от Postgres); нарушение контракта `Action.quantity`; падение прогона |
| `WARN` | кандидат отброшен (NULL от UDF, не хватило кэша, нет позиции); частичное заполнение (`fill_ratio < 1.0`); пустые данные у тикера |
| `INFO` | старт прогона (стратегия, окружение, период, стартовый капитал); завершение со всеми семью метриками; отмена |
| `DEBUG` | начало тика; результат триггера каждого правила (имена сработавших тикеров); посчитанный `quantity` для каждой пары `(rule, ticker)`; запись каждой исполненной сделки; конец тика с equity/cash/positions |
| `TRACE` | каждое обращение к UDF и поставщику данных: имя функции, аргументы, результат, попадание в кэш, `duration_ms`. Также длительность каждого SQL-вызова триггера / `Action.quantity` и длительность тика целиком. |

**Уровень по умолчанию — `DEBUG`**. На этом уровне в файле есть полная картина каждого тика: что вернул триггер, какие кандидаты сформированы, что из них исполнено, чем закончился тик. `TRACE` включается отдельным флагом для совсем подробной диагностики.

**Live-tail в UI.** Эндпоинт `GET /api/backtest/runs/{id}/log?after_byte=N` отдаёт хвост файла после байта `N`. Виджет «Лог прогона» опросом раз в секунду тянет новые строки и дописывает в свою консоль. Это даёт пользователю отчётливо видеть «что делает движок» в реальном времени, не переключаясь в терминал. После завершения прогона тот же эндпоинт работает и отдаёт лог целиком.

**Поиск узких мест.** Отдельной встроенной системы профилирования в движке нет — всё, что нужно, уже есть в TRACE-логе. Workflow:

1. Запустить прогон с уровнем `TRACE` (флаг или конфиг сервера).
2. Лог автоматически содержит `duration_ms` у каждого SQL-вызова, UDF-вызова и тика целиком, а также указание правила-источника у строк триггера и кандидатов.
3. После прогона — анализ:
   - Простыми `grep` / `awk` собрать суммарное время по UDF, по правилам, по этапам тика — структура строк предсказуемая (пары `ключ=значение`).
   - Или скормить файл LLM с просьбой найти самые медленные операции и закономерности.
   - Опционально написать скрипт `scripts/analyze_backtest_log.py`, который выводит готовую сводку (накопится по мере необходимости).

Никаких новых таблиц, сущностей или эндпоинтов это не требует. Накладные расходы на сам профайлинг минимальны: только дополнительные поля в TRACE-строках; уровень включается, когда нужен, и не действует в обычном режиме.

### 6.5. Способы запуска

Прогон можно стартовать тремя способами, все ведут к одному `POST /api/backtest/run`:

- **UI.** Виджет `BacktestRunDialog` — пользователь руками выбирает стратегию, окружение и исследование.
- **REST.** Прямой вызов API (см. 6.3) — для интеграций, скриптов, ноутбуков.
- **LLM-агент.** Subagent, выполняющий контракт [`BACKTEST_RUNNER_AGENT.md`](BACKTEST_RUNNER_AGENT.md): пользователь говорит «прогони стратегию X на окружении Y», агент сам сверяет покрытие данных, делает smoke-прогон на коротком интервале, потом длинный, читает логи, отдаёт отчёт с метриками и удаляет smoke-артефакты. Полезен для рутинной проверки гипотез без переключения в UI.
