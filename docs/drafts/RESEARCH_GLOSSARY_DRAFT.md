# Исследования (Research) — концептуальный драфт

Драфт описывает добавление **исследований** как организационной сущности поверх стратегий, правил, окружений и прогонов бэктеста. Спека финального вида (`docs/SPEC_RESEARCH.md`) пишется после реализации первой вертикали — драфт фиксирует только концепцию.

Ниже используются термины из `docs/GLOSSARY.md` (раздел 2: «Сущности приложения»).

---

## Часть 1. Зачем нужны исследования

К моменту накопления нескольких десятков стратегий и правил рабочее пространство перестает быть удобным: при выборе стратегии для нового прогона приходится листать список из всех когда-либо созданных. Часть из них относится к одной задаче, часть — к другой, но границы этих задач существуют только в голове аналитика.

**Исследование** — именованная группа, в рамках которой аналитик ведёт работу над **одной целью** (один связный круг гипотез). Конкретные роли исследования:

1. **Контекст работы.** Когда аналитик заходит в приложение, он сначала выбирает, в каком исследовании работает. После этого все основные виджеты (редактор стратегий, редактор правил, редактор окружений, диалог запуска прогона, журнал прогонов) показывают только то, что относится к выбранному исследованию.
2. **Контейнер для отчёта.** В конце исследования аналитик пишет выводы и получает готовый текстовый отчёт по всему, что было сделано в его рамках: какие стратегии и правила были созданы, в каком окружении прогонялись, какие метрики получены.
3. **Логическая граница.** Удаление исследования каскадно удаляет его приватные стратегии, правила, окружения и **все** его прогоны. Параллельные исследования не пересекаются.

Без исследований аналитик может работать в одном пространстве, но эта модель не масштабируется на продолжительную работу с десятками гипотез.

## Часть 2. Сущность исследования

Исследование характеризуется именем, опциональным описанием идеи и опциональным разделом выводов.

- **Имя** — короткая фраза, по которой исследование выбирается в переключателе и появляется в шапке отчёта. Уникально среди всех исследований. Можно переименовывать в любой момент.
- **Описание идеи** — свободный текст. Заполняется на старте исследования (что хотим выяснить, какие гипотезы планируем, какой контекст), дополняется по ходу. Может быть пустым.
- **Выводы** — свободный текст. Заполняется в конце, когда исследование можно считать завершённым. Войдут в финальный раздел отчёта. Может быть пустым.

Исследование **не имеет** формального статуса «открыто/закрыто/архивировано». Завершённость определяется тем, написаны ли выводы. Если у аналитика будет потребность скрывать неактивные исследования из переключателя — добавим механизм архивации отдельной итерацией.

### Системное исследование `Default`

При первом запуске приложения автоматически создаётся одно исследование с именем `Default`. Это **системное** исследование, к которому привязываются все ранее существовавшие прогоны при миграции, и в которое попадают новые пользователи, ещё не создавшие своё исследование.

`Default`-исследование **нельзя переименовать** и **нельзя удалить**. Это инвариант, опираясь на который UI гарантированно может переключиться на исследование при удалении любого другого, и аналитик никогда не окажется в состоянии «нет ни одного исследования».

## Часть 3. Приватные и общие сущности

`Research` ограничивает видимость **стратегий**, **правил** и **окружений**, а также служит контейнером для **прогонов**. Принадлежность управляется одним полем-ссылкой `research_id` у каждой из этих сущностей. Поведение поля различается:

| Сущность | Семантика принадлежности |
|---|---|
| Стратегия, Правило, Окружение | **Опциональная**. Если ссылка пустая — сущность считается **общей** и видна во всех исследованиях. Если заполнена — сущность **приватная** и видна только в одном указанном исследовании. |
| Прогон бэктеста, Результат бэктеста | **Обязательная**. Прогон **всегда** принадлежит ровно одному исследованию — тому, из которого был запущен. Общих прогонов не бывает. |

### Назначение общих сущностей

Общая сущность нужна для случаев, когда один и тот же артефакт логически переиспользуется в разных исследованиях. Типичные примеры:

- **Окружение** `LKOH full history 2002-2025` — объективная пара (тикер, период, стартовый капитал), не зависящая от целей исследования. Создавать его заново в каждом новом исследовании — неоправданная рутина.
- **Стратегия-baseline** (например, простой buy-and-hold) — может быть нужна как точка сравнения в нескольких разных исследованиях.
- **Базовое правило** (например, «купить тикер на весь свободный кэш») — может входить в несколько разных стратегий, в том числе из разных исследований.

### Видимость в интерфейсе

В исследовании по умолчанию показываются **только приватные** сущности. Это даёт аналитику чистый рабочий список, не загромождённый артефактами параллельных задач. Чтобы получить доступ к общим — у каждого редактора есть переключатель «Показать общие». При его включении общие сущности появляются в списке вместе с приватными и помечаются визуально (как именно — деталь UI).

### Перевод между общим и приватным состоянием

Аналитик может **расширять** или **сужать** видимость существующей сущности:

- **Сделать общую сущность приватной** для текущего исследования — разрешено, **если** на эту сущность не ссылается ни один прогон, принадлежащий другому исследованию. Иначе чужой прогон стал бы ссылаться на невидимую ему сущность.
- **Сделать приватную сущность общей** — разрешено всегда, это только расширяет видимость.

Перевод не запрещает дальнейшие изменения (общая → приватная → снова общая), пока сохраняется инвариант видимости относительно прогонов.

### Удаление общей сущности

Удаление общей сущности разрешено, **если** на неё не ссылается ни один прогон ни в одном исследовании. Это симметрично переводу: пока есть зависимости, состояние сохраняется.

## Часть 4. Активное исследование как контекст работы

Аналитик в любой момент работает **в контексте ровно одного активного исследования**. Это состояние:

- **Обязательное.** Без выбранного активного исследования основные функции приложения недоступны: нельзя создавать стратегии, правила, окружения, нельзя запускать прогоны, нельзя смотреть журнал прогонов. Запрет реализуется и на уровне UI (виджеты неактивны / экран блокирует работу), и на уровне API (запросы без идентификатора активного исследования отклоняются).
- **Сохраняемое между сессиями.** Активное исследование запоминается на стороне клиента, переживает перезагрузку страницы. Бэкенд не хранит «текущее» исследование пользователя — это контекст конкретного UI-сеанса.
- **Переключаемое.** Аналитик может переключиться на другое исследование в любой момент. После переключения весь зависящий UI перерисовывается под новый контекст.
- **Привязка прогона.** Когда аналитик запускает прогон в активном исследовании `R`, прогон получает `research_id = R` независимо от того, общие или приватные у него стратегия и окружение. Тот же общий baseline, прогнанный из двух разных исследований, даст два разных результата в двух разных журналах прогонов.

Виджеты, не связанные с бэктестом (просмотр свечей, событийный анализ, поиск прецедентов), **не зависят** от активного исследования: они работают с общими данными (свечи, дивиденды, события, прецедентные запросы) и доступны всегда.

## Часть 5. Жизненный цикл исследования

Типовой сценарий:

1. **Создание.** Аналитик нажимает «Создать исследование», вводит имя и (опционально) описание идеи. UI автоматически переключается на новое исследование.
2. **Работа.** В рамках исследования создаются приватные стратегии и правила, при необходимости — приватные окружения. Запускаются прогоны, читаются метрики и журналы сделок. Описание идеи может дополняться по мере появления новых наблюдений.
3. **Завершение.** Аналитик заполняет раздел выводов. Формальной кнопки «закрыть исследование» нет — наличие текста выводов и есть критерий завершённости.
4. **Отчёт.** В любой момент (но логичнее — после завершения) аналитик получает текстовый отчёт по исследованию: имя, описание, перечень всех приватных артефактов, журнал прогонов с метриками, выводы.
5. **Архивация / удаление.** Исследование можно удалить вручную (с подтверждением) — каскадно удаляются все его приватные стратегии, правила, окружения и все прогоны. Общие сущности, привязанные к нему через прогоны, остаются — но удалившиеся прогоны больше на них не ссылаются. `Default`-исследование удалить нельзя.

## Часть 6. Поведение API

API остаётся в текущей форме (CRUD стратегий, правил, окружений; запуск, прогресс, отмена прогона; чтение результатов и журнала сделок), но получает два изменения:

1. **Новая группа эндпоинтов** для CRUD исследований: создание, переименование, изменение описания и выводов, удаление, чтение списка и одного исследования. Плюс эндпоинт получения **отчёта** по исследованию (см. часть 7).
2. **Сквозной идентификатор активного исследования.** Все запросы, изменяющие состояние или возвращающие списки стратегий/правил/окружений/прогонов, обязаны передавать идентификатор активного исследования. Запрос без него отклоняется. Ответы отфильтровываются по правилу видимости из части 3 с учётом флага «показывать общие».

## Часть 7. Отчёт по исследованию

Отчёт — основной результат исследования для внешнего читателя. Это структурированный текст, в котором:

- В шапке — имя исследования и описание идеи.
- Перечень созданных в исследовании приватных стратегий, правил и окружений с их описаниями.
- Журнал всех прогонов исследования с метриками: общая и годовая доходность, максимальная просадка, Sharpe, profit factor, win rate, число сделок, окружение и стратегия.
- В подвале — раздел выводов.

**Логика отчёта живёт на бэкенде.** Эндпоинт получения отчёта возвращает готовый текст в текстовом формате, который удобно сохранять и пересылать (например, Markdown). Клиент рендерит его в виджете-превью и предлагает скачать. Это даёт единственную точку истины по структуре отчёта и позволяет добавлять новые форматы (HTML, PDF) как варианты того же эндпоинта.

### На будущее: кастомный отчёт

Текущая версия отчёта — автоматическая (из всех данных исследования по фиксированному шаблону). В будущей итерации запланирована возможность кастомного отчёта: аналитик собирает структуру вручную из текстовых блоков и **ссылок** на конкретные прогоны, в том числе на прогоны из **других** исследований. Это превращает отчёт в более гибкий инструмент, похожий на ноутбук «текст + результаты». Концептуально: новый тип сущности «блок отчёта», упорядоченный список которых принадлежит исследованию. В этой итерации не делается, но при проектировании текущей схемы учитывается, что эта возможность появится позже.

## Часть 8. Миграция существующих данных

К моменту внедрения исследований в БД уже существуют стратегии, правила, окружения и прогоны без поля `research_id`. Стратегия миграции:

1. Создать системное `Default`-исследование.
2. Все существующие стратегии, правила и окружения становятся **общими** (их `research_id` остаётся пустым). Это соответствует фактическому положению дел: до введения исследований все артефакты были «глобальными».
3. Все существующие прогоны привязываются к `Default`-исследованию (их `research_id` обязателен и непустой).

После миграции аналитик заходит в приложение и оказывается в `Default`-исследовании. Все прежние прогоны видны на своём месте; стратегии и правила видны при включении переключателя «Показать общие». Дальнейшая работа ведётся в новых исследованиях, в которые аналитик может переводить нужные общие сущности в приватные по мере организации тематических групп.

## Часть 9. Открытые вопросы

На момент драфта открытых вопросов нет — концептуальная модель закрыта. Мелкие решения уровня UI (как именно выглядит переключатель исследования, где располагается тоггл «Показать общие», какой формат отчёта по умолчанию) принимаются в реализации.

## Приложение. Закрытые вопросы

Вопросы, которые обсуждались при проектировании и закрыты решением:

1. **Модель группировки: тег / папка / жёсткая принадлежность.** Закрыт в пользу жёсткой принадлежности с опциональным «общим» состоянием. Тег-модель отвергнута: размывала границу исследования и делала отчёт неоднозначным.
2. **Можно ли добавить чужой прогон в исследование.** Нет; вместо этого в будущем планируется механизм **цитирования** прогонов из других исследований в кастомном отчёте, без перемещения.
3. **Окружения — общие или приватные.** Гибрид: общие по умолчанию (для типовых пресетов вроде `LKOH full history 2002-2025`), приватные по необходимости (для исследовательских песочниц).
4. **Можно ли менять состояние общая ↔ приватная после создания.** Можно, при условии сохранения инварианта видимости относительно прогонов.
5. **Видимость в UI: приватные / приватные + общие.** По умолчанию только приватные, общие появляются по тоггл-переключателю.
6. **Принадлежность прогона при общей стратегии и общем окружении.** Прогон принадлежит активному исследованию на момент запуска. Это даёт возможность одну и ту же общую стратегию прогонять из разных исследований и видеть их результаты в разных журналах.
7. **Поле «гипотеза».** Не вводится. Исследование — это группа гипотез, а не одна; формулирование гипотез остаётся в свободном поле описания.
8. **Поле `is_default` или захардкоженное имя.** Захардкоженное имя `Default`. Один-единственный системный объект, поведение которого определяется именем, не требует отдельного флага в схеме.
9. **Логика отчёта: бэк или фронт.** Бэкенд. Одна точка истины по структуре, расширяется на новые форматы вывода через варианты эндпоинта.
10. **Что делать с уже накопленными данными при миграции.** Все стратегии/правила/окружения становятся общими; все прогоны попадают в `Default`-исследование.
11. **Что делать с пользователем без активного исследования.** Заблокировать основной функционал и заставить выбрать или создать. По умолчанию активным становится `Default`.
