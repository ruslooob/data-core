### Проверка 1: Линии факт vs прогноз

**Что рисуем.** Два временных ряда на оценочном окне (по умолчанию `200` торговых дней до окна события):

- **Факт.** Фактическая дневная лог-доходность акции `r_t`.
- **Прогноз.** Предсказание модели `E[r_t] = α + β · r_m(t)`.

**Зачем именно это и почему первой.** В окне события модель проверить нельзя — фактическая доходность есть, но «как было бы без события» неизвестно по построению. На оценочном окне сравнение прямое: фактический ряд есть, предсказание модели есть. Если модель плохо работает на `200` спокойных днях, нет оснований верить ей на `11` днях окна события.

Аналогия. Синоптик каждый день предсказывает температуру; вечером записывают фактическую. Через `200` дней получаются две линии. Если идут рядом — синоптику можно верить, его завтрашний прогноз содержателен. Если расходятся всюду — прогнозу веры нет, фактическая погода живёт своей жизнью.

**Как аналитик читает график.**

- **Линии идут рядом, повторяют форму друг друга.** Модель ловит акцию. Зелёный свет: AR/CAR в окне события содержательны.
- **Фактическая прыгает, модельная плоская.** Модель не объясняет акцию. Типичная картина для второго эшелона (низкая ликвидность, слабая корреляция с IMOEX). AR/CAR в окне события — это собственная шумность акции, а не отклик на событие. Соответствует низкому `R²` (проверка 2).
- **Линии идут рядом, но в нескольких днях огромный разрыв.** Кандидаты на «чужие события в оценочном окне» (отчётность, дивиденд, корпоративная новость той же акции, попавшая в estimation). Эти дни сильно раздувают `σ_ε` — фоновый шум, с которым потом будут сравниваться AR в окне события. Требуют проверки календаря и решения об исключении / винзоризации (см. §7.3).

**Решения по реализации (график).**

- Две линии (факт и прогноз). Без маркеров точек.
- Виден **весь** интервал оценочного окна через горизонтальный скролл графика. Возможность пробежать глазами весь интервал — ключевое требование.
- Стилистика: линия факта — ярче, основной акцент; линия прогноза — приглушённая, пунктиром.
- Легенды нет (на этом этапе).
- При отсутствии данных — компактная заглушка вместо графика.

**Решения по реализации (layout виджета).**

- Расширяется существующий `EventStudyWidget`, без отдельного виджета.
- Размер каждого графика **не привязан к размеру виджета**: у обоих графиков фиксированная высота.
- `CarChart` — основной артефакт, открыт по умолчанию, занимает видимую область при первой загрузке (фиксированная высота ≈ дефолтная высота виджета минус шапка).
- График факт vs прогноз — фиксированная высота ниже `CarChart`, доступен через **вертикальный скролл внутри виджета** (`overflow-y: auto`).
- Шапка управления **не sticky** — уезжает вверх вместе с контентом при скролле.
- Координатные шкалы у двух графиков **независимые**: `CarChart` сохраняет свою синтетическую `t`-ось `(−W..+W)`, факт vs прогноз использует реальные даты estimation окна.

**Контракт API.** Расширяется существующий `POST /api/event-study` — отдельного эндпойнта под диагностику не делаем (один расчёт = один ответ, без рассинхронизации). Поля плоские, без вложенной структуры — группировка под диагностику откладывается до момента, когда полей станет заметно больше.

К `EventStudyResponse` добавляются три ряда (одинаковой длины, в исходном порядке оценочного окна):

- `estimation_dates: list[str]` — даты оценочного окна (ISO), оставшиеся после фильтрации выбросов.
- `estimation_actual: list[float]` — фактическая дневная лог-доходность акции на этих датах. Шкала — доли.
- `estimation_predicted: list[float]` — предсказание модели на этих датах. Шкала — доли.

Инвариант:
`len(estimation_dates) == len(estimation_actual) == len(estimation_predicted) == estimation_window - outliers_removed`.

Разница `estimation_actual − estimation_predicted` равна `estimation_residuals` (которые уже считаются внутри `EventStudy.analyze`, но в response не пробрасываются).

**Отложено (не входит в P0).**

- **Подсветка выбросов.** Дни с `|r_t − E[r_t]| > k · σ_ε` отрисовываются красными точками поверх линий — прямое визуальное указание на кандидатов для исключения / проверки календаря. Требует выбора порога `k` и решения, как соотносится с `outlier_threshold` из `EventStudy`.

### Проверка 2: `R²` и `σ_ε`

Следующий шаг. На обсуждение:

- **Где отображать.** Числа в углу графика «факт vs прогноз» (компактная подпись над/под графиком) или отдельная строка-стрипа над графиком. В [EVENT_STUDY.md §7.2](../EVENT_STUDY.md) сказано «два числа в углу графика».
- **Что считать `R²`.** Доля дисперсии акции, объяснённая моделью. Для MarketModel — это просто квадрат корреляции `corr(r_i, r_m)²`. Считать на бэке (новое поле в `EventStudyResponse`) или на фронте из уже отдаваемых рядов.
- **Цветовая разметка.** В EVENT_STUDY.md обозначены три зоны (`R² > 0.4`, `0.2..0.4`, `< 0.2`). Решить, нужна ли подсветка цифры цветом (зелёный/жёлтый/красный), или достаточно просто числа.
- **`σ_ε` (`estimation_std`)** уже отдаётся бэком, новой работы не требует.

При обсуждении принять решения по этим трём пунктам, добавить контракт API (если `R²` считается на бэке), отправить в реализацию.
