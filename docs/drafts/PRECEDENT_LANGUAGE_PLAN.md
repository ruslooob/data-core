# Язык поиска прецедентов — вертикаль до работающего виджета

> Это черновик плана для редактирования. Источник правды — этот файл.
> Когда правки внесёшь, попроси меня обновить копию в `~/.claude/plans/playful-waddling-bubble.md`.

## Контекст

В проекте data-core уже есть черновик SQL-подобного DSL (`docs/ANOMALY_DSL.md`), задуманного для поиска аномалий. Пользователь редизайнит концепт: язык становится **общего назначения** (поиск событий по любым критериям, аномалии — частный случай), а первый его потребитель — **виджет-редактор по аналогии с SQL-editor**: ввёл текст запроса → выполнил → увидел таблицу.

Цель — пройти полную вертикаль: спецификация → парсер → интерпретатор → API → UI.

**Жёсткое ограничение пользователя:** код не пишется, пока не утверждены глоссарий и спецификация языка. Поэтому план разбит на Этап 0 (текстовый, без кода и без имён `.py`/`.tsx`-файлов как создаваемых артефактов) и пять рабочих этапов (1–5). Старый функционал anomaly-детектора (`anomaly_detector.py`, `AnomalyWidget.tsx`, эндпоинты `/api/anomalies/*`) **не трогаем** — новый виджет параллельный.

## Этап 0 — Глоссарий и спецификация

Артефакты живут в `docs/`. Этап делится на две последовательные под-итерации (0.1 — глоссарий, 0.2 — синтаксис); каждая закрывается явным «согласовано» или продолжается обсуждением.

### 0.1 — Глоссарий: имена сущностей

**Утверждено (2026-04-25):**

| Концепт | Русский | Код |
|---|---|---|
| Сам язык | язык поиска прецедентов | `PrecedentQueryLanguage` (PQL) |
| Запрос (текст) | прецедентный запрос | `PrecedentQuery` |
| Операция выполнения | поиск прецедентов | `PrecedentSearch` |
| Результат целиком | результат поиска | `PrecedentSearchResult` |
| Одна строка результата | прецедент (одна находка) | `Precedent` |

**Разница `Event` vs `Precedent` (зафиксировано):**
- `Event` — сырой факт из БД (`event_date`, `event_text`, `tags`); существует независимо от анализа.
- `Precedent` — пара `(event, ticker)` + посчитанные на ней метрики реакции (`car`, `vol_ratio` и т.п.); это «событие с известным эффектом».
- Один `Event` порождает **разные** прецеденты для разных тикеров.
- В DSL источник — `FROM events` (сырые факты). Результат — список прецедентов.

Также решить судьбу `AnomalyRule`, `EventFilter`, `Scan` — но это **позже**, не блокирует Этап 0.

**Куда пишем:** новый раздел в `docs/GLOSSARY.md` (имя файла — обсудим в 0.2 при структуре спецификации).

### 0.2 — Синтаксис (MVP-подмножество)

**Главный принцип, утверждённый пользователем (2026-04-25):** пользователь, знающий SQL, **не должен ничего доучивать** у нашей системы. Эталон — стандартный SQL, реализованный любой популярной СУБД.

**Стратегическое ограничение (2026-04-25):** проектируем с прицелом на **PostgreSQL** в будущем (целевая прод-СУБД). Сейчас работаем на менее тяжёлой движке (например, DuckDB или SQLite), но НИКАКИХ DuckDB-специфичных расширений: всё, что мы используем — должно один-в-один работать в Postgres.

**Функция `car()` поддерживает все три модели (2026-04-25):** `MeanAdjusted`, `MarketModel`, `CAPM`. Модель выбирается аргументом функции (например, `model => 'capm'`) с дефолтом `'market_model'`.

**Реализация `car()` — Python UDF, зарегистрированная в DuckDB (2026-04-25).** Функция остаётся Python-обёрткой над уже существующим `EventStudy.analyze()`; ETL для индекса и RUONIA не нужен — данные считаются через имеющиеся провайдеры. JOIN'ы и фильтрация выполняются движком (стандартный SQL), `car` работает в любом месте запроса (`SELECT`/`WHERE`/`ORDER BY`/`LIMIT`). Postgres-совместимость сохраняется: при переезде Python-UDF переписывается на `LANGUAGE plpython3u`, остальное остаётся.

**Видимая схема для пользователя (2026-04-25):**

| Объект | Тип | Назначение |
|---|---|---|
| `events` | таблица | Сырые события (`id`, `event_date`, `event_text`, ...). Источник правды. |
| `tags` | таблица | Справочник тегов (`id`, `code`, `type`). |
| `event_tags` | таблица | Связь many-to-many (`event_id`, `tag_id`). |
| `tagged_events` | вьюха | Удобная обёртка: одна строка на пару (event, tag). Колонки: `event_id`, `event_date`, `event_text`, `tag`, `tag_type`. Создаётся как `events JOIN event_tags JOIN tags`. Без фильтров по типу тега — пользователь сам решает, что искать. |
| `car(ticker, event_date, ...)` | функция | Кумулятивная аномальная доходность. Возвращает `NULL`, если по `ticker` нет данных или данных недостаточно для расчёта. Не падает. |

**Сигнатура `car()`** (именованные аргументы через `=>`, стандарт DuckDB):

| Параметр | Тип | Дефолт           | Назначение |
|---|---|------------------|---|
| `ticker` | TEXT | — обязательный   | тикер акции |
| `event_date` | DATE | — обязательный   | дата события |
| `model` | TEXT | `'market_model'` | `'mean_adjusted'` / `'market_model'` / `'capm'` |
| `window_before` | INT | `5`              | торговых дней до события |
| `window_after` | INT | `5`              | торговых дней после события |
| `estimation` | INT | `200`            | длина оценочного окна |
| `outlier_threshold` | DOUBLE \| NULL | `NULL`           | σ-порог фильтрации выбросов; `NULL` = без фильтра |

**Регистрация в DuckDB** — `SIDE_EFFECTS=False`, `deterministic=True`, чтобы движок мог кешировать одинаковые вызовы в рамках одного запроса (например, `car(...)` повторяется и в `SELECT`, и в `WHERE`).

**Формат ответа API (2026-04-25):** универсальный табличный. Объект `{ columns: [{name, type}], rows: [[...], ...], stats: {...} }`. Колонки и типы определяются `SELECT`-списком запроса, виджет рисует таблицу динамически.

**Обработка ошибок (2026-04-25):**
- Синтаксические и семантические ошибки запроса возвращаются с указанием **строки и колонки** в исходном тексте + сообщением от БД (DuckDB-сообщение пробрасывается пользователю как есть, без перевода).
- Ошибки данных (нет цен по тикеру, недостаточно данных для расчёта) → `car()` возвращает `NULL`, не падает; запрос исполняется, в колонке стоит `NULL`.
- Транспортная ошибка (бэкенд недоступен) → виджет показывает «Сервер недоступен».

**Жёсткий лимит выборки (2026-04-25):** `MAX_ROWS = 1000`. Применяется на стороне сервера всегда, даже если пользовательский `LIMIT` не задан или больше 1000. При срабатывании лимита в `stats` возвращается флаг `truncated: true`.

1. **Работа с тегами — УТВЕРЖДЕНО (2026-04-25): чистый SQL, через JOIN.** Никаких функций-сахаров (`HAS_TAG`, `IN tags` и т.п.) в MVP. Пользователь пишет:
   ```sql
   SELECT events.event_date, events.event_text
   FROM events
   JOIN event_tags ON event_tags.event_id = events.id
   JOIN tags       ON tags.id = event_tags.tag_id
   WHERE tags.code = 'LKOH'
   ```
   **Следствие 1:** в спецификации обязан быть явный раздел «Схема видимых таблиц» с именами таблиц/колонок (`events`, `event_tags`, `tags` и их полей). Это контракт, который пользователь видит и на котором строит запросы.
   **Следствие 2:** алиасы таблиц **УТВЕРЖДЕНО (2026-04-25): в MVP**. Поддерживаются обе формы — `FROM events e` и `FROM events AS e` (как в DuckDB).

**Что входит в MVP (2026-04-25):** **весь стандартный SQL, поддерживаемый DuckDB**. Мы не пишем свой парсер — пользовательский запрос идёт прямо в движок. Это значит, что доступны: `SELECT`/`FROM`/`JOIN`/`WHERE`/`ORDER BY`/`LIMIT`, агрегации (`COUNT`/`AVG`/`SUM`/...), `GROUP BY`/`HAVING`, подзапросы (`IN (...)`, `EXISTS (...)`, скалярные), `CASE WHEN`, `WITH` (CTE), оконные функции, `IN`/`BETWEEN`/`IS NULL`, алиасы таблиц и колонок — всё, что входит в стандартный SQL и реализовано в DuckDB.

Граница MVP проходит не по **синтаксису языка**, а по **набору наших объектов**, доступных пользователю:
- Таблицы: `events`, `tags`, `event_tags`.
- Представления: `tagged_events`.
- Функции: `car(...)`.

Параметры событийного анализа (модель, окна) задаются **аргументами `car()`** — не отдельным DSL-механизмом. Других «зарезервированных под нас» конструкций в языке нет.
