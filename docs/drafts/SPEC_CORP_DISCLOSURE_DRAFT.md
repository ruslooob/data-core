# Эмитенты и корпоративные события (драфт реализации)

> Драфт — не спецификация. Фиксирует решения по новой подсистеме «эмитенты + расширенная карточка бумаги + корпоративные события с e-disclosure». Разделы с пометкой `TBD` сами по себе служат повесткой того, что осталось обсудить.

## Контекст

Сейчас в БД по бумаге хранится практически только тикер и имя; эмитента как сущности нет вовсе. Из событий присутствуют дивиденды, сплиты и решения ЦБ по ставке. Для event study этого мало: ключевые драйверы котировок — корпоративные сообщения эмитента (раскрытие отчётности, объявления и исполнения программ обратного выкупа, решения совета директоров) — в БД отсутствуют.

Цель — добавить три источника данных к существующей модели:

1. **Эмитент** как самостоятельная сущность с юридическими реквизитами (ИНН, ОГРН) и человекочитаемыми наименованиями.
2. **Расширенная карточка бумаги** — поля, которые MOEX отдаёт по каждой ценной бумаге (ISIN, дата начала торгов, уровень листинга, тип, объём выпуска и др.) и которые сейчас игнорируются.
3. **Корпоративные события эмитента** — раскрытия с портала e-disclosure.ru, ограниченные на первой итерации четырьмя самыми «громкими» типами.

## Принцип P0

Охват по эмитентам — все, у которых в БД есть хотя бы одна бумага (без отбора по ликвидности или капитализации). Ограничения P0 — по перечню типов событий: минимальный набор с однозначной интерпретацией. Расширение списка типов и углубление карточки эмитента — за пределами P0; повестка по этим темам — в разделах `TBD` ниже.

## Сущности и связи

**Эмитент** — юридическое лицо, выпустившее ценную бумагу. Один эмитент может выпустить несколько бумаг (типовой пример: обыкновенная и привилегированная акции). Эмитент опознаётся по ИНН.

**Бумага** — расширение существующей записи о ценной бумаге. Сохраняет существующий первичный ключ (тикер MOEX) и добавляет ссылку на эмитента плюс набор биржевых характеристик. Связь с эмитентом — Many-to-One.

**Корпоративное событие** — раскрытие информации, опубликованное эмитентом на портале e-disclosure.ru. С точки зрения модели данных физически кладётся в существующую таблицу событий, без структурных изменений. Связь с конкретными бумагами эмитента осуществляется через существующий механизм тегов: на каждое корпоративное событие в `event_tags` создаются связи со всеми бумагами, принадлежащими эмитенту на момент загрузки. Дублирование сознательное (см. ниже про скрытую зависимость).

### Скрытая зависимость связи «корпоративное событие → бумага»

Связь корпоративного события со списком бумаг эмитента застывает в момент загрузки. Если позже у эмитента появляется новая бумага (новый выпуск, новая категория), уже загруженные корпоративные события не получат тег этой бумаги автоматически — требуется backfill. Это осознанный компромисс в пользу простоты модели; альтернатива (хранение `emitter_id` непосредственно в событии и вычисление связи через JOIN) обсуждалась и отвергнута на этапе проектирования. Возврат к альтернативе технически возможен и обратим.

## Типы событий первой волны

На P0 загружается четыре типа корпоративных событий. ID на портале e-disclosure указаны для отслеживания контракта, в БД они не сохраняются — событие в БД опознаётся по тегу типа.

| Тег события | Тип на e-disclosure | Что закрывает |
|---|---|---|
| `REPORT_IFRS` | Раскрытие эмитентом бухгалтерской отчётности в стандартах МСФО или US GAAP | Основная отчётность голубых фишек, наиболее сильная реакция котировок |
| `REPORT_RSBU_ANNUAL` | Раскрытие в сети Интернет годовой бухгалтерской отчётности | Годовая РСБУ — для эмитентов без МСФО |
| `BUYBACK_ANNOUNCE` | Принятие решения о приобретении размещённых эмитентом акций | Объявление программы обратного выкупа |
| `BUYBACK_EXECUTE` | Приобретение эмитентом собственных голосующих акций | Фактическое исполнение программы выкупа |

Расширение перечня (квартальные отчёты, консолидированная финансовая, squeeze-out, погашение акций) — отдельной итерацией, см. `TBD` ниже.

## Источники данных

### MOEX ISS

- **Перечень бумаг фондового рынка** — `/iss/securities.json?engine=stock&market=shares`. Возвращает по каждой бумаге набор полей, достаточный для одновременного заполнения и расширенной карточки бумаги, и базовой записи эмитента (ИНН, ОКПО, юридическое наименование). Пагинация курсором. За один проход — все ценные бумаги, торгующиеся на фондовом рынке MOEX.
- **Карточка эмитента, расширенная** — `/iss/emitters/{emitter_id}.json`. Поштучно. Добавляет к базовой записи эмитента ОГРН, ОКСМ и транслитерированное наименование. На P0 не требуется; вынесено в `TBD`.

### e-disclosure.ru

- **Поиск раскрытий** — POST `/api/search/sevents`. Контракт описан ниже в разделе про загрузчик. Фильтр по эмитенту — по ИНН в текстовом поле поиска. Фильтр по типам сообщения — повторяющимся ключом с числовым идентификатором типа.

## Идентификаторы и идемпотентность

| Сущность | Стабильный ключ | Источник |
|---|---|---|
| Эмитент | `emitter_id` MOEX | `/iss/securities.json` или `/iss/emitters/{id}` |
| Бумага | тикер MOEX (`SECID`) | существующий ключ |
| Корпоративное событие | `pseudoGUID` e-disclosure | `/api/search/sevents` |

Внутренний идентификатор эмитента в системе e-disclosure (`companyID`) хранится опционально и нужен только для построения внешней ссылки на карточку компании (`portal/company.aspx?id=...`). Как первичный ключ не используется: цепочка опознавания идёт через ИНН, который стабилен и един для обеих систем.

Идентификатор события `pseudoGUID` детерминирован и не меняется при повторной выдаче того же события — поэтому идемпотентность загрузки достигается на уровне `INSERT ... ON CONFLICT DO NOTHING` по первичному ключу события.

## Загрузчики

Общие принципы (двухступенчатость «парсер → файл → загрузчик в БД», инкрементальная загрузка, sanity-проверки, overlap-проверка) — те же, что и для существующих источников; описаны в [SPEC_LOADERS.md](../SPEC_LOADERS.md).

### load_moex_securities_list.py

Источник: ISS MOEX. Что грузит: расширенную карточку каждой ценной бумаги фондового рынка плюс минимальную карточку её эмитента (ИНН, ОКПО, юридическое наименование). Результат — два сырых CSV-файла с фиксированными именами; идемпотентность — по дате модификации файла (повторный запуск в течение того же дня — no-op).

Реализован в две фазы. Первая — батч-листинг `/iss/securities.json?engine=stock&market=shares` с пагинацией. Возвращает по каждой бумаге базовые поля (тикер, ISIN, регистрационный номер, юридическое наименование, тип бумаги, основной торговый режим) и поля связанного эмитента (`emitter_id`, ИНН, ОКПО, юридическое наименование). Вторая — поштучное обогащение через `/iss/securities/{secid}.json`: добавляет к карточке бумаги поля, отсутствующие в батч-выдаче (LATNAME, ISSUEDATE, ISSUESIZE, FACEVALUE, FACEUNIT, LISTLEVEL). Запросы второй фазы параллелятся.

Уникальность эмитента — по `emitter_id` MOEX; повторяющиеся в выгрузке эмитенты (например, обыкновенная и привилегированная акции одного банка) дают одну запись.

В P0 пропускаются бумаги без `emitter_id` и без ИНН (иностранные DR, фиксинги, индексы) — для них нет российского эмитента, события на e-disclosure тоже не загружаются.

Заменяет ранее планируемый в [SPEC_LOADERS.md](../SPEC_LOADERS.md) загрузчик `load_moex_securities_list.py` — его роль сводилась к простому списку тикеров, теперь расширяется до полной карточки.

### load_edisclosure_events.py

Источник: e-disclosure.ru, ручка POST `/api/search/sevents`. Что грузит: корпоративные события четырёх типов (см. выше) по каждому эмитенту, у которого в БД есть хотя бы одна бумага.

Принцип работы:

1. Список эмитентов берётся из `emitters` через JOIN с `stocks` (только те, у которых есть бумага в БД — иначе событие некуда привязать).
2. Для каждого эмитента — POST на ручку с параметрами: ИНН эмитента в полях поиска по компании, числовые идентификаторы выбранных типов событий повторяющимся ключом, окно дат (incremental — от последней даты события в БД минус overlap до сегодня; initial — от заведомо ранней даты до сегодня).
3. Пагинация по странице, пока не пройдены все доступные страницы выдачи.
4. Каждое событие из ответа кладётся в файл `data/events/edisclosure_<inn>_<from>_<till>.json` с теми же сырыми полями, что отдаёт API. Идемпотентность — на уровне файла: если файл с тем же окном уже существует, эмитент пропускается.

Загрузка в БД (через `load_data_to_postgres.py`): на каждое событие — одна строка в `events` (с детерминированным `id = edisc:<pseudoGUID>`), плюс связи в `event_tags` со всеми бумагами эмитента и с тегом типа события. Заодно заполняется `emitters.e_disclosure_company_id` — внутренний идентификатор эмитента в системе e-disclosure, нужный для построения внешней ссылки на карточку компании. Дубли уходят в no-op через `ON CONFLICT DO NOTHING` по первичному ключу события.

### Аутентификация на e-disclosure

Портал закрыт WAF Servicepipe. Программный доступ требует наличия cookie сессии, передаваемых через переменные окружения. На практике WAF самостоятельно перевыдаёт основные cookie через 307-flow при первом запросе, а валидация на стороне приложения мягкая, поэтому передача заведомо устаревших значений всё равно даёт рабочую сессию. Тем не менее cookie остаются обязательными — без них API отдаёт пустой результат (`totalItems = 0`) на корректный по форме запрос.

Cookie берутся из браузера один раз и обновляются при изменении поведения WAF. Полный автоматизированный обход через headless-браузер (Playwright и т.п.) сознательно отвергнут как избыточный для P0.

### Маппинг типов событий

API не возвращает идентификатор типа в каждом событии — связь «событие → тег нашей системы» строится по точному тексту поля `eventName`. Маппинг ведётся в `load_data_to_postgres.py`. Это хрупкое решение: при добавлении новых типов на стороне портала или вариативности написания (с «ё» / без «ё», с завершающим переносом строки) загрузчик отбрасывает события с предупреждением, не падая. Расширение словаря — по факту обнаружения новых вариантов.

Дополнительно: API по фильтру четырёх выбранных типов иногда возвращает родственные события «соседних» подтипов (например, «Сообщение о раскрытии…», «Принятие эмитентом решения о применении МСФО…»). Они не входят в наш строгий маппинг и отбрасываются. Это сознательный выбор в пользу однородности данных — смешивать подтипы в одном теге методологически нечисто.

## Ограничения источников

### Лимит выдачи на e-disclosure

API `/api/search/sevents` ограничивает выдачу одного запроса значением, доступным через поле `maxFoundEventsToShow` ответа (на момент проектирования — 1200 событий). Если в реальности по фильтрам найдено больше — лишние молча отбрасываются. Парсер при приближении к лимиту обязан бить запрос по более узким окнам дат и повторять, пока каждое окно укладывается в лимит. При P0-объёме (четыре типа событий на одного эмитента) превышение лимита маловероятно даже на горизонте нескольких лет; защита нужна как страховка от долгих initial-загрузок и от случаев, когда тип события массовый.

### Истечение WAF-cookie

Если WAF перестаёт пропускать сессию, ручка возвращает HTML challenge-страницу вместо JSON. Парсер распознаёт ситуацию по Content-Type ответа, останавливается с диагностическим сообщением и инструкцией обновления cookie. Уже сохранённые файлы по обработанным эмитентам остаются на диске; при повторном запуске после обновления cookie они пропускаются по idempotency.

### Расширенная карточка эмитента

### Связь корпоративного события с тикером через `emitter_id`

Текущая модель связи — через дублирование тегов; обсуждалось и принято на этапе проектирования. Возврат к альтернативе (`events.emitter_id` + JOIN) обратим. Триггер пересмотра — появление сценария, где состав бумаг эмитента активно меняется и backfill становится регулярной операцией.

### Иные источники корпоративных событий

В рамках P0 — только e-disclosure.ru. Расширение списка источников (Интерфакс СКРИН, СПАРК, MOEX disclosure) — отдельной итерацией; полезно как cross-validation того, что приходит с e-disclosure.

### Расширение словаря типов событий

API по фильтру четырёх выбранных типов иногда возвращает события «соседних» подтипов с другим текстом `eventName`. На полном прогоне это около 1% выдачи: устаревшие формулировки («Сообщение о раскрытии на странице в сети Интернет годовой бухгалтерской отчётности»), кастомные тексты с именем эмитента, «решение о применении МСФО» вместо самого раскрытия. Они корректно отбрасываются с предупреждением. Решение по каждому подтипу — отдельно: расширить словарь и грузить, или оставить отброшенным как методологически отличающееся.

### Покрытие тикеров company-тегами

Существующая модель `event_tags` требует, чтобы любой тикер, используемый как тег события, имел запись в `tags` с типом `company`. На момент реализации в БД 12 эмитентов имели бумагу в `stocks`, но ни одного company-тега для неё в `tags`. Загрузчик корректно пропускает такие эмитенты (их файлы остаются на диске в `data/events/`), но события в БД не попадают до тех пор, пока соответствующий тикер не зарегистрирован как company-тег. Регистрация company-тегов — за пределами текущего загрузчика; при следующем прогоне `load_data_to_postgres.py` после регистрации события подхватятся.
