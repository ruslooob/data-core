# Параллельный доступ к DuckDB — драфт

> Сессия от 2026-05-03. Записан как заметка, к которой можно вернуться позже,
> когда станет реальной проблема с производительностью или количеством
> параллельных прогонов.

## Корень проблемы

Два архитектурных факта DuckDB-Python:

1. Один и тот же DuckDB-коннект **не потокобезопасен** при concurrent
   `execute()` из разных потоков. На большом числе параллельных запросов из
   FastAPI threadpool ловили segfault (exit 139) и зависшие потоки в
   `CloseWait`.
2. На Windows DuckDB **не даёт двум разным коннектам** одновременно открыть
   один файл (даже если один read-only) — `IOException: File is already open`.

Из этих двух следует: если в одном Python-процессе несколько потоков делают
запросы к одной БД через **один** коннект — может упасть. А если завести
**второй** коннект к тому же файлу — упадёт точно.

Частичный фикс уже сделан: `_get_precedent_engine()` возвращает
`con.cursor()` per request. Курсор изолирует поток, и пока пишет один —
остальные в этом курсоре сериализуются. Это снимает большинство случаев
segfault при типовой нагрузке (один пользователь, редкие записи), но **не**
решает фундаментально: при достаточном параллелизме DuckDB всё равно может
дать сбой.

## Принятая на сегодня архитектура (2 роли)

- **Web-процесс (FastAPI).** Единственный писатель в `data-core.duckdb`.
  Все INSERT/UPDATE/DELETE идут через него. Курсор-per-request.
- **Backtest-воркер** (отдельный процесс на каждый прогон). Открывает
  свой DuckDB-коннект только в режиме `:memory:` (никакого файла). Загружает
  spec стратегии/окружения через **отдельный кратковременный read-only
  коннект** к persistent-БД либо через предзагрузку из веб-процесса в
  Python-объекты до старта воркера. По завершении прогона возвращает
  результат веб-процессу через `multiprocessing.Queue`. Веб-процесс
  атомарно пишет результат в `backtest_results` + `trade_journal`.

Что это даёт:
- Веб-сервер не блокируется длинным прогоном.
- Только один писатель в файл — concurrent-write невозможен.
- Параллельные прогоны работают независимо в `:memory:`, в конце по очереди
  отдают результаты веб-писателю.

Чего не даёт:
- Если параллельных прогонов будут десятки в секунду, веб-процесс станет
  узким местом записи. Но для текущего use-case (один пользователь, один
  прогон обычно одновременно) это не проблема.

## Архитектура «3 роли» — для возможного будущего перехода

Если когда-то возникнет реальная нагрузка, при которой веб-процесс не
успевает записывать или его блокировка на запись становится заметной для UI,
архитектура расширяется до трёх ролей:

- **DB writer-процесс.** Единственный держит **write-коннект** к
  `data-core.duckdb`. Слушает очередь команд. Все остальные процессы (FastAPI,
  backtest-воркеры) посылают сюда write-операции и ждут ответа.
- **Web-процесс (FastAPI).** Читает БД через свой read-only коннект. Для
  любой записи кладёт команду в очередь writer'a.
- **Backtest-воркер.** То же самое: чтение spec через свой read-only коннект,
  запись результата через очередь writer'а — без посредничества web.

Концептуальная стоимость перехода:
- Каждый `con.execute('INSERT ...')` / `'UPDATE ...'` / `'DELETE ...'` в
  `main.py` превращается в `submit_write(...).await_result()`. Это десятки
  точек.
- Транзакции (например, текущий каскад в `delete_strategy`) посылаются как
  атомарный батч команд — нужен либо API «отправь N команд одной транзакцией»,
  либо `begin/commit` через очередь.
- Появляется протокол команд между всеми участниками и writer'ом
  (form, error handling, timeouts).
- Развёртывание усложняется: writer должен подняться раньше всего
  остального; нужен health-check и стратегия рестарта при крахе.
- Read-only коннекты у всех участников — это нативная возможность DuckDB,
  не требует обвязки.

Цена в производительности — практически отсутствует: latency на запись
вырастает на десяток миллисекунд (IPC), что незаметно для UI.

## Когда возвращаться к этой заметке

Если хотя бы одно из следующих стало проблемой:

- UI «подвисает» на запись (создание правила/стратегии/окружения занимает
  больше пары секунд) при нагрузке, которая идёт параллельно с прогоном.
- Параллельные прогоны (несколько одновременно) реально нужны и упираются в
  очередь записи в веб-процессе.
- Бекенд снова падает с segfault DuckDB при штатной работе, и курсор-per-
  request уже не лечит.

Пока ничто из этого не наблюдается — сидим на 2 ролях, текущая архитектура
достаточна.

## Защита от утечек памяти (отложено в реализации)

Эти пункты намеренно **не** реализованы в первой версии 2 ролей — для текущего
сценария (один пользователь, один прогон одновременно) проблемы не будет.
Но при росте нагрузки или длительных сессиях нужно вернуться:

- **Очередь прогресса между воркером и веб-процессом.** Воркер должен слать
  прогресс с дросселем (раз в 0.5–1 секунду, не каждый тик). Очередь —
  bounded (`maxsize=8`), при переполнении использовать `put_nowait` с
  безопасным игнорированием (последнее значение прогресса всегда
  актуальнее устаревших). Хранится только **последнее** значение в
  `RunHandle.last_progress`, история не накапливается.
- **Словарь `_active_runs` в веб-процессе.** TTL после терминального
  статуса (`done`/`error`/`cancelled`): если фронт не опрашивал ≥ 5 минут —
  handle удаляется. Дополнительно жёсткий потолок (например, 50 handle'ов).
- **Поле `final_result` внутри `RunHandle`.** После того как `BacktestResult`
  атомарно записан в persistent, ссылка на него в `RunHandle` обнуляется —
  карточка достаётся из БД через `GET /api/backtest/results/{id}`, не из
  памяти.
- **Зомби-процессы воркера** при отмене. На `cancel()` ставим `cancel_event`,
  затем `process.join(timeout=10)`. Если не завершился — `process.terminate()`,
  потом `join(timeout=5)`, в крайнем случае `process.kill()`.
- **Орфан-воркеры при перезапуске веб-процесса.** Воркер живёт независимо;
  если веб упал — воркер остаётся. При следующем старте веб-процесса нужно
  пройтись `psutil` и убить висящие `python.exe` с маркером
  `backtest_worker`.

## Открытые вопросы (на момент написания)

- **Как backtest-воркер читает spec.** Два пути: (1) веб-процесс
  читает `Strategy/Rule/Environment` в Python-DTO и передаёт воркеру через
  pickle/queue до старта; (2) воркер открывает свой read-only коннект к
  файлу. Вариант 1 проще, не требует второго коннекта к файлу. Идём
  по нему по умолчанию.
- **Прогресс-канал.** В драфте бэктеста (Q23) — polling с
  `GET /api/backtest/runs/{id}/progress`. Источник прогресса — словарь
  `_active_runs` в памяти веб-процесса, куда воркер шлёт обновления через
  очередь. Структура хранения и формат сообщений — открыто, обсудим
  при реализации.
- **Отмена прогона.** Воркер должен периодически чекать флаг отмены.
  Простейший путь — `multiprocessing.Event`, который веб-процесс выставляет
  при `POST /cancel`. Воркер проверяет на каждом тике.
- **Что делать с коннектом FastAPI к persistent-БД при запуске воркера.**
  Сейчас он открыт на запись. Если воркер тоже захочет открыть файл (даже
  read-only) — на Windows упадёт. Поэтому **воркер не открывает файл вообще**
  — все нужные данные ему отдаются через queue до старта. Это и решает
  «двое держат один файл» без обвязки.
