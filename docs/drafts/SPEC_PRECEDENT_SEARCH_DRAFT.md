# Спецификация: поиск прецедентов (Precedent Search)

> **Статус:** драфт. Новый виджет для формирования выборки прецедентов из базы событий.

---

## Назначение

Аналитик хочет найти **группу похожих исторических событий**, чтобы дальше анализировать их вместе — посмотреть на CAR, объёмы, проверить, есть ли закономерность и насколько она стабильна. Если стабильна — основа для торговой стратегии.

В базе могут быть тысячи событий. Виджет «Поиск прецедентов» — это **способ выделить нужную подвыборку**, чтобы остальные виджеты не тонули в общей массе.

---

## Размещение

Плавающий виджет на канвасе, как все остальные. Не системный, не в тулбаре. Если аналитик не открыл — значит сейчас не нужен.

Привязка к логической группе наследуется от общего механизма виджетов проекта (`none`, `red`, `blue`, `green`, `yellow`).

---

## Два сценария использования

### С привязкой к группе

Виджет — **источник набора прецедентов** для всех виджетов этой группы. Что аналитик отметил галочками — то и видят остальные виджеты группы (event study, прогноз по прецедентам, robustness, маркеры на графике). Виджеты группы пересчитываются автоматически при изменении набора.

### Без группы (`none`)

Виджет работает как **исследовательский инструмент**. Аналитик ищет, накапливает галочки, может вернуться к набору в любой момент — но набор никуда не транслируется. Полезно для эксплорации базы, выбора кейсов, формирования будущей группы.

---

## Структура виджета

### Шапка

- **Дропдаун режима поиска** — варианты:
  - **Fuzzy** (по дефолту) — простой подстрочный поиск (см. «Что не делаем в MVP» — это `contains lowercase`, не «настоящий» fuzzy).
  - **PQL** — SQL-запрос на языке поиска прецедентов (см. «Разграничение PQL и виджета»).
  - **Семантика** — поиск по смыслу через эмбеддинги, top-K похожих к заданному тексту. В MVP **выключен**, см. «Что не делаем в MVP».
- **Поле запроса** — текст запроса. В семантическом режиме — inline-параметр `top K` (default 10).

### Список результатов

Колонки: **event** (описание события, единственное текстовое поле в `events`) и **теги**.

- Слева от каждой строки — **чекбокс** (отметка для включения в набор).
- Справа — **колонка «близость»** (числовое значение). Есть только в режимах fuzzy и семантика; в PQL колонки нет.
- Над списком — **переключатель «Найденные | Выбранные (N)»**, где N — счётчик выбранных. Переключает содержимое одного и того же списка между результатами текущего поиска и накопленным набором.

Теги в UI **дотягиваются виджетом самостоятельно** через `event_tags` / `tagged_events` по идентификатору события. В выдаче из режимов поиска тегов не должно быть — виджет берёт их из БД отдельно.

### Кнопка «Очистить набор»

Видна в режиме «Выбранные». Снимает все галочки одним кликом, очищает накопление.

## Разграничение PQL и виджета

**PQL (Precedent Query Language)** — это самостоятельный язык запросов, описанный в [SPEC_PRECEDENT_LANGUAGE.md](../SPEC_PRECEDENT_LANGUAGE.md). Существует независимо от виджета: те же таблицы (`events`, `tags`, `event_tags`, `tagged_events`), те же UDF (`car()`, `vol_ratio()`, …), тот же синтаксис.

**Поиск прецедентов** — это **виджет**, в котором PQL — один из трёх режимов ввода запроса (наряду с fuzzy и семантикой). Виджет не ограничивает сам язык, но накладывает **контракт на форму результата**.

### Контракт PQL-результата в виджете

PQL-запрос обязан вернуть **ровно две колонки**:
- `id` или `event_id` — идентификатор события (TEXT). Имя колонки зависит от того, из какой таблицы делается `SELECT`: из `events` — `id`, из `tagged_events`/`event_tags` — `event_id`.
- `event` — описание события (TEXT, единственное текстовое поле в таблице `events`).

Любое отклонение от контракта — лишние колонки, отсутствие обязательных, дубликаты `event_id` — считается **ошибкой контракта виджета**, сообщение выводится в плейсхолдер красным (по аналогии с синтаксической ошибкой PQL).

Сложные выражения внутри запроса допустимы — например, `car()`, JSON-доступ к `payload`, JOIN с `event_tags` — главное, чтобы итоговая выдача соответствовала контракту.

### PQL Editor vs «Поиск прецедентов»

| | PQL Editor (существующий) | Поиск прецедентов (новый) |
|---|---|---|
| Режимы ввода | только PQL | PQL + fuzzy + semantic |
| Контракт результата | произвольная таблица | строго `id`/`event_id` + `event` |
| Связь с группой | нет (автономный) | опциональная, передаёт набор в группу |
| Назначение | исследовательский редактор: сложные SELECT, агрегаты, разовые расчёты | формирование выборки прецедентов для дальнейшего анализа |

Существующий PQL Editor **остаётся** — это специализированный исследовательский инструмент. «Поиск прецедентов» не заменяет его, а дополняет.

## Поведение

### Накопление

- Галочки **накапливаются между запросами**. Сделал поиск «дивиденды LKOH», отметил 10. Сменил запрос на «дивиденды GAZP» — первые 10 не пропадают, к ним добавляются новые.
- Если событие из набора попало в результаты нового поиска — чекбокс отмечен **сразу**, аналитику не нужно ставить его повторно.

### Смена режима

- Найденные очищаются, поле запроса пустое, ожидается новый запрос.
- Выбранные сохраняются — набор не зависит от режима.

### Сортировка результатов

- **Fuzzy** — по релевантности (стандартный алгоритм fuzzy-поиска).
- **Семантика** — по убыванию близости.
- **PQL** — задаётся пользователем через `ORDER BY`/`LIMIT` в запросе.

### Жёсткий потолок результатов

При превышении выводится предупреждение (как в PQL-виджете). Аналитик должен уточнить запрос.

---

## Что не делаем в MVP

- **Семантический режим**. В MVP реализуем только два режима — PQL и fuzzy. Семантический поиск (эмбеддинги, top-K) — отдельная итерация, продумывается позже. В UI дропдаун режима пока показывает только PQL и fuzzy.
- **«Настоящий» fuzzy**. В MVP fuzzy реализуется через простой подстрочный поиск (`contains lowercase` по индексируемым полям). Алгоритмы с морфологией, опечатками, релевантностью — после стабилизации остальных частей виджета.
- **Сохранение запросов и наборов**. Для PQL уже есть избранные запросы — этого достаточно.
- **Кнопка «найти похожие» прямо в карточке события** — пока аналитик копирует текст в поле семантики вручную (когда семантика появится).
- **Сохранение «именованного набора»** (типа «дивидендные гэпы LKOH 2010-2020»).

## Виджеты-потребители набора прецедентов

| Виджет | Как использует |
|--------|----------------|
| **Event Study** (одиночный анализ) | Стрелочки ← → ходят по набору вместо комбобокса по всей БД. Тикер — от ведущего графика. |
| **Event Effect Analysis** | Главный потребитель. Анализирует индивидуальные CAR, строит forecast (профиль CAR(t)) и heatmap чувствительности. См. [SPEC_EVENT_EFFECT_ANALYSIS_DRAFT.md](SPEC_EVENT_EFFECT_ANALYSIS_DRAFT.md). |
| **Robustness Check** | Агрегирует CAR с перебором параметров на этом же наборе. |
| **Ценовой график с маркерами** | Маркеры событий — только из набора. |
| **Anomaly Detector** | Переосмыслен: «возьми набор прецедентов и подсвети, какие из них аномальные». |
| **Backtest** | Запуск стратегии по событиям из набора. Валидация прогноза на out-of-sample. |
| **Кросс-тикерный анализ** (будущее) | Набор × набор тикеров → heatmap CAR. |
| **Календарь / timeline** (будущее) | Визуализация набора во времени. |
| **Cluster explorer** (будущее) | Семантические под-группы внутри набора. |

## Открытые вопросы

Все базовые UX-вопросы закрыты. Открытые относятся к смежным виджетам:

- **Семантика веса прецедента** при агрегации в forecast и heatmap — линейный по близости, экспоненциальный, отсечка по порогу? Перенесено в [SPEC_EVENT_EFFECT_ANALYSIS_DRAFT.md](SPEC_EVENT_EFFECT_ANALYSIS_DRAFT.md).

- **Рефакторинг PQL и устранение `events-info` как костыля.** Сейчас фронт делает два запроса: сначала поиск (`/search` или `/search/fuzzy`) — он возвращает только `id + event`, потом отдельный `/events-info` — он добивает `date_start` и теги. Это естественно вытекло из контракта PQL виджета (ровно две колонки), но визуально и по архитектуре выглядит костылём — данные о событии «дробятся» между двумя ручками. Возможные пути:
  - Унифицировать ответ поиска — пусть `/search` сразу возвращает `date_start` и теги вместе с `id + event` (а контракт PQL виджета — расширить до 3+ колонок или сделать необязательным).
  - Альтернативно: оставить минимальный поиск, но включить `events-info` в виде view/функции Postgres, чтобы фронт делал один RPC. Хуже, потому что всё равно два логических запроса.
  - Подумать про сам контракт PQL виджета: «ровно две колонки» — оправдан ли он? Может быть `SELECT id, event, date_start, ...` от пользователя естественнее, и виджет сам решает что показать.
  Решается отдельно от основного функционала — текущая реализация работает, переезд — оптимизация архитектуры.

## Закрытые вопросы

- **Имя виджета** — «Поиск прецедентов» / «Precedent Search».
- **Размещение** — плавающий виджет на канвасе.
- **Привязка к группе обязательна?** — нет, виджет работает и без группы (как исследовательский инструмент).
- **Сосуществование с существующим `PQL Editor`** — старый виджет остаётся как более специализированный исследовательский инструмент. Новый «Поиск прецедентов» не заменяет его, а дополняет.
- **Три режима поиска** — fuzzy (default), PQL, семантика. Дропдаун в шапке.
- **Что индексировать для семантического сравнения** — колонка `event` (название) и теги события.
- **Где параметр top-K для семантики** — inline в поле запроса. Default 10. Нижнего предела нет, главное `K > 0`.
- **Колонки в UI-списке результатов** — `event` (описание) и теги. Колонка «близость» только в fuzzy и семантике. Теги в БД и в выдаче PQL не находятся напрямую — виджет дотягивает их сам через `event_tags`/`tagged_events`.
- **Разграничение PQL и виджета** — PQL это язык (отдельный концепт). «Поиск прецедентов» это виджет, использующий PQL как один из режимов ввода. Виджет не ограничивает язык, но накладывает контракт на форму результата.
- **Контракт PQL-результата в виджете** — ровно две колонки: `id` (или `event_id`) и `event`. Лишние или отсутствующие — ошибка контракта, выводится в плейсхолдер красным.
- **Чекбоксы** — для отметки события в набор. Состояние сохраняется между запросами и режимами.
- **Если событие уже в наборе и снова появилось** — чекбокс отмечен автоматически.
- **Просмотр накопленного набора** — переключатель «Найденные / Выбранные (N)» над списком, переиспользует то же место.
- **Колонка близости в режиме «Выбранные»** — нет, близость имеет смысл только в момент текущего поиска.
- **Кнопка «Очистить набор»** — есть, видна только в режиме «Выбранные».
- **Пересчёт виджетов группы** — автоматически после изменения набора.
- **Сценарий смены режима** — найденные очищаются, выбранные сохраняются.
- **Лимит результатов** — жёсткий потолок (как в PQL), при превышении — предупреждение.
- **Пустой результат** — плейсхолдер «ничего не найдено».
- **Ошибка PQL** (синтаксис, лимит, недоступная функция) — выводится в плейсхолдер красным цветом, как в существующем PQL-виджете.
- **Сохранение запросов/наборов в MVP** — не делаем. Для PQL остаются избранные запросы.
- **Источник целевого события для семантики** — свободный текст. Кнопка «найти похожие» в карточке события — после MVP.

## Не входит в этот документ

- Алгоритм семантического сравнения (модель эмбеддингов, метрика близости, индексация в БД) — реализационная деталь.
- Алгоритм fuzzy-поиска — стандартный, реализационная деталь.
- Event Effect Analysis (включая forecast как одно из представлений) — отдельная спецификация ([SPEC_EVENT_EFFECT_ANALYSIS_DRAFT.md](SPEC_EVENT_EFFECT_ANALYSIS_DRAFT.md)).
- Автоматическая разметка событий тегами через NER — отдельная спецификация.
