# Спецификация: автономный исследовательский агент (Research Agent)

> Этот документ описывает **что** делает автономный исследовательский агент и **зачем** — на языке [глоссария](../GLOSSARY.md). Реализационные детали (модель LLM, библиотеки, имена эндпоинтов, схемы данных) — в коде. Цель спеки — оставаться валидной при любом рефакторинге.

> **Статус:** черновик второй итерации. Часть основания уже реализована — см. [`SPEC_ASSISTANT.md`](../SPEC_ASSISTANT.md) (помощник). Открытые вопросы, которые требуют решения до реализации, перечислены в разделе 12.

---

## 1. Назначение

Аналитик формулирует исследовательскую гипотезу на естественном языке («покупать ЛУКОЙЛ на дивидендном гэпе», «когда повышение ключевой ставки — покупать золото»). **Автономный исследовательский агент** разворачивает гипотезу в последовательность шагов событийного анализа и бэктеста, выполняет их без участия человека и возвращает аналитический отчёт.

Цель — сократить путь от идеи до проверки с часов ручной работы до минут, оставив человеку **постановку вопроса** и **интерпретацию результата**, а не механический pipeline.

---

## 2. Отличие от помощника

В проекте уже реализован **помощник** (см. [`SPEC_ASSISTANT.md`](../SPEC_ASSISTANT.md)) — реактивный чат-партнёр, выполняющий **по одному действию за реплику пользователя**. Между помощником и автономным агентом — принципиальная разница в **инициативе** и **горизонте планирования**.

| Параметр | Помощник | Автономный агент |
|---|---|---|
| Инициатива | Реактивен. Ждёт реплику пользователя. | Активен. Ведёт цепочку шагов сам. |
| Цель | Не имеет собственной цели — выполняет частный запрос. | Принимает гипотезу и доводит её до отчёта. |
| Длительность сессии | Реплика — ответ. Секунды. | Минуты — часы (по разным гипотезам). |
| Решения | Пользователь решает после каждого ответа. | Агент сам принимает промежуточные решения по заранее заданным правилам. |
| Состояние | Эфемерно: история живёт в браузере. | Должно сохраняться: цепочка рассуждений принадлежит исследованию. |
| Артефакты | Меняет сущности по запросу пользователя. | Создаёт правила, стратегии, прогоны и финальный отчёт самостоятельно. |

Автономный агент **не заменяет** помощника. Помощник остаётся инструментом точечной работы и ручной верификации того, что сделал автономный.

---

## 3. Архитектурная идея

Гипотеза аналитика — это пара «условие на рынке → ожидаемая реакция цены». Например, «после анонса дивидендов ЛУКОЙЛа на ≥X% — цена растёт ещё на Y% в течение N дней».

Автономный агент превращает её в **исследовательский план** — последовательность фаз:

1. **Декомпозиция гипотезы.** Из свободной формулировки извлекаются: исследуемые тикеры, тип событий-триггеров, направление реакции, временной горизонт, метрика оценки.
2. **Подтверждение прецедентов.** Через язык поиска прецедентов формируется запрос, отбирающий из истории все случаи, удовлетворяющие условию. Если случаев меньше порога — гипотеза отклоняется как невоспроизводимая на исторических данных.
3. **Анализ эффекта событий.** На отобранном наборе считается агрегированный CAR с доверительным интервалом, сравнивается с нормой движения, выполняется анализ чувствительности (см. глоссарий).
4. **Бэктест.** Если эффект статистически значим — формулируется торговое правило, строится стратегия, выполняется прогон на длинной истории.
5. **Отчёт.** Финальный аналитический документ: гипотеза, методология, результаты каждой фазы, выводы.

Между фазами действуют **точки решения** (см. §6). Не каждая гипотеза доходит до бэктеста — агент может остановиться на любой фазе, если данные не поддерживают гипотезу.

---

## 4. Что использует от существующей реализации

Автономный агент **повторно использует** инфраструктуру помощника:

- Тот же runtime (Claude Code CLI в headless-режиме), тот же whitelist инструментов (Read под `docs/**`, Bash на локальный REST-API проекта).
- Тот же доступ к REST-API всех артефактов исследования.
- Тот же стриминг событий в UI.

Это означает, что **граница доступа агента та же, что у помощника**: он действует только через документированные REST-эндпоинты, не правит код, не выходит во внешний интернет, не выполняет произвольных bash-команд. Принцип «аналитический уровень доступа» из [`SPEC_ASSISTANT.md`](../SPEC_ASSISTANT.md) сохраняется.

Что добавляется поверх:

- Принципиально другой системный промпт — описывающий цикл фаз, а не реактивный диалог.
- Механизм журналирования цепочки рассуждений (см. §7).
- Бюджет на исполнение (см. §8).
- Декомпозиция гипотезы (см. §5).
- Скептический разбор результата (см. §9).

---

## 5. Декомпозиция гипотезы

Естественноязыковая формулировка — самое непрозрачное место. Гипотеза «купи Сбербанк после повышения ставки» допускает несколько прочтений: купи на дату решения или на следующий день, держи день или месяц, при любом повышении или только при шаге ≥X базисных пунктов.

Агент **первым шагом фиксирует разложение** гипотезы в структурированную форму и **показывает её пользователю до начала работы**:

| Поле | Значение в этой гипотезе |
|---|---|
| Тип события | Решение по ключевой ставке (`KeyRateDecision`) |
| Фильтр на событии | Повышение, шаг ≥X базисных пунктов |
| Исследуемые тикеры | SBER, SBERP |
| Направление реакции | Падение цены |
| Окно анализа | t=0..t+N торговых дней |
| Метрика | CAR с доверительным интервалом |
| Сравнение | С нормой движения тех же тикеров |

Если разложение содержит **неопределённые поля** (например, не указан горизонт N), агент подставляет **разумный дефолт** из методологии проекта и явно помечает его как принятое им допущение. Аналитик может вмешаться и поменять — либо до запуска, либо в виде корректирующей реплики во время работы (см. §6).

Этот шаг — **главная защита от неверной интерпретации**: лучше остановиться и согласовать понимание, чем потратить минуты на бэктест не той гипотезы.

## 6. Граница автономности

Агент принимает решения сам в пределах **заранее перечисленных правил**. Любое решение вне этого списка — повод остановиться и спросить пользователя.

### 6.1. Решает сам

- Выбор разумных дефолтов в декомпозиции (горизонт, окно, модель ожидаемой доходности — берёт `MarketModel` или `CAPM`, как указано в требованиях диплома).
- Создание приватных правил/стратегий/окружений для текущей задачи.
- Удаление собственных smoke-прогонов после завершения (как в `BACKTEST_RUNNER_AGENT.md`).
- Чтение документов из `docs/` для уточнения терминов.
- Прекращение работы при ошибке инструмента — с сохранением журнала.

### 6.2. Останавливается и спрашивает

- Размер выборки прецедентов **меньше порога** — например, найдено 3 случая. Продолжать с малой статистикой или искать смягчение фильтра?
- Данные **не покрывают окружение** — короче нужного периода. Догрузить, обрезать, или прервать?
- Эффект **на границе значимости** — не уверен, считать гипотезу подтверждённой или нет.
- Удаление чего-либо, **не созданного агентом** в этой сессии (например, чужого правила) — никогда не делает молча.
- Любая операция, в которой пользователь явно потребовал подтверждение в реплике («перед каждым прогоном спрашивай»).

### 6.3. Не делает никогда

- Не правит код, файлы вне `docs/`, схему БД, миграции (повторяет ограничения помощника).
- Не отвечает на вопросы вне проекта.
- Не создаёт правил/стратегий/окружений в **чужих** исследованиях — только в активном.
- Не выполняет bash-команды вне `curl http://127.0.0.1:8080/api/*`.

## 7. Журнал рассуждений

Помощник эфемерен по дизайну: история чата живёт в браузере. Это допустимо для интерактивной работы, но **категорически не подходит** для автономного агента: цепочка рассуждений — это часть результата исследования и должна быть воспроизводимой.

Автономный агент пишет **журнал прогона** — хронологический поток с каждой фазой:

- Декомпозиция гипотезы (см. §5) и принятые дефолты.
- Каждый запрос на язык поиска прецедентов и его результат.
- Конфигурация анализа эффекта событий (окна, модель, фильтрация выбросов) и итоговые метрики.
- Сформированное торговое правило и стратегия с их id.
- Результаты прогона: метрики, ссылки на сохранённые артефакты.
- Все точки решения и аргумент, по которому агент пошёл по одной ветке.
- Все остановки и заданные пользователю вопросы с его ответами.

Журнал **принадлежит исследованию** — сохраняется на сервере и связан с активным `Research`. Аналитик может вернуться к нему через виджет помощника или отдельный журнал агента (UI определяется в реализации).

---

## 8. Бюджет

Каждый шаг агента — это вызов LLM и работа с данными. Без явного бюджета один запуск может выйти неконтролируемо дорогим (по токенам) и долгим. Поэтому каждый прогон агента ограничен:

- **По времени** — твёрдый таймаут на весь прогон. По истечению — мягкая остановка с сохранением журнала.
- **По числу шагов** — счётчик действий (вызовов инструментов). Защита от зацикливания.
- **По стоимости** — суммарные токены LLM. Дублирует ограничение по числу шагов на случай, если отдельные шаги аномально дороги.

Лимиты задаются по умолчанию (читаются из конфигурации проекта) и могут быть переопределены при запуске («дай больше бюджета на эту гипотезу»). Сейчас в спецификации не фиксируются конкретные цифры — это решается в реализации с учётом стоимости тарифа и типичной длительности задач.

---

## 9. Защита от ошибочных выводов

LLM может пройти весь pipeline, но прийти к выводу, который не следует из данных. Чтобы это не утекло в отчёт, агент применяет **три уровня защиты**:

1. **Декомпозиция гипотезы с явными допущениями.** Аналитик видит и принимает декомпозицию до запуска (см. §5).
2. **Цитирование источника каждого числа.** В отчёте каждая метрика — со ссылкой на конкретный артефакт (`backtestResultId`, `eventEffectAnalysisRunId`), а каждое утверждение — со ссылкой на документ или конкретное наблюдение. Утверждение без ссылки на источник — баг отчёта.
3. **Скептический разбор.** Перед финализацией отчёта агент сам себе задаёт вопросы из заранее заданного списка:
   - Достаточен ли размер выборки прецедентов?
   - Не попали ли в выборку перекрывающиеся события (см. глоссарий)?
   - Стабилен ли эффект при разумных вариациях параметров (анализ чувствительности)?
   - Воспроизводится ли он в субпериодах истории?
   - Не объясняется ли эффект тривиальным фактором (например, общим трендом рынка)?

   На каждый вопрос даётся явный ответ; ответы попадают в отчёт.

Это не гарантирует отсутствия ошибок, но делает их **видимыми при чтении отчёта** — а значит, опровергаемыми человеком.

---

## 10. Связь с моделью данных

Агент пишет в те же таблицы, что и аналитик через UI: `rules`, `strategies`, `environments`, `backtest_results`, `trade_journal` (см. [SPEC_DATABASE.md](../SPEC_DATABASE.md)). Это даёт два важных эффекта:

- Артефакты, созданные агентом, **неотличимы по статусу** от созданных вручную. Их видно в виджетах редакторов, по ним можно открыть карточку прогона, их можно использовать как baseline для следующих гипотез.
- Никакой отдельной «теневой» модели данных не появляется. Это сознательное упрощение, удобное для дипломной работы: один источник правды.

Что **появится новое** в модели данных — это сущности самого автономного прогона: журнал агента (см. §7) и финальный отчёт. Это будут отдельные таблицы, в спецификации они называются концептуально и не фиксируются в конкретных полях.

---

## 11. Что является собственной разработкой автора

Важная развилка для научного руководителя: что в этой части проекта — **собственная работа автора диплома**, а что — **интеграция готового LLM**.

**Собственная разработка:**

- Методологическое ядро event study, бэктеста, языка поиска прецедентов и анализа аномалий — реализовано в Python, описано в спецификациях, лежит в репозитории. Эти куски **не зависят от LLM** и работают без него (см. ноутбуки, виджеты, API).
- Декомпозиция гипотезы в структурированные параметры цикла исследования — собственный мостик между естественным языком и доменной моделью проекта.
- Контракт автономного агента: фазы, точки решения, журнал рассуждений, скептический разбор, формат отчёта — формализованы в этой спеке.
- Whitelist инструментов и граница доступа — собственные. LLM не имеет произвольного контроля над системой.

**Интеграция готового LLM:**

- Сам LLM — внешняя зависимость (Claude Code CLI), используется через документированный интерфейс.
- Перевод естественного языка в структурированные параметры — выполняется LLM, но **по жёсткому контракту**, который описан в этой спеке и проверяется в реализации.

То есть LLM — это **исполнитель оркестрации**, а не **источник методологии**. Методология остаётся в проекте; LLM приклеен поверх как удобный интерфейс к ней.

## 12. Открытые вопросы

Вопросы, которые предстоит решить до начала реализации. Каждый — потенциальный источник несовместимости с уже существующими виджетами или с дипломной частью.

1. **UI запуска агента.** Через тот же виджет помощника со специальным режимом или отдельный виджет «Запуск исследования»?
2. **Сохранение журнала рассуждений.** В таблице с привязкой к `Research` или в файловом артефакте? Это влияет на схему БД.
3. **Отчёт как сущность.** Является ли отчёт отдельной сущностью со своим жизненным циклом (можно править вручную) или иммутабельным результатом прогона агента?
4. **Возобновление прерванного прогона.** Поддерживать ли «продолжить отсюда» после остановки на точке решения или каждый запуск стартует с нуля?
5. **Параллельные прогоны.** Сколько прогонов агента одновременно в одном исследовании — один, ограниченное число, без ограничений?
6. **Формат и состав отчёта.** Какие разделы обязательны, как организовано цитирование артефактов, в каких форматах экспорт.
7. **Дефолты декомпозиции гипотезы.** Какой набор разумных значений по умолчанию (окна, модели, метрики) фиксируется как «методология проекта»?
8. **Скептические вопросы.** Точный список вопросов скептического разбора — должен покрывать характерные ошибки, типичные для российского рынка и используемых данных.
9. **Граница автономности — пограничные случаи.** Уточнение правил из §6 на типичных ситуациях: что считать «значимым» эффектом, при каких показателях продолжать.
10. **Конкретные значения бюджета.** Цифры по времени, шагам, токенам — на основе фактических замеров после первых прогонов.

---

## 13. Что не входит в этот документ

- **Конкретный формат skill** (системного промпта, описания инструментов) — фиксируется при реализации.
- **Выбор тарифа и модели LLM** — реализационная деталь; ограничение «должна поддерживать tool use и стрим» уже выполнено в текущем выборе (Claude Code CLI).
- **Документация по skill для пользователя** — пишется отдельно, после стабилизации спецификации.
- **Защита от использования агента не по назначению** (например, для прокачки личного исследования вне диплома) — приложение однопользовательское, такого риска нет.
- **Многоагентные конфигурации** (несколько LLM-агентов работают параллельно над разными подгипотезами) — выходит за рамки первой итерации.

## Приложение A. Справочник REST-эндпоинтов агента

Через эти эндпоинты агент взаимодействует с проектом. Whitelist Bash-инструмента ограничен `curl http://127.0.0.1:8080/api/*`, других путей агент не вызывает.

**Источник правды — Swagger UI:** <http://127.0.0.1:8080/docs>. Машиночитаемая схема — <http://127.0.0.1:8080/openapi.json>. Таблицы ниже — конспект для понимания «что вообще есть»; при сомнениях в форме запроса агент сверяется со Swagger.

### A.1. Исследования

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/research` | Список всех исследований |
| `POST` | `/api/research` | Создать исследование (имя обязательно, описание опционально) |
| `GET` | `/api/research/{research_id}` | Карточка исследования |
| `PATCH` | `/api/research/{research_id}` | Обновить имя / описание идеи / выводы |
| `DELETE` | `/api/research/{research_id}` | Удалить исследование вместе со всеми приватными артефактами |

## Приложение B. Известные грабли при работе через curl

### B.1. Кириллица в JSON-аргументах curl на Windows

**Симптом:** `curl -d '{"name":"Стратегия Икс"}'` идёт через git-bash на Windows и приходит на backend с битой кодировкой; сервер возвращает `400 There was an error parsing the body`.

**Причина:** аргумент `-d '...'` парсит cmd.exe, перекодируя из UTF-8 в cp1251. Сервер ожидает UTF-8 — JSON не разбирается.

**Решение для агента:**

- **Имена артефактов** (правил, стратегий, окружений) при создании через curl формулируй на латинице. Например: `Rebalance_exit_all_positions`, а не `Ребаланс: выход из всех позиций`.
- **Описания** (`description`) для артефактов, создаваемых через curl, тоже лучше делать на ASCII. Если в описании нужна кириллица — попроси пользователя добавить через UI.
- В существующих артефактах, созданных через UI с кириллицей, всё в порядке — там Vite/React шлёт корректный UTF-8.

### B.2. Парсинг JSON-ответов

`curl` отдаёт чистый JSON в stdout. Не пытайся пропускать через `python -c`, `jq` или другие утилиты — это:

- запрещено whitelist'ом и приведёт к permission denied;
- не нужно: ты разбираешь JSON «в голове» без потери качества.

Если нужно дёрнуть несколько ручек — это несколько отдельных вызовов `curl`, по одному на вызов Bash.
