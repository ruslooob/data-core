# Бэктест стратегий — черновик глоссария и устройства

> Сессия с пользователем (ноябрь 2026). Только концептуальная модель — без кода и спецификации API. Используется как стартовая точка следующей сессии: на её основе будет написана `docs/SPEC_BACKTEST.md` и план реализации.

---

## Уровень 1 — что такое бэктест

Бэктест — это **симуляция**: берём стратегию пользователя и историю цен, прокручиваем её через прошлое день за днём (как будто торговля шла прямо тогда), в конце смотрим, что получилось.

**Вход:**
- стратегия (что делать)
- период (с какой по какую дату)
- стартовый капитал

**Выход:**
- журнал всех сделок (TradeJournal)
- метрики (Performance) — финальный капитал, прибыль, риски
- кривая капитала (EquityCurve) — как менялся баланс во времени

---

## Уровень 2 — главный цикл

Симуляция — это **главный цикл по времени**:

```
для каждого тика (= торгового дня) в периоде:
    1) дать стратегии видеть рынок (даты, цены, объёмы, состояние портфеля)
    2) спросить стратегию: «что делаем?» — получить список кандидатов
    3) исполнить кандидатов (с проверкой бюджета)
    4) зафиксировать текущий капитал в EquityCurve
```

**Тик** = единица времени симуляции. Сейчас 1 тик = 1 торговый день; в будущем может быть час/минута. Между тиками стратегия «спит». Стратегия видит состояние «на конец дня», действия исполняются по цене закрытия этого же дня — стандартное упрощение.

В конце периода — финальный отчёт.

## Уровень 3 — стратегия как набор правил

**Стратегия (Strategy)** — набор правил.

**Правило (Rule)** — независимая единица. Состоит из **двух разных частей**, которые нельзя смешивать:

### 3a. Триггер (Trigger)
**PQL-запрос**, который на каждом тике возвращает **список тикеров, для которых правило сегодня сработало**. Только поиск, без «сколько» и «что делать».

Форма: `SELECT ticker FROM ... WHERE ...` с подстановкой текущей даты как параметра.

Примеры:
```sql
-- триггер «всплеск объёма у любой компании»
SELECT t.code AS ticker
FROM tags t
WHERE t.type = 'company'
  AND volume_ratio(t.code, :tick) > 1.5

-- триггер «дивиденды LKOH сегодня»
SELECT 'LKOH' AS ticker
WHERE EXISTS (
  SELECT 1 FROM tagged_events te
  WHERE te.tag = 'DIVIDEND_ANNOUNCEMENT'
    AND te.date_start = :tick
    AND te.event_id IN (SELECT event_id FROM tagged_events WHERE tag = 'LKOH')
)
```

### 3b. Действие (Action)
**Отдельная конфигурация** правила, не часть запроса. Включает:
- **тип операции** — `buy` / `sell` (или нейтральнее: `open_long` / `close_long` / `open_short` / `close_short` если будем поддерживать шорты)
- **объём** — три формы:
  - `N` акций (фиксировано)
  - на сумму `K` рублей
  - `P` процентов от свободного кэша / от всей equity
- **приоритет** — число для сортировки кандидатов на одном тике
- **имя** — для отчётности

### Главное про разделение

Триггер ищет «когда и для кого». Действие описывает «что и сколько». Они независимы — это два разных вопроса. Один и тот же триггер можно подцепить к разным действиям (одинаковый паттерн, разные тактики выхода), и наоборот.

### Симметрия правил

И правило-покупка, и правило-продажа устроены одинаково. Стоп-лосс — это просто правило-продажа с триггером «текущая цена < цена входа − 3%». Никакой специальной сущности «exit-rule» — все правила симметричны.

## Уровень 4 — как именно работает один тик

```
для каждого тика:
    кандидаты = []

    для каждого rule в стратегии:
        список_тикеров = выполнить rule.trigger с подстановкой tick.date
        для t в список_тикеров:
            кандидаты += сформировать_кандидата(rule.action, ticker=t)

    отсортировать кандидатов по убыванию приоритета

    для каждого кандидата по порядку:
        если хватает денег / есть позиция (для продажи):
            исполнить (записать сделку в TradeJournal, обновить кэш и позиции)
        иначе:
            пропустить

    зафиксировать equity в EquityCurve
```

**Кандидат (Candidate)** — желание правила на действие, ещё не исполненное. Имеет: тикер, тип операции, объём, приоритет, ссылку на правило.

**Сделка (Trade)** — фактически исполненная операция. Не «пара open+close», а одно действие. Пары для отчётности группируются постфактум по тикеру/времени.

**Бюджетная проверка** — на этапе исполнения:
- покупка: хватает ли cash на (количество × цена закрытия + комиссия)
- продажа: есть ли в портфеле столько акций
Если не проходит — кандидат пропускается без ошибки.

## Уровень 5 — что доступно триггеру

В PQL-запросе триггера, помимо обычной видимой схемы (`events`, `tags`, `event_tags`, `tagged_events`, UDF: `car`, `volume_ratio`, `vol_ratio`, `pre_event_car`), доступны **новые контекстные сущности**:

- `:tick` — текущая дата как параметр запроса.
- **Состояние портфеля** — нужно для триггеров вида «продать если цена упала на 3% от входа». Конкретная форма обсудим в реализации (зарегистрированные временные таблицы / параметры функций / UDF). Логически это:
  - `portfolio.cash` — свободный кэш на тике
  - `portfolio.position(ticker)` — открытая позиция: `quantity`, `avg_price` (средняя цена входа), `days_held`, `null` если позиции нет
  - `portfolio.equity` — общая стоимость портфеля = cash + sum(position × current_price)

Это обсуждаемые имена — финализируем при реализации.

## Открытые вопросы (не закрыты в этой сессии)

Эти вопросы намеренно оставлены на следующую сессию — обсуждаются после того, как пользователь прочитает черновик с свежей головой.

1. **Объём (`Action.size`)** — финальный список форм: фиксированное N / сумма K / процент от cash / процент от equity. Все четыре или подмножество?
2. **Шорты** — в MVP только лонги? Или сразу `open_long` / `open_short` / `close_long` / `close_short`?
3. **Комиссии** — фиксированный процент от сделки в настройках бэктеста? Игнорируем в MVP?
4. **Слиппедж** (отклонение фактической цены исполнения от закрытия) — игнорируем в MVP?
5. **Plurality правил** — количество правил в стратегии может быть произвольным? Лимит?
6. **Хранение стратегий** — отдельная таблица `strategies` в БД (по аналогии с `precedent_queries`)? Имена уникальны? Системные пресет-стратегии?
7. **Universe тикеров** — нужен ли как отдельная сущность Strategy.universe, или каждый триггер сам определяет свою область через WHERE?
8. **Приоритеты** — целое число / float / enum «high/normal/low»? Что делает движок при равных приоритетах (стабильная сортировка по имени правила?)?
9. **Состояние портфеля в SQL** — техника интеграции (временные таблицы / UDF / переменные). Чисто реализационный вопрос.
10. **Связь с PQL-редактором** — может ли пользователь скопировать триггер прямо из сохранённого прецедентного запроса? Как описать «сделать правило из этого запроса»?
11. **UI** — отдельный виджет «Strategy editor» (по аналогии с PrecedentEditor), или встраивается в PrecedentEditor через спецсинтаксис? Скорее отдельный виджет с двумя редакторами (триггер + действие) и таблицей правил.
12. **Запуск бэктеста** — как пользователь указывает период / стартовый капитал / комиссии? Отдельный диалог при запуске?
13. **Сохранение результатов** — `BacktestResult` хранится в БД для последующего сравнения? Отдельная таблица `backtest_runs`?
14. **Сравнение стратегий** — две EquityCurve рядом, две таблицы Performance — нужна отдельная UI-фича?
