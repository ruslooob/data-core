# Бэктест стратегий — черновик глоссария и устройства

> Сессии с пользователем (ноябрь 2026 + 28 апреля 2026 — структурная переработка). Только концептуальная модель — без кода и спецификации API. Используется как стартовая точка следующей сессии: на её основе будет написана `docs/SPEC_BACKTEST.md` и план реализации.

## Часть 1 — Концепция

### 1.1. Что такое бэктест

Бэктест — это **симуляция**: берём стратегию пользователя и историю цен, прокручиваем её через прошлое торговый день за днём, в конце смотрим, что получилось.

**Вход:**
- `Strategy` — что делать (набор правил)
- `Environment` — окружение прогона: стартовый капитал + период (`date_start`, `date_end`)

Одну и ту же `Strategy` можно прогонять в разных `Environment`. Это позволяет проверять стратегию на разных периодах и при разных стартовых капиталах, не дублируя сами правила.

**Выход — `BacktestResult`:**
- набор метрик прогона (финальный капитал, прибыль, риски — состав финализируется отдельно)
- `TradeJournal` — полный журнал сделок прогона
- `EquityCurve` — представление поверх `TradeJournal` + `Environment.starting_capital` + рыночных данных, вычисляется при отображении (не хранится отдельным полем)

### 1.2. Главный цикл

```
для каждого тика (= торгового дня) в периоде:
    1) дать стратегии увидеть рынок и состояние портфеля
    2) спросить стратегию: «что делаем?» — получить список кандидатов
    3) исполнить кандидатов (частично, если не хватает кэша или позиции)
    4) обновить состояние портфеля на конец тика (cash, equity, лоты)
```

В конце периода — финальный отчёт. Подробности шагов — в Части 3.

### 1.3. Сущности и их роли

| Сущность | Что это                                                                                                                                                                                                                                                               |
|---|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Strategy` | Набор правил. Не зависит от параметров прогона.                                                                                                                                                                                                                       |
| `Environment` (`Env`) | Окружение прогона: `Strategy` + стартовый капитал + период (`date_start`, `date_end`). Одну и ту же `Strategy` можно тестировать в разных `Environment`.                                                                                                              |
| `Rule` | Одно правило. Состоит из `name` + `trigger` + `action` + `priority`. Имя живёт у правила, не у его частей. Анатомия — Часть 2.                                                                                                                                       |
| `Trigger` | PQL-запрос «кого сегодня затронуть» — возвращает список тикеров.                                                                                                                                                                                                      |
| `Action` | Конфигурация «что и сколько делать с тикером»: `type`, `quantity` (PQL-запрос).                                                                                                                                                                                      |
| `Candidate` | Кандидат на исполнение на текущем тике. Кортеж `(ticker, type, quantity, priority, rule_name)`.                                                                                                                                                                       |
| `Trade` | Исполненная операция, порождённая срабатыванием правила: одна покупка либо одна продажа, фиксируется одной строкой в `trade_journal`.                                                                                                                                 |
| `Tick` | Один торговый день в MVP (в будущем — час/минута).                                                                                                                                                                                                                    |
| `Portfolio` | Состояние счёта на тике: cash, открытые позиции, equity.                                                                                                                                                                                                              |
| `TradeJournal` | Журнал всех исполненных сделок прогона. SQL-таблица — `trade_journal`.                                                                                                                                                                                                |
| `EquityCurve` | Показывает баланс портфеля с течением времени по мере исполнения стратегии. Точки `(date, equity)` от старта до текущего тика. **Не хранится** — вычисляется по запросу из `TradeJournal` + `Environment.starting_capital` + рыночных данных.                         |
| `BacktestResult` | Результат прогона: набор метрик (см. 1.4) + `TradeJournal`. `EquityCurve` доступен как представление поверх `TradeJournal`. Метрики **сохраняются** в момент завершения прогона — `TradeJournal` неизменяем, повторный пересчёт даст те же значения. |

### 1.4. Метрики `BacktestResult` для MVP

Минимальный набор; в будущем расширяется. Все метрики вычисляются один раз по завершении прогона и сохраняются в `BacktestResult`.

| Метрика | Что показывает | Источник |
|---|---|---|
| Суммарная доходность, % | (final_capital − starting_capital) / starting_capital | journal + market |
| Годовая доходность, % | суммарная доходность, нормированная на длину прогона | journal + market + dates |
| Максимальная просадка, % | худшее падение эквити от пика к дну за прогон | производное от `EquityCurve` |
| Sharpe | годовая доходность ÷ годовая волатильность доходности эквити | производное от `EquityCurve` |
| Количество сделок | число строк в `trade_journal` | journal |
| Profit factor | Σ прибылей ÷ Σ убытков по `pnl_realized` | journal |
| Доля прибыльных сделок, % | count(`pnl_realized > 0`) ÷ count(всех `sell`) | journal |

Состав расширяется в будущем при необходимости. Способ хранения метрик в БД — открытый вопрос 21 (целостная модель персистентности).

## Часть 2 — Анатомия правила

`Rule` состоит из четырёх полей:

- **`name`** — имя правила (для отчётности и идентификации в `trade_journal`)
- **`trigger`** — PQL-запрос «кого затронуть» (см. 2.1)
- **`action`** — конфигурация «что и сколько» (см. 2.2)
- **`priority`** — целое число (`int`) для сортировки кандидатов на одном тике (см. 2.3)

### 2.1. Trigger — поиск «кого затронуть»

PQL-запрос вида `SELECT ticker FROM ... WHERE ...`. Возвращает список тикеров, для которых правило сегодня сработало. Только поиск — никаких «сколько» и «что делать».

Видит контекст из Части 5. Подчиняется принципу no-lookahead из Части 4.

Пример (всплеск объёма):
```sql
SELECT t.code AS ticker
FROM tags t
WHERE t.type = 'company'
  AND volume(t.code, :tick - 1) / volume_sma(t.code, :tick, 20) > 1.5
```

Пример (дивиденды LKOH объявлены вчера):
```sql
SELECT 'LKOH' AS ticker
WHERE EXISTS (
  SELECT 1 FROM tagged_events te
  WHERE te.tag = 'DIVIDEND_ANNOUNCEMENT'
    AND te.date_start = :tick - 1
    AND te.event_id IN (SELECT event_id FROM tagged_events WHERE tag = 'LKOH')
)
```

### 2.2. Action — тип действия и кол-во акций

Конфигурация из двух полей:

- **`type`** — `buy` или `sell` (в MVP — только лонги)
- **`quantity`** — отдельный PQL-запрос, возвращающий **одну ячейку** — целое число акций для подставленного `:ticker`. Везде в коде и таблицах БД пишется полное слово `quantity`, не `qty`.

#### Как работает `quantity`

После того как trigger вернул список тикеров, для каждого из них движок выполняет **второй PQL-запрос** — `Action.quantity` — подставляя `:ticker`. Запрос возвращает одну ячейку (число акций).

```
trigger:    SELECT ticker FROM ...                            →  ['LKOH', 'GAZP']

для LKOH:   action.quantity, :ticker = 'LKOH'
            SELECT FLOOR(s.cash * 0.10
                       / close_price(:ticker, :tick - 1))
            FROM portfolio_state s
                                                              →  8

→ кандидат {ticker='LKOH', type='buy', quantity=8, priority=100}
```

То же повторяется для `GAZP` и для всех остальных тикеров **этого правила**. Затем движок переходит к следующему правилу стратегии. Общий список кандидатов идёт в Часть 3 (исполнение).

#### Контракт `quantity`-запроса

- ровно 1 строка × 1 колонка
- возвращает целое число ≥ 0
- доступен параметр `:ticker` — пришёл из триггера
- видит **тот же контекст**, что триггер (Часть 5)
- подчиняется тому же no-lookahead (Часть 4)
- если запрос вернул `0`, `NULL` или упал с ошибкой — кандидат пропускается, бэктест не падает

#### Примеры

Все три формы из старой схемы (`N акций` / `на сумму K` / `% от cash или equity`) — частные случаи одного механизма:

```sql
-- "Купить 100 акций"
SELECT 100

-- "Купить на 50 000 рублей"
SELECT FLOOR(50000 / close_price(:ticker, :tick - 1))

-- "10% от свободного кэша"
SELECT FLOOR(s.cash * 0.10
           / close_price(:ticker, :tick - 1))
FROM portfolio_state s

-- "5% от equity"
SELECT FLOOR(s.equity * 0.05
           / close_price(:ticker, :tick - 1))
FROM portfolio_state s

-- "Продать всю позицию" (стоп-лосс) — по всем лотам тикера
SELECT SUM(quantity) FROM portfolio_positions WHERE ticker = :ticker

-- "Продать половину" (частичный выход)
SELECT FLOOR(SUM(quantity) / 2) FROM portfolio_positions WHERE ticker = :ticker

-- "Позиция, нормированная на волатильность" (Kelly-style)
SELECT FLOOR(s.cash * 0.02
           / close_price(:ticker, :tick - 1)
           / volatility(:ticker, :tick, 20))
FROM portfolio_state s
```

#### Что это даёт

Один язык (PQL) и для триггера, и для расчёта количества. Никаких enum-режимов в движке. Любую новую форму объёма пользователь выражает формулой. Quantity-запрос отлаживается прямо в PQL-редакторе с подставленным `:ticker`.

#### Сахар (не блокирует MVP)

Самый частый случай — `SELECT 100`. UI редактора Action может принимать литерал и автоматически оборачивать его в `SELECT <число>`. Это удобство, не отдельная сущность.

### 2.3. Priority — порядок исполнения

`Rule.priority` — целое число, задающее порядок применения кандидатов одного тика. Чем выше значение, тем раньше кандидаты от этого правила попадают на исполнение. При равном `priority` порядок определяется позицией правила в списке `Strategy.rules` (см. Часть 3.2).

Это координационное свойство правила среди соседей по стратегии: `trigger` и `action` оперируют одним тикером и не знают о других правилах, а `priority` определяет, кто первым тратит общий кэш и существующие позиции.

### 2.4. Стоп-лосс как обычное sell-правило

Триггер ищет «когда и для кого». Action описывает «что и сколько». Один и тот же триггер можно подцепить к разным Action, и наоборот. Стоп-лосс — это просто правило с `Action.type = sell` и триггером по цене позиции; никакой специальной сущности «exit-rule» нет.

## Часть 3 — Один тик

### 3.1. Шаги движка

```
для каждого тика:
    кандидаты = []

    для каждого rule в стратегии:
        список_тикеров = выполнить rule.trigger (:tick = today)
        для t в список_тикеров:
            qty = выполнить rule.action.quantity (с :ticker = t, :tick = today)
            кандидаты += {ticker=t, type=rule.action.type,
                          quantity=qty, priority=rule.priority,
                          rule_name=rule.name}

    отсортировать кандидатов по убыванию priority
        (при равном priority — по порядку правил в Strategy)

    для каждого кандидата по порядку:
        фактическое_кол-во = cash / цена открытия (см. 3.2)
        если фактическое_кол-во > 0:
            записать сделку в trade_journal с этим количеством,
            обновить portfolio_state и portfolio_positions
        иначе:
            кандидат отбрасывается

    переоценить equity по close-ценам текущего тика:
        portfolio_state.equity = cash + Σ(quantity × close_price(ticker, :tick))
            по всем открытым лотам
```

### 3.2. Исполнение кандидата (с частичным заполнением)

Если кандидат не может быть исполнен полностью, **исполняем частично** — сколько позволяет состояние счёта.

- **Покупка `quantity` акций по цене `price`:** реально исполняется `min(quantity, FLOOR(cash / price))`. Если получился `0` — кандидат отбрасывается; иначе в `trade_journal` записывается **фактическое** исполненное количество и в `portfolio_positions` добавляется **новый лот** с этим количеством, ценой `price` и датой `:tick`.
- **Продажа `quantity` акций:** реально исполняется `min(quantity, Σ quantity по всем лотам тикера)`. Если позиции нет — кандидат отбрасывается; иначе в `trade_journal` записывается **фактически** проданное количество. Списание из лотов — по принципу **FIFO**: сначала из самого старого лота (минимальная `buy_date`), потом следующий и т.д. Это влияет на зафиксированную прибыль/убыток (`pnl_realized`) каждой sell-сделки и на состав оставшихся лотов.

**Порядок обработки кандидатов:** по убыванию `priority`. **При равном `priority`** — в порядке, в котором правила записаны в `Strategy` (по позиции в списке правил).

Цены исполнения берутся по правилу из Части 4.

## Часть 4 — Главный принцип: no look-ahead bias

На текущем тике (дата = `:tick` = `run_context.current_date`) стратегия видит только прошлое. «Сегодня» для триггера ещё не наступило.

```
Стратегия видит:    данные ≤ close(:tick - 1)
Стратегия решает:   список кандидатов на тике
Движок исполняет:   по open(:tick)
Equity фиксируется: на close(:tick)
```

### 4.1. Архитектурная гарантия

Принцип обеспечен на уровне поставщиков данных: каждый принимает в конструкторе поле `max_date`, и любой запрос к дате после `max_date` возвращает «нет данных». Движок бэктеста создаёт поставщиков с `max_date = :tick - 1` на каждом тике, поэтому пользовательский запрос физически не может прочитать данные текущего или будущего тика. Подробности — см. [`docs/SPEC_DATA_PROVIDERS.md`](../SPEC_DATA_PROVIDERS.md).

В редакторе PQL поставщики создаются без `max_date`, и доступ к историческим данным открыт целиком — это нужно для пост-факт-анализа.

### 4.2. Что движок исполняет

По `open(:tick)` (для MVP). Семантика: «ордер выставлен после закрытия вчера, исполнен по открытию сегодня».

### 4.3. Equity фиксируется

В конце тика — одна точка `(date=:tick, equity)`, где `equity = cash + Σ(quantity × close(:tick))` по открытым позициям. (Кривая капитала — представление поверх `trade_journal`, см. 1.1.)

### 4.4. Реалия gap-down

Стоп-лосс между `close(:tick - 1)` и `open(:tick)`: триггер видит «−3% от входа», `open(:tick)` может быть «−5%». Это **честность модели**, а не баг.

## Часть 5 — Контекст PQL-запросов

Триггер и `Action.quantity` видят **один и тот же контекст**. Описывается ниже.

### 5.1. Общие данные — `:tick` + таблица `run_context`

Все «глобальные» поля прогона живут в одной таблице с одной строкой `run_context`:

| Колонка | Что |
|---|---|
| `current_date` | сегодняшняя дата текущего тика |
| `index` | порядковый номер тика от старта (0, 1, 2…) |
| `date_start` | начало прогона |
| `date_end` | конец прогона |
| `starting_capital` | стартовый капитал |

Дополнительно — **сокращение** `:tick`, дублирующее `run_context.current_date`. Большинство запросов оперируют только сегодняшней датой; писать `JOIN run_context rc … rc.current_date` каждый раз — лишний шум. Поэтому:

- **`:tick`** — именованный параметр, `=` `run_context.current_date`. Пользоваться, когда нужна только сегодняшняя дата (90% случаев). Биндится через `con.execute(sql, {'tick': date})`.
- **`run_context`** — обычный `JOIN run_context rc` или подзапрос. Пользоваться, когда нужны другие поля: `index`, `date_start`, `date_end`, `starting_capital`.

Это сознательный компромисс ради читаемости частых запросов. Примеры:

```sql
-- частый случай: нужна только сегодняшняя дата
SELECT t.code FROM tags t
WHERE volume(t.code, :tick - 1) / volume_sma(t.code, :tick, 20) > 1.5

-- редкий случай: нужен ещё стартовый капитал
SELECT FLOOR(rc.starting_capital * 0.10
           / close_price(:ticker, :tick - 1))
FROM run_context rc
```

Реализация: при инициализации прогона движок создаёт `run_context` через `CREATE TABLE` и вставляет одну строку. На каждом тике делает `UPDATE run_context SET current_date = ?, index = ?` (остальные поля стабильны весь прогон). Параллельно биндит ту же дату как именованный параметр через `con.execute(sql, {'tick': date})`. Это два представления одной величины — не источник правды vs зеркало, а просто два API.

`:ticker` остаётся как параметр **только** в `Action.quantity`-запросах: движок подставляет его при вызове запроса для каждого кандидата.

### 5.2. Состояние портфеля

Состояние **на конец предыдущего тика** (после исполнения вчерашних сделок и переоценки по `close(:tick - 1)`). Две таблицы.

**`portfolio_positions`** — таблица **лотов**. Одна строка = один акт покупки (не агрегированная позиция). При докупке того же тикера — добавляется новая строка. При продаже списываются лоты по **FIFO** — сначала самые старые (см. Часть 3.2).

| Колонка | Что |
|---|---|
| `ticker` | тикер |
| `quantity` | сколько акций осталось в этом лоте (уменьшается при частичных продажах из лота; строка удаляется при `quantity = 0`) |
| `buy_price` | цена, по которой акции этого лота были куплены (не меняется) |
| `buy_date` | дата покупки лота (не меняется) |

«Средняя цена входа» **не хранится** — выводится функцией `avg_price(ticker)` (см. 5.4) поверх лотов: `Σ(quantity × buy_price) / Σ(quantity)`.

«Дни удержания» **не хранятся** — это `:tick - buy_date` для конкретного лота.

**`portfolio_state`** — таблица из одной строки, глобальные скаляры счёта.

| Колонка | Что |
|---|---|
| `cash` | свободный кэш |
| `equity` | cash + Σ(quantity × close_price(ticker, :tick - 1)) по всем лотам |

`equity` хранится как поле (а не выводится при каждом запросе) — компромисс ради скорости: пересчёт по всем лотам и обращение к рыночным данным на каждом обращении триггера дороги. Движок инкрементально обновляет `equity` на каждом тике.

### 5.3. История

`trade_journal` — все исполненные сделки с начала прогона до `close(:tick - 1)`:

| Колонка | Что |
|---|---|
| `trade_date` | дата исполнения |
| `ticker` | тикер |
| `type` | `buy` / `sell` |
| `quantity` | фактически исполненное количество (с учётом частичного заполнения) |
| `price` | цена исполнения (для MVP — `open(trade_date)`) |
| `rule_name` | имя правила-источника |
| `pnl_realized` | зафиксированная прибыль/убыток сделки — только у `sell`, у `buy` = NULL |

```
pnl_realized = Σ по списываемым лотам: quantity_из_лота × (sell_price − buy_price_лота)
```

Это **зафиксированный** результат (деньги уже на счету). Не путать с **нереализованной (бумажной) прибылью/убытком** открытой позиции = `(close_price(ticker, :tick - 1) − avg_price(ticker)) × Σ quantity` (по всем лотам тикера) — она выводится из `portfolio_positions` на лету.

Сумма `pnl_realized` по всему журналу — суммарная зафиксированная прибыль/убыток за прогон. Не входит напрямую в список 7 метрик MVP (см. 1.4), но используется при их вычислении: `profit factor` = `Σ положительных pnl_realized ÷ |Σ отрицательных|`, доля прибыльных сделок = доля строк с `pnl_realized > 0`.

**`EquityCurve`** не хранится — это представление поверх `trade_journal` + рыночных данных (см. 1.1, 1.3). Если триггер хочет смотреть на **форму кривой во времени** («equity не падало 10 дней», «текущее equity выше своего 30-дневного среднего») — это требует прохода по истории; конкретная форма доступа (табличная функция, вью или отдельная производная таблица) обсуждается отдельно.

### 5.4. TA-функции

Доступные пользователю функции технического анализа. Все они — методы поставщиков данных (см. [`docs/SPEC_DATA_PROVIDERS.md`](../SPEC_DATA_PROVIDERS.md)), зарегистрированные в DuckDB как UDF. Видимое окно ограничивается `max_date` поставщика, который движок выставляет в `:tick - 1`.

**Точечные функции** — аргумент-дата интерпретируется как сама эта дата, включительно. В бэктесте, чтобы прочитать данные предыдущего дня, пишется `:tick - 1`.

| Функция | Что возвращает |
|---|---|
| `close_price(ticker, date)` | цена закрытия за `date` |
| `open_price(ticker, date)` | цена открытия за `date` |
| `volume(ticker, date)` | объём за `date` |

**Оконные функции** — аргумент-дата интерпретируется как **правая граница интервала, не включая её**. Расчёт идёт по `[date - window, date - 1]`. В бэктесте можно писать просто `:tick` — поставщик автоматически отдаст последние `window` дней, не считая текущего.

| Функция | Что возвращает |
|---|---|
| `sma(ticker, date, window)` | простая скользящая средняя цены за `window` дней до `date` |
| `volume_sma(ticker, date, window)` | средний объём за `window` дней до `date` |
| `volatility(ticker, date, window)` | стандартное отклонение дневных логдоходностей за `window` дней до `date` |
| `return_n_days(ticker, date, n)` | накопленная доходность за последние `n` дней до `date` |

Это финальный набор для MVP. Расширение (EMA, RSI, MACD, Bollinger, high/low дня) — пост-MVP, без слома структуры.

**Учётные функции** (читают `trade_journal`, чистые):

| Функция | Что возвращает |
|---|---|
| `avg_price(ticker)` | Средневзвешенная цена входа по **открытым лотам** тикера: `Σ(quantity × buy_price) / Σ(quantity)` поверх `portfolio_positions WHERE ticker = X`. **Чистая**. Используется в стопах: `WHERE close_price(ticker, :tick - 1) < avg_price(ticker) * 0.97`. Если позиции нет — NULL. |

**События** — без новых функций, обычный SELECT по `tagged_events`:
```sql
SELECT * FROM tagged_events WHERE date_start <= :tick - 1
```

### 5.5. Что НЕ доступно (намеренно)

- **Сигналы других правил на этом же тике** — правила оцениваются независимо. Координация — через `priority`, порядок правил в стратегии и доступный кэш / позиции на момент исполнения.
- **Будущие тики** — Часть 4. Любая функция, которой попросили данные с датой ≥ `:tick`, возвращает «нет данных» (это поведение поставщика данных, см. [`SPEC_DATA_PROVIDERS.md`](../SPEC_DATA_PROVIDERS.md)).
- **Состояние других прогонов** — у каждого `Backtest` свой `Portfolio` / `TradeJournal` / `EquityCurve`.

## Часть 6 — Реализация в DuckDB (нативно)

Никаких новых форматов, парсеров или обёрток. Всё — через стандартный DuckDB API. Тот же подход, что в `backend/core/precedent_engine.py`.

| Что | Как |
|---|---|
| `:tick` | Именованный параметр через `con.execute(sql, {'tick': date})`. Стандартный механизм DuckDB. Сокращение для `run_context.current_date`. |
| `run_context`, `portfolio_state`, `portfolio_positions`, `trade_journal` | **Настоящие DuckDB-таблицы** в `:memory:`-БД прогона. Движок создаёт их через `CREATE TABLE` при инициализации прогона и поддерживает обычными `INSERT` / `UPDATE` / `DELETE`. Никаких DataFrame-регистраций. Цель — переносимость на Postgres и единообразие. |
| TA-функции, `avg_price` | Python-функции, регистрируются один раз через `con.create_function(...)`. То же, что для `car()` в `precedent_engine`. |
| `events`, `tags`, `event_tags`, `tagged_events` | Уже зарегистрированы PQL-движком. Используются как есть. |
| `:ticker` | Именованный параметр, биндится при выполнении `Action.quantity` для каждого кандидата (стандартный механизм DuckDB). |

> Различение runtime vs persistent: `run_context`/`portfolio_state`/`portfolio_positions`/`trade_journal` живут в `:memory:`-БД одного прогона (эфемерные, пересоздаются при следующем прогоне). Для долгоживущих сущностей (`Strategy`, `Rule`, `Environment`, `BacktestResult`, исторический `trade_journal`) — отдельная файловая БД. Подробности — Часть 6.2.

### 6.2. Persistent-хранилище

Один файл `data/db/backtest.duckdb` с нативными DuckDB-таблицами. Стандартный реляционный подход: FK работают «из коробки», транзакции, миграции через DuckDB. Просматривать содержимое можно через DuckDB CLI, DBeaver или вкладку Database в PyCharm.

**Список таблиц.**

| Таблица | Назначение |
|---|---|
| `strategies` | Сохранённые стратегии. Колонки: `id`, `name` (UNIQUE), `created_at`. |
| `rules` | Сохранённые правила (переиспользуются между стратегиями). Колонки: `id`, `name` (UNIQUE), `trigger_sql`, `action_type`, `action_quantity_sql`, `priority`, `created_at`. |
| `strategy_rules` | Связь M2M «правило ↔ стратегия». Колонки: `strategy_id` (FK), `rule_id` (FK), `position` (порядок правила в стратегии — задаёт очерёдность исполнения при равном `priority`). |
| `environments` | Сохранённые окружения. Колонки: `id`, `name` (UNIQUE), `date_start`, `date_end`, `starting_capital`, `created_at`. |
| `backtest_results` | Результаты прогонов. Колонки: `id`, `strategy_id` (FK), `environment_id` (FK), `created_at`, `total_return_pct`, `annual_return_pct`, `max_drawdown_pct`, `sharpe`, `n_trades`, `profit_factor`, `win_rate_pct` (= 7 метрик из 1.4). |
| `trade_journal` | Persistent-журнал сделок всех прогонов. Колонки: `id` (PK), `backtest_result_id` (FK), `trade_date`, `ticker`, `type`, `quantity`, `price`, `rule_name`, `pnl_realized`. Индекс на `backtest_result_id`. |

> **Имя `trade_journal` совпадает с runtime-таблицей** в `:memory:`-БД прогона. Runtime-журнал в конце прогона переносится в persistent одной командой `INSERT INTO file_db.trade_journal (backtest_result_id, ...) SELECT <id>, ... FROM memory_db.trade_journal`.

**Автосохранение.**

- **Стратегии**: при каждом изменении в редакторе сохраняются автоматически. Пользователь может удалить стратегию вручную.
- **Прогоны**: каждый завершённый прогон автоматически добавляется в `backtest_results` + `trade_journal`. Пользователь может удалить прогон вручную.
- **Ad-hoc сущности**: если пользователь запускает прогон со «свежей» стратегией / правилом / Environment без выбора из списка, движок автосохраняет их под автосгенерированным именем (типа `Untitled-2026-04-29-14:32`). В `backtest_results` лежит ссылка на эту сохранённую сущность; ad-hoc-флаг отдельно не хранится.

**Уникальность имён**: `name` UNIQUE в каждой из таблиц `strategies`, `rules`, `environments`. Дубль → ошибка.

**Системные пресеты**: при первом старте приложения в каждую таблицу засеваются предустановленные примеры (стратегии, правила, Environment). Конкретный набор финализируется при реализации.

**Повторные прогоны**: запуск той же `(Strategy, Environment)` дважды → две строки в `backtest_results` (разные `id`, разный `created_at`). В будущем это пригодится для стратегий с элементом случайности.

**Иммутабельность.** Содержание `Strategy`, `Rule`, `Environment` после создания **не редактируется**: правила стратегии, привязки, текст триггера и `Action.quantity`-запроса, тип действия, период и стартовый капитал окружения. Чтобы получить другое содержание — создаётся новая сущность. Это гарантирует, что каждый `BacktestResult` всегда ссылается на ровно ту версию данных, которая его произвела.

**Переименование.** `name` — единственное поле, которое можно изменить после создания. Это нужно для случаев, когда сущность была сохранена ad-hoc под автогенерированным именем (`Untitled-...`) и пользователь хочет дать ей осмысленное имя. Применяется ко всем трём именованным сущностям: `Strategy`, `Rule`, `Environment`. Ссылки идут по `id`, поэтому переименование никогда не ломает уже сохранённые `BacktestResult` или связи `strategy_rules`. Новое имя должно быть непустым и уникальным внутри своей таблицы — иначе ошибка.

**Семантика удаления.**

| Сущность | Кого удаляет | Кого НЕ трогает | Запрет |
|---|---|---|---|
| `Strategy` | свои `backtest_results` и связанные `trade_journal`-строки; записи в `strategy_rules` | сами `Rule`, сами `Environment` (они независимы) | — |
| `Rule` | — | — | удалять нельзя, пока на неё ссылается хоть одна `Strategy` (через `strategy_rules`). Сначала удалить зависимые стратегии. |
| `Environment` | — | — | удалять нельзя, пока на него ссылается хоть один `BacktestResult`. Сначала удалить зависимые прогоны (или содержащие их стратегии). |
| `BacktestResult` | свои `trade_journal`-строки | `Strategy`, `Environment` остаются | — |

### 6.3. REST-API бэкенда

Минимальный набор. Из всех модифицирующих операций над `Strategy` / `Rule` / `Environment` доступны только создание, удаление и переименование (`PATCH` строго на поле `name`):

| Метод и путь | Что делает |
|---|---|
| `POST /api/backtest/run` | Запустить прогон. Тело: `strategy_id` или ad-hoc-определение стратегии; `environment_id` или ad-hoc-определение Environment. Ответ: `backtest_result_id` + посчитанные метрики. |
| `GET /api/backtest/results` | Список всех прогонов (для таблицы топа). Поддерживает сортировку по любой метрике. |
| `GET /api/backtest/results/{id}` | Карточка прогона: метрики + сделки + `EquityCurve` как вычисляемое представление. |
| `DELETE /api/backtest/results/{id}` | Удалить прогон + его строки в `trade_journal`. |
| `GET /api/strategies` | Список стратегий. |
| `POST /api/strategies` | Создать стратегию (с правилами по `rule_id`, либо с ad-hoc-определениями правил). |
| `PATCH /api/strategies/{id}` | Переименовать стратегию. Тело: `{ name }`. Любое другое поле в теле → 400. |
| `DELETE /api/strategies/{id}` | Каскадное удаление стратегии и её прогонов. |
| `GET /api/rules` | Список правил. |
| `POST /api/rules` | Создать правило. |
| `PATCH /api/rules/{id}` | Переименовать правило. Тело: `{ name }`. |
| `DELETE /api/rules/{id}` | Удалить правило. Ошибка, если на него ссылается хоть одна стратегия. |
| `GET /api/environments` | Список окружений. |
| `POST /api/environments` | Создать окружение. |
| `PATCH /api/environments/{id}` | Переименовать окружение. Тело: `{ name }`. |
| `DELETE /api/environments/{id}` | Удалить окружение. Ошибка, если на него ссылается хоть один прогон. |

**Ad-hoc сущности при `POST /api/backtest/run`**: если в теле запроса передано полное определение стратегии/правила/Environment вместо `id`, движок сначала автосохраняет под автосгенерированным именем, потом запускает прогон со ссылкой на эту новую запись.

**Имена**: `name` UNIQUE в каждой таблице. Попытка создать дубль через `POST` или переименовать через `PATCH` в существующее имя → 409. Пустое имя → 400.

18. ~~**Реализация runtime-таблиц** (`trade_journal` и пр.) — DataFrame + `register` или нативные таблицы с `INSERT`/`UPDATE`/`DELETE`?~~ **РЕШЕНО** (Часть 6): все runtime-таблицы — **нативные DuckDB-таблицы** с обычным SQL. Цель — переносимость на Postgres и единообразие.
19. ~~**Продажа больше, чем есть.**~~ **РЕШЕНО** (Часть 3.2): частичное заполнение. То же для покупки на нехватке кэша.
20. ~~**Очерёдность при равном `priority`.**~~ **РЕШЕНО** (Часть 3.2): порядок правил в `Strategy`.
21. ~~**Целостная модель персистентности (объединяет 6, 12, 13).**~~ **РЕШЕНО** (Часть 6.2):
    - Один файл `data/db/backtest.duckdb` с нативными таблицами.
    - `Strategy`, `Rule`, `Environment`, `BacktestResult` — каждый своя таблица; `strategy_rules` для связи M2M; persistent `trade_journal` со ссылкой на `backtest_results`.
    - Автосохранение всех сущностей; ad-hoc — под автосгенерированным именем; ручное удаление.
    - Уникальные имена в каждой таблице.
    - Один и тот же `(Strategy, Environment)` запущенный дважды → две строки в `backtest_results`.
    - Системные пресеты — да, контент при реализации.
22. ~~**API бэкенда.**~~ **РЕШЕНО** (Часть 6.3): минимальный CRUD; `PUT` нет, `PATCH` — только на поле `name` для всех трёх именованных сущностей (переименование разрешено, остальное иммутабельно). Каскад при удалении стратегии; запрет удаления `Rule`/`Environment` при наличии ссылок. Ad-hoc сущности автосохраняются при `POST /api/backtest/run`.
23. ~~**Прогресс длинного прогона.**~~ **РЕШЕНО.** **MVP**: прогресс-бар + минимальный живой индикатор (текущая `equity`, `n_trades_so_far`). Транспорт — polling: фронт раз в секунду делает `GET /api/backtest/runs/{id}/progress` → `{progress, current_date, current_equity, n_trades_so_far, done}`. По `done=true` забирает полный результат через `GET /api/backtest/results/{id}`. **Пост-MVP**: полный стрим (WebSocket/SSE) — живая equity-кривая + поток сделок, чтобы пользователь мог корректировать стратегию по ходу. Переход не ломает API, добавляется параллельный канал.
24. ~~**Модель ошибок.**~~ **РЕШЕНО.** Двухуровневая политика. **Жёсткие** (прогон падает полностью, `BacktestResult` не создаётся, ответ API — 400 с сообщением): синтаксические и семантические ошибки SQL в `trigger`/`Action.quantity`; нарушение контракта `Action.quantity` (не 1×1, отрицательное, нечисловой тип); период прогона выходит за пределы доступных рыночных данных. Ловятся до старта (через `EXPLAIN` / dry-compile DuckDB) или в первой sell-сделке (для контракта). **Мягкие** (продолжаем без падения, кандидат отбрасывается): `NULL` от любой функции — нет данных по тикеру, мало данных для окна, неизвестный тикер.
25. ~~**Отмена прогона.**~~ **РЕШЕНО.** Отменить можно через `POST /api/backtest/runs/{id}/cancel`. Частичный прогон **не сохраняется** — строка в `backtest_results` не создаётся, runtime-таблицы движка освобождаются. С точки зрения `backtest_results` отменённый прогон выглядит как несуществовавший.
26. ~~**Параллельные прогоны.**~~ **РЕШЕНО.** Никаких лимитов и очередей. Каждый хендлер `POST /api/backtest/run` создаёт свой `:memory:`-коннект DuckDB для runtime-таблиц — они независимы; FastAPI разруливает запросы сам. Запись `BacktestResult` + связанных `trade_journal`-строк в персистентный `data/db/backtest.duckdb` оборачивается в одну транзакцию (атомарно). Если в будущем возникнет проблема с памятью — добавим лимит.
27. ~~**Валидация стратегии при сохранении.**~~ **РЕШЕНО.** Все проверки включены; распределение по моменту срабатывания:
    - **`POST /api/strategies`**: имя непустое и уникальное; минимум одно правило; уникальные `rule_id` в наборе.
    - **`POST /api/rules`**: SQL триггера и `Action.quantity` синтаксически и семантически валидны (`con.execute('EXPLAIN ' + sql)`); `Action.quantity` на тестовой подстановке (фиктивные `:tick`, `:ticker`) возвращает 1×1 с целым ≥ 0.
    - **`POST /api/environments`**: `date_start ≤ date_end`, обе даты в глобальном диапазоне доступных рыночных данных.
    - **`POST /api/backtest/run`**: грубая проверка совместимости периода с тикерами стратегии — по тегам в SQL триггера; конкретное несовпадение ловится на лету как мягкая ошибка (NULL → пропуск).
    - Любая жёсткая ошибка → 400 с понятным сообщением.

Также зафиксированы по ходу:

- **Случайность в стратегиях (random/seed)**: в MVP **не делаем**. Прогон детерминирован — стабильная сортировка кандидатов + FIFO дают одинаковый результат на одних и тех же входах.
- **Миграции схемы `backtest.duckdb`**: явных миграций в MVP **не пишем**. На ломающем изменении схемы — пересоздаём файл (теряем накопленные прогоны). Возвращаемся к этому, когда станет реальной проблемой.
- **Логирование прогона** (базовое решение): пишем в **stdout сервера** — детали обсуждаем как открытый вопрос Q28.
