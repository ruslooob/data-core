# Бэктест стратегий — черновик глоссария и устройства

> Сессия с пользователем (ноябрь 2026). Только концептуальная модель — без кода и спецификации API. Используется как стартовая точка следующей сессии: на её основе будет написана `docs/SPEC_BACKTEST.md` и план реализации.

---

## Уровень 1 — что такое бэктест

Бэктест — это **симуляция**: берём стратегию пользователя и историю цен, прокручиваем её через прошлое день за днём (как будто торговля шла прямо тогда), в конце смотрим, что получилось.

**Вход:**
- стратегия (что делать)
- период (с какой по какую дату)
- стартовый капитал

**Выход:**
- журнал всех сделок (TradeJournal)
- метрики (Performance) — финальный капитал, прибыль, риски
- кривая капитала (EquityCurve) — как менялся баланс во времени

---

## Уровень 2 — главный цикл

Симуляция — это **главный цикл по времени**:

```
для каждого тика (= торгового дня) в периоде:
    1) дать стратегии видеть рынок (даты, цены, объёмы, состояние портфеля)
    2) спросить стратегию: «что делаем?» — получить список кандидатов
    3) исполнить кандидатов (с проверкой бюджета)
    4) зафиксировать текущий капитал в EquityCurve
```

**Тик** = единица времени симуляции. Сейчас 1 тик = 1 торговый день; в будущем может быть час/минута. Между тиками стратегия «спит». Временной контракт тика — см. Уровень 5.

В конце периода — финальный отчёт.

---

## Уровень 3 — стратегия как набор правил

**Стратегия (Strategy)** — набор правил.

**Правило (Rule)** — независимая единица. Состоит из **двух разных частей**, которые нельзя смешивать:

### 3a. Триггер (Trigger)
**PQL-запрос**, который на каждом тике возвращает **список тикеров, для которых правило сегодня сработало**. Только поиск, без «сколько» и «что делать».

Форма: `SELECT ticker FROM ... WHERE ...` с подстановкой текущей даты как параметра.

Триггер видит только данные **до конца предыдущего торгового дня** — `tick.current_date - 1` и раньше (см. Уровень 5).

Примеры:
```sql
-- триггер «вчера был всплеск объёма у любой компании»
SELECT t.code AS ticker
FROM tags t
WHERE t.type = 'company'
  AND volume(t.code, tick.current_date - 1)
    / volume_sma(t.code, tick.current_date - 1, 20) > 1.5

-- триггер «дивиденды LKOH объявлены вчера»
SELECT 'LKOH' AS ticker
WHERE EXISTS (
  SELECT 1 FROM tagged_events te
  WHERE te.tag = 'DIVIDEND_ANNOUNCEMENT'
    AND te.date_start = tick.current_date - 1
    AND te.event_id IN (SELECT event_id FROM tagged_events WHERE tag = 'LKOH')
)
```

### 3b. Действие (Action)
**Отдельная конфигурация** правила, не часть запроса. Включает:
- **тип операции** — `buy` / `sell` (или нейтральнее: `open_long` / `close_long` / `open_short` / `close_short` если будем поддерживать шорты)
- **объём** — три формы:
  - `N` акций (фиксировано)
  - на сумму `K` рублей
  - `P` процентов от свободного кэша / от всей equity
- **приоритет** — число для сортировки кандидатов на одном тике
- **имя** — для отчётности

### Главное про разделение

Триггер ищет «когда и для кого». Действие описывает «что и сколько». Они независимы — это два разных вопроса. Один и тот же триггер можно подцепить к разным действиям (одинаковый паттерн, разные тактики выхода), и наоборот.

### Симметрия правил

И правило-покупка, и правило-продажа устроены одинаково. Стоп-лосс — это просто правило-продажа с триггером «текущая цена < цена входа − 3%». Никакой специальной сущности «exit-rule» — все правила симметричны.

## Уровень 4 — как именно работает один тик

```
для каждого тика:
    кандидаты = []

    для каждого rule в стратегии:
        список_тикеров = выполнить rule.trigger с подстановкой tick.current_date
        для t в список_тикеров:
            кандидаты += сформировать_кандидата(rule.action, ticker=t)

    отсортировать кандидатов по убыванию приоритета

    для каждого кандидата по порядку:
        если хватает денег / есть позиция (для продажи):
            исполнить (записать сделку в TradeJournal, обновить кэш и позиции)
        иначе:
            пропустить

    зафиксировать equity в EquityCurve
```

**Кандидат (Candidate)** — желание правила на действие, ещё не исполненное. Имеет: тикер, тип операции, объём, приоритет, ссылку на правило.

**Сделка (Trade)** — фактически исполненная операция. Не «пара open+close», а одно действие. Пары для отчётности группируются постфактум по тикеру/времени.

**Бюджетная проверка** — на этапе исполнения:
- покупка: хватает ли cash на (количество × цена исполнения + комиссия)
- продажа: есть ли в портфеле столько акций
Если не проходит — кандидат пропускается без ошибки.

## Уровень 5 — временной контракт тика (no look-ahead bias)

**Главный принцип:** на тике `tick.current_date` стратегия видит только прошлое. «Сегодня» для триггера ещё не наступило.

```
Стратегия видит:    данные ≤ close(tick.current_date - 1)
Стратегия решает:   список кандидатов на тике
Движок исполняет:   по open(tick.current_date)   -- предложено для MVP, см. открытый вопрос 15
Equity фиксируется: на close(tick.current_date), позиции оцениваются по close
```

Это убирает целый класс скрытых ошибок: стратегия не может «подсмотреть» сегодняшнюю цену закрытия и торговать по ней же. Технически инвариант гарантирует движок: функция, получившая `tick.current_date`, физически не имеет доступа к данным после `tick.current_date - 1`.

**Стоп-лосс между close вчера и open сегодня** — реальный gap down: триггер видит «−3% от входа», исполнение по open может быть «−5%». Это часть честности модели, не баг.

**Валидация триггера на look-ahead** — отдельная фича движка (статический анализ AST или sandbox с обрезанными данными). Должна предупреждать пользователя, если он использует `close_price(ticker, tick.current_date)` напрямую — то же касается всех функций, чьи параметры даты не строго раньше `tick.current_date`.

**Следствие:** функции с двусторонним окном вокруг события (`car()` с `window_after`, `volume_ratio` / `vol_ratio` в их текущей pre/post форме) **в триггере запрещены**. Они остаются доступны в **PQL-редакторе** для пост-hoc анализа, где look-ahead легитимен.

## Уровень 6 — что доступно триггеру

PQL-запрос триггера видит обычную схему (`events`, `tags`, `event_tags`, `tagged_events`) **и** дополнительный контекст:

- `tick.current_date` — текущая дата как параметр.
- **Состояние портфеля** на момент закрытия предыдущего тика:
  - `portfolio.cash` — свободный кэш
  - `portfolio.position(ticker)` → `qty`, `avg_price`, `days_held` (NULL если нет позиции)
  - `portfolio.equity` — cash + сумма открытых позиций по `close(tick.current_date - 1)`

Конкретная форма интеграции состояния портфеля в SQL — открытый вопрос 9.

### 6a. Технический анализ (TA-функции)

Все аргументы-даты должны быть `≤ tick.current_date - 1`.

| Функция | Что возвращает |
|---|---|
| `close_price(ticker, date)` | цена закрытия |
| `open_price(ticker, date)` | цена открытия |
| `volume(ticker, date)` | объём за день |
| `log_return(ticker, date)` | логдоходность за день |
| `sma(ticker, date, window)` | скользящая средняя цены за `window` дней |
| `volume_sma(ticker, date, window)` | среднее объёма за `window` дней |
| `volatility(ticker, date, window)` | std логдоходностей за `window` дней |
| `return_n_days(ticker, date, n)` | накопленная доходность за `n` дней |

### 6b. Триггеры на основе событий

Просто `SELECT FROM tagged_events WHERE date_start <= tick.current_date - 1`. Двжижок гарантирует фильтрацию по дате. Никаких новых функций не нужно.

### 6c. Что НЕ для триггера

`car()` (с `window_after`), `volume_ratio`, `vol_ratio` (с pre+post окном) — только в PQL-редакторе для пост-hoc анализа. Набор UDF триггера и набор UDF редактора — два частично пересекающихся набора: пересечение — TA-примитивы; редактор — CAR/volume_ratio; триггер — `portfolio.*` и TA с строгой причинностью.

## Уровень 7 — контекст внутри тика

Помимо схемы PQL и TA-функций, триггер видит **четыре слоя состояния**. Всё строго `≤ close(tick.current_date - 1)`.

### 7.1. Параметры тика и прогона

| Переменная | Что |
|---|---|
| `tick.current_date` | сегодняшняя дата (триггер не вправе обращаться к ценам этого дня) |
| `tick.index` | порядковый номер тика от старта (0, 1, 2…) — для условий «не торговать первые 30 дней» |
| `backtest.date_start`, `backtest.date_end` | границы прогона |
| `backtest.starting_capital` | стартовый капитал |
| `backtest.commission_rate` | комиссия (если включена) |

### 7.2. Портфель — таблицы `portfolio_positions` и `portfolio_state`

Состояние **на конец предыдущего тика** (т.е. после исполнения вчерашних сделок и переоценки по `close(tick.current_date - 1)`).

`portfolio_positions` — все открытые позиции:

| Колонка | Что |
|---|---|
| `ticker` | тикер |
| `qty` | количество акций |
| `avg_price` | средневзвешенная цена входа |
| `days_held` | сколько торговых дней позиция держится |
| `cost_basis` | qty × avg_price |

`portfolio_state` — одна строка:

| Колонка | Что |
|---|---|
| `cash` | свободный кэш |
| `equity` | cash + Σ(qty × close_price) по открытым позициям |
| `equity_peak` | максимум equity за прогон |
| `drawdown` | `(equity_peak − equity) / equity_peak` |
| `n_open_positions` | количество открытых позиций |

**Реализационная заметка.** В `precedent_engine` мы уже регистрируем таблицы: `con.register('events', df)`. Тот же приём для портфеля — на каждом тике брать актуальный Python-объект `Portfolio`, выливать в `DataFrame`, делать `con.register('portfolio_positions', ...)` и `con.register('portfolio_state', ...)`. Без UDF и DDL — обычный реестр на тик. Идентично работает для `trades` и `equity_curve` ниже.

**Что такое `avg_price`** — средневзвешенная цена тех акций, которые **сейчас** в позиции. Пересчитывается только при докупке; при продаже не меняется.

| Действие | qty | avg_price | cost_basis |
|---|---|---|---|
| Купил 10 LKOH @ 6000 | 10 | 6000 | 60 000 |
| Докупил 5 @ 6300 | 15 | (10·6000 + 5·6300) / 15 = **6100** | 91 500 |
| Продал 8 @ 6500 | 7 | **6100** (без изменений) | 42 700 |
| Продал 7 @ 6800 | 0 | позиция удалена из таблицы | — |

Почему «средняя», а не «последняя покупка»: стоп-лосс «упал на 3% от входа» опирается на среднюю точку входа. Если бы был «last_price», при докупках на росте стоп сдвигался бы вверх и ловил шум.

Пример триггера-выхода:
```sql
SELECT ticker FROM portfolio_positions
WHERE close_price(ticker, tick.current_date - 1) < avg_price * 0.97
```

### 7.3. Журнал сделок — таблица `trades`

Все исполненные сделки с начала прогона до `close(tick.current_date - 1)`.

| Колонка | Что |
|---|---|
| `trade_date` | дата исполнения |
| `ticker` | тикер |
| `type` | `buy` / `sell` |
| `qty` | количество |
| `price` | цена исполнения (для MVP — `open(trade_date)`) |
| `commission` | комиссия по сделке |
| `rule_name` | имя правила-источника |
| `pnl_realized` | реализованный PnL — только у `sell`, у `buy` = NULL |

**Что такое `pnl_realized`** — прибыль/убыток, **зафиксированная** этой конкретной сделкой:

```
pnl_realized = qty_sold × (sell_price − avg_price_на_момент_продажи) − commission
```

Из примера выше:
- Продал 8 LKOH @ 6500 при `avg_price = 6100` → `8 × (6500 − 6100) − commission = 3200 − commission`
- Продал 7 LKOH @ 6800 при `avg_price = 6100` → `7 × (6800 − 6100) − commission = 4900 − commission`

Это **зафиксированный** результат (деньги уже на счету). Не путать с **нереализованным** PnL открытой позиции = `(current_price − avg_price) × qty`, который живёт в `portfolio_positions`.

Использование триггером:
- «не покупай тикер, если последняя продажа была убыточной за 5 дней»
- «не делай больше 3 сделок в день»
- «не повторяй сигнал того же правила чаще раза в неделю»

```sql
SELECT t.code AS ticker
FROM tags t
WHERE t.type = 'company'
  AND volume(t.code, tick.current_date - 1)
    / volume_sma(t.code, tick.current_date - 1, 20) > 1.5
  AND NOT EXISTS (
    SELECT 1 FROM trades
    WHERE ticker = t.code
      AND trade_date >= tick.current_date - 5
      AND pnl_realized < 0
  )
```

Сумма `pnl_realized` по всему журналу — одна из метрик `Performance` (чистая фиксированная прибыль за прогон).

### 7.4. Кривая капитала — таблица `equity_curve`

Точки `(date, equity)` от старта до `close(tick.current_date - 1)`. Удобные агрегаты `equity_peak` и `drawdown` уже есть в `portfolio_state`, поэтому `equity_curve` нужна, только когда триггер смотрит **на форму кривой во времени**: «equity не падало за последние 10 дней», «текущее equity выше своего же 30-дневного среднего» и т.п.

### 7.5. Что НЕ внутри тика (намеренно)

- **Сигналы других правил на этом же тике** — правила оцениваются независимо. Координация — через `priority` и проверку бюджета на этапе исполнения, не через прямую видимость.
- **Будущие тики** — no-lookahead (Уровень 5).
- **Состояние других прогонов** — у каждого `Backtest` свой `Portfolio` / `TradeJournal` / `EquityCurve`.

## Открытые вопросы (не закрыты в этой сессии)

Эти вопросы намеренно оставлены на следующую сессию — обсуждаются после того, как пользователь прочитает черновик с свежей головой.

1. **Объём (`Action.size`)** — финальный список форм: фиксированное N / сумма K / процент от cash / процент от equity. Все четыре или подмножество?
2. **Шорты** — в MVP только лонги? Или сразу `open_long` / `open_short` / `close_long` / `close_short`?
3. **Комиссии** — фиксированный процент от сделки в настройках бэктеста? Игнорируем в MVP?
4. **Слиппедж** (отклонение фактической цены исполнения от закрытия) — игнорируем в MVP?
5. **Plurality правил** — количество правил в стратегии может быть произвольным? Лимит?
6. **Хранение стратегий** — отдельная таблица `strategies` в БД (по аналогии с `precedent_queries`)? Имена уникальны? Системные пресет-стратегии?
7. **Universe тикеров** — нужен ли как отдельная сущность Strategy.universe, или каждый триггер сам определяет свою область через WHERE?
8. **Приоритеты** — целое число / float / enum «high/normal/low»? Что делает движок при равных приоритетах (стабильная сортировка по имени правила?)?
9. **Состояние портфеля в SQL** — техника интеграции (временные таблицы / UDF / переменные). Чисто реализационный вопрос.
10. **Связь с PQL-редактором** — может ли пользователь скопировать триггер прямо из сохранённого прецедентного запроса? Как описать «сделать правило из этого запроса»?
11. **UI** — отдельный виджет «Strategy editor» (по аналогии с PrecedentEditor), или встраивается в PrecedentEditor через спецсинтаксис? Скорее отдельный виджет с двумя редакторами (триггер + действие) и таблицей правил.
12. **Запуск бэктеста** — как пользователь указывает период / стартовый капитал / комиссии? Отдельный диалог при запуске?
13. **Сохранение результатов** — `BacktestResult` хранится в БД для последующего сравнения? Отдельная таблица `backtest_runs`?
14. **Сравнение стратегий** — две EquityCurve рядом, две таблицы Performance — нужна отдельная UI-фича?
15. **Цена исполнения** — по `open(tick.current_date)` (предложено для MVP, согласовано с no-lookahead) или по `close(tick.current_date)` (стандартное упрощение event study)? Слиппедж см. в вопросе 4.
16. **Финальный список TA-функций для триггера** — таблица в Уровне 6a — это набросок. Минимально достаточный список + сигнатуры финализируются перед реализацией.
17. **Финальная схема таблиц `portfolio_positions`, `portfolio_state`, `trades`, `equity_curve`** — Уровень 7 — набросок колонок. Финализируется перед кодом.
18. **Хранение журнала сделок и кривой капитала во время прогона** — DataFrame в памяти + `con.register` на каждом тике, или отдельная DuckDB-таблица, в которую движок дописывает строки? Последний вариант избавляет от регистрации, но требует общей с прогоном БД.
