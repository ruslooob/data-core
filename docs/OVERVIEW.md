# Обзор системы data-core

## Что это такое

Система для анализа влияния событий на финансовые рынки.

Дано:
- **События** — исторические события с датами: санкции, войны, катастрофы, выборы, изменения политики и т.д.
- **Котировки** — ценовые ряды акций, сырьевых активов, индексов и других финансовых инструментов

Задача: по заданному событию (или набору событий) количественно оценить, как изменилось поведение рынка в окне вокруг даты события — цена, волатильность, объём торгов.

Это называется **событийный анализ (event study)**. Ключевая метрика — CAR (Cumulative Abnormal Return): накопленная аномальная доходность, то есть отклонение фактической доходности от ожидаемой (baseline).

## Архитектура системы

```
Сырые данные (буфер обмена, Wikipedia, открытые источники)
        ↓
   ETL-конвейер
        ↓
  Структурированная БД (CSV + DuckDB)
        ↓
   Тэгирование событий
        ↓
  Аналитические модули (core/)
        ↓
   Jupyter-ноутбуки (визуализация, исследование)
```

## Структура тегов

Теги — иерархическая система классификации событий. Каждый тег имеет тип (`type`) и роль (`role`).

### Иерархия

```
actor
 ├── country      — государства, регионы, территории (RUS, USA, EU)
 ├── organization — организации, союзы, ведомства (UN, NATO, OPEC, CBR)
 ├── company      — корпорации, бизнес-структуры (GAZPROM, SBERBANK)
 ├── person       — персоны, ключевые акторы (PUTIN, BIDEN, ZELENSKY)
 └── region       — географические макрорегионы (EUROPE, ASIA, LATAM)

event
 ├── topic        — громкие единичные события (PLANE_CRASH, EARTHQUAKE, TSUNAMI)
 ├── policy       — изменения в политике или законодательстве (LAW_REFORM, MONETARY_POLICY)
 └── crisis       — кризисные явления (SANCTIONS, WAR, DEFAULT)

context
 ├── asset        — финансовые и сырьевые инструменты (OIL, BRENT, USD/RUB, S&P500)
 ├── sector       — отрасли экономики (ENERGY, TECH, FINANCE, AGRICULTURE)
 └── metric       — экономические показатели (INFLATION, GDP, UNEMPLOYMENT_RATE)
```

### Зачем нужны теги

Теги решают задачу поиска похожих событий. Пользователь вводит новое событие → система находит исторические события с пересекающимися тегами → строит статистику по этим аналогам.

Например: новое событие помечается тегами `crisis/sanctions + actor/country/RUS` → система находит все исторические санкционные события против России.

## Структура базы данных

БД имитируется через DuckDB поверх CSV-файлов. Это осознанное решение для MVP: данные остаются человекочитаемыми, легко редактируются вручную, не требуют отдельного сервера.

### Таблицы (`data/db/`)

| Файл | Содержимое |
|------|-----------|
| `events.csv` | Все события: `id`, `date_start`, `date_end`, `event` |
| `tags.csv` | Справочник тегов: `code`, `type`, `role`, `description` |
| `event_tags.csv` | Связь событий и тегов: `event_id`, `tag_code` |

### Котировки (`stocks/`)

CSV-файлы по тикерам: `DATE`, `OPEN`, `HIGH`, `LOW`, `CLOSE`, `VOL`. Плюс `splits.json` для корректировки на сплиты.

## ETL-конвейер

### Принцип работы

Конвейер превращает неструктурированные сырые данные в размеченную базу событий. Каждый шаг — отдельный скрипт или ноутбук.

```
data/events/1_raw/      — сырые данные (скопированы вручную из Wikipedia и др.)
        ↓
data/events/2_struct/   — структурированные CSV (парсер в ноутбуке make_structured_data)
        ↓
data/db/events.csv      — финальная БД событий
        ↓
data/db/event_tags.csv  — тэгирование (скрипты тэгирования)
```

### Скрипты тэгирования

Каждый скрипт отвечает за один тип тегов:

| Скрипт / ноутбук | Что тэгирует | Тег |
|-----------------|-------------|-----|
| `spacy_country_recognition` | Страны, упомянутые в тексте события | `actor/country` |
| `air_plane_crash_classification` | Авиакатастрофы | `event/topic/PLANE_CRASH` |
| *(аналогично для остальных)* | ... | ... |

### Требования к скриптам ETL

- **Идемпотентность** — повторный запуск не перезаписывает уже обработанные записи. Если изменилась только часть сырых данных, обновляется только эта часть.
- **Воспроизводимость** — результат не зависит от порядка запуска скриптов.

### Почему это важно

Система проектируется для итеративной работы: данные добавляются постепенно, скрипты запускаются многократно. Устойчивость к изменениям — ключевое требование к архитектуре.

## Аналитические модули (`core/`)

| Модуль | Назначение |
|--------|-----------|
