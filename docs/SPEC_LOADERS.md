# Загрузчики данных из внешних источников

Документ описывает архитектуру и принципы скриптов, забирающих данные из внешних источников и кладущих их в БД проекта. Цель — единые правила, по которым устроен каждый загрузчик: где хранится состояние, как избежать повторных запросов за уже скачанные данные, как ловить сбои источника и парсинга, как заменять один источник другим.

## Принципы

### Один модуль на источник, две стадии

Каждому внешнему источнику соответствует модуль `scripts/loaders/<источник>.py`. Модуль определяет до двух стадий:

- `fetch()` — ходит во внешний API/сайт, кладёт snapshot в `data/<подпапка>/`. Источник недоступен → правится только эта функция; формат файла остаётся стабильным контрактом с заливкой.
- `load(pg)` — читает локальные файлы и заливает строки в Postgres через `INSERT ... ON CONFLICT DO NOTHING`.

Стадии могут отсутствовать: у источников, где snapshot готовится вручную (RUONIA-xlsx, splits-csv), есть только `load`. По мере появления автоматической выгрузки в эти модули добавится `fetch`.

Зачем разделение стадий внутри одного модуля:

- **Обязанности раздельны.** Источник изменил API → правится `fetch`; схема БД изменилась → правится `load`; формат промежуточного файла остаётся контрактом.
- **Файл как побочный артефакт** даёт возможность аудита (что именно пришло из источника) и переналив БД с нуля без нового похода во внешнюю систему.

### Оркестратор `scripts/load_all_data.py`

Тонкий слой над лоадерами. Знает только порядок: какие стадии запускаются и в какой последовательности. Логики обработки данных не содержит. Один прогон обновляет всё.

Флаги:

- `--list` — показать доступные лоадеры.
- `--only A,B,C` — запустить только выбранные.
- `--skip-fetch` — пропустить `fetch`, выполнить только `load` из существующих файлов.
- `--only-fetch` — только `fetch`, без заливки в БД.

Зависимости между лоадерами зашиты в порядке вызова в самом оркестраторе (формальный DAG для небольшого числа источников — overengineering). У `moex_stocks` стадия `load` разбита на `load_metadata` и `load_candles`, чтобы между ними оркестратор успел вставить `moex_securities.load` (UPDATE `stocks.emitter_id`) и `stock_splits.load` (создание split-events, от которых зависит нормализация свечей).

### Идемпотентность

- На уровне БД — `INSERT ... ON CONFLICT DO NOTHING`. Повторная заливка тех же строк — no-op.
- На уровне `fetch` — повторный запуск с тем же диапазоном дат не плодит мусор и не повреждает существующие файлы.

### Инкрементальная загрузка

БД — источник правды о том, что у нас уже есть. Алгоритм `fetch` для лоадеров с инкрементом:

1. `last_date = SELECT MAX(...) FROM <table> WHERE <key>`.
2. Если `last_date IS NULL` — **initial load**: запрос во внешний источник без нижней границы. Источник сам отдаёт всю доступную историю по бумаге. Файл создаётся с нуля.
3. Иначе — **incremental load**: запрос с нижней границей, охватывающей последние 7 торговых дней по версии БД (см. overlap-проверку ниже) и далее до сегодня. Дельта дописывается в существующий файл.
4. `load(pg)` подхватывает файл; дубли уходят в no-op через `ON CONFLICT DO NOTHING`.

### Cross-validation при замене источника

Перед первой заменой существующего источника новым делается **разовая** сверка двух источников на одной выборке. Это **отдельный скрипт** в `scripts/`, не часть лоадера. После успешного прохождения скрипт удаляется отдельным коммитом — история остаётся в git.

Правила сверки:

- **Акции (ISS vs Finam):** ~10 sample-дат равномерно по истории, ~10 тикеров. Допуск **0.5%** по `open` и `close` одновременно. Превышение в любой точке — стоп, диагностика пользователю.
- **Дивиденды (ISS vs `dividends_all.csv`):** жёсткое сравнение по количеству выплат на тикер, суммам и датам. Любое расхождение — стоп, полный diff пользователю; пользователь сам решает, какой источник считать каноном.

При стопе `fetch` новый файл не пишет; решение «принимать или нет» принимает пользователь после анализа diff.

### Sanity-проверки на каждом запуске

`fetch` проверяет качество дельты перед записью в файл:

- `open / high / low / close ≤ 0` → ошибка. NULL допускается.
- `high < low` → ошибка (нарушение OHLC-инварианта).
- Для **акций** дополнительно: `close > 10⁷` или `close < 10⁻⁴` → ошибка (защита от сдвига порядков). Для индексов и валют не применяется — у них шире диапазон по природе.
- Нет дублей по ключу (например, `(ticker, date)`).
- Все даты дельты лежат в окне `(last_date - overlap, today]` (для incremental) или `(-∞, today]` (для initial).

При любой ошибке `fetch` останавливается, файл не пишется.

### Overlap-проверка связности на incremental-запуске

Каждый incremental-запрос захватывает **7 последних торговых дней по версии БД** (читаются как `ORDER BY date DESC LIMIT 7`). Эти 7 точек **уже есть в БД**. `fetch` сверяет значения, отдаваемые источником сейчас, со значениями в БД. Несовпадение хотя бы в одной точке — стоп, диагностика.

Защищает от двух классов сбоев:

- Корректировка истории на стороне источника (сплит, делистинг, реорганизация, переоценка).
- Ошибка парсинга в нашем коде.

## Лоадеры

### loaders/moex_stocks.py
Источник: ISS Мосбиржи, ручки `/iss/history/engines/stock/markets/{shares|index}/securities/{ticker}`. Объединяет акции и индексы — оба пишутся в Finam-формате в `data/stocks/<TICKER>_<имя>_1day.txt`, общая стадия `load` сканирует `data/stocks/*.txt` единым glob'ом.

`fetch_stocks()` — инкрементально обновляет акции (initial для нового тикера, incremental с overlap-проверкой для остальных). НЕ заменяет Finam-выгрузки, а **дополняет** их — у ISS физически нет старых данных по большинству бумаг (Мосбиржа начала торговать многими акциями в 2003-2013 годах, до этого торги шли на тогдашней РТС, эта история есть только в Finam-файлах). После cross-validation Finam и ISS-данные хранятся в одном файле по тикеру.

`fetch_indices()` — полностью перезаписывает историю индексов (RGBITR, RGBI, MCFTR, RTSI).

`load(pg)` разбит на два публичных метода:
- `load_metadata(pg)` — создаёт записи в `stocks` (тикеры из имён файлов).
- `load_candles(pg)` — загружает свечи с нормализацией по сплитам, прочитанным из `events`.

### loaders/moex_securities.py
Источник: ISS Мосбиржи, ручки `/iss/securities.json` (батч-листинг) и `/iss/securities/{ticker}.json` (детальные карточки). Что грузит: перечень бумаг фондового рынка и связанных эмитентов с обогащением полями LATNAME, ISSUEDATE, ISSUESIZE, FACEVALUE, FACEUNIT, LISTLEVEL.

`fetch()` — двухпроходный: Pass 1 идёт по батч-листингу, Pass 2 параллельно (10 потоков) обогащает каждую бумагу. Результат — `data/stocks/moex_securities.csv` и `data/stocks/moex_emitters.csv`. Идемпотентно: пропускается если файлы обновлены сегодня.

`load(pg)` — INSERT эмитентов в `emitters`, UPDATE `stocks` по `emitter_id` для уже известных тикеров. Синтетические тикеры (SAVINGS_MIACR и пр.) остаются с `emitter_id IS NULL`.

### loaders/stock_splits.py
Только `load(pg)` — `fetch` сейчас отсутствует. CSV `data/stocks/splits.csv` пополняется руками по результатам ручного аудита (см. `scripts/ops/check_splits.py` — сканер подозрительных скачков цены). TODO добавить `fetch` с ISS, когда появится надёжная ручка истории корпоративных действий.

`load(pg)` создаёт события `STOCK_SPLIT` в `events` (id — детерминированный UUID5 от ticker + date) и связки в `event_tags`: тег `STOCK_SPLIT` плюс company-тег тикера. Запускается **до** загрузки свечей — нормализация цен читает сплиты обратно из БД.

### loaders/mfd_rates.py
Источник: [mfd.ru/credits/centrobank](https://mfd.ru/credits/centrobank/). Объединяет fetch ставок межбанковского рынка и генерацию синтетического безрискового индекса.

`fetch()` — для каждого рабочего дня парсит таблицу 6 сроков (1, 7, 30, 90, 180, 360 дней) × 3 ставки (MIBID, MIBOR, MIACR). Дописывает в `data/stocks/mfd_rates.csv` инкрементально. Чтобы перезалить с нуля — удалить CSV.

`load(pg)` — генерирует синтетический тикер `SAVINGS_MIACR` из овернайт-ставки MIACR (тенор=1, ACT/365, сложный процент с начальной ценой 1000). Используется как безрисковый бенчмарк и источник R_f для Sharpe.

### loaders/ruonia.py
Только `load(pg)` — `fetch` сейчас отсутствует. Исходный xlsx `data/stocks/RUONIA_*.xlsx` лежит руками. TODO добавить `fetch`, тянущий с открытой страницы статистики ЦБ.

`load(pg)` читает первый найденный `RUONIA_*.xlsx`, лист `RC`, колонки `DT` и `ruo`, льёт в таблицу `risk_free_rate`.

### loaders/dividends_dohod.py
Источник: dohod.ru, страница `/ik/analytics/dividend/<ticker>`. Что грузит: история дивидендных выплат по российским акциям.

`fetch()` — для каждого тикера, уже присутствующего в `dividends_all.csv` (плюс опциональный список EXTRA_TICKERS), парсит страницу. Полностью переписывает CSV (источник отдаёт всю историю каждый раз). Перед записью сравнивает старое и новое по количеству выплат на тикер.

`load(pg)` — создаёт два события в `events` на каждую строку: «Объявление дивидендов» (event_date = announcement_date) и «Выплата дивидендов» (event_date = payment_date). id события — детерминированный UUID5.

### loaders/cb_rates.py
Источник: cbr.ru, страница `/hd_base/KeyRate/` (GET с параметрами `UniDbQuery.Posted=True&UniDbQuery.From=...&UniDbQuery.To=...`, кодировка cp1251). Что грузит: историю ключевой ставки ЦБ РФ (с 13.09.2013).

`fetch()` — страница отдаёт посуточный ряд значений; парсер дедуплицирует подряд равные значения и оставляет только **даты изменения ставки**. Записывает в `data/macro/cb_rates.csv` со столбцами `effective_date, rate_pct, rate_type='key'`. Инкрементально.

`load(pg)` создаёт события `CB_RATE_DECISION` в `events` с приближением `announcement_date = effective_date - 1 business day`. В payload — `rate_pct`, `rate_pct_prev`, `change_bp`, `direction` (hike/cut/hold/initial), `effective_date`. Тег: `CB_RATE_DECISION` без тегов-тикеров — макрособытие.

Ставка рефинансирования (1992–2015) в первой итерации **не грузится**: cbr.ru через `hd_base/` эту страницу больше не отдаёт. Альтернативный источник — отдельной итерацией, см. `todo.md`.

### loaders/edisclosure_events.py
Источник: e-disclosure.ru, ручка `POST /api/search/sevents`. Что грузит: корпоративные раскрытия по эмитентам, у которых есть бумаги в `stocks`.

`fetch()` — для каждого эмитента (JOIN `emitters × stocks`) делает запрос без фильтра типа за окно дат [2000-01-01, сегодня]. API режет выдачу одного запроса значением `maxFoundEventsToShow` (обычно 1200) — окно дат при превышении лимита делится пополам рекурсивно. Все подокна сливаются в один JSON-файл `data/events/edisclosure/<inn>.json`. WAF Servicepipe принимает запрос даже без cookies (через 307-redirect); опциональные cookies подкладываются из env, если заданы.

`load(pg)` — читает JSON-файлы и для каждого события, чей `eventName` есть в словаре маппинга, создаёт строку в `events` (id = `edisc:<pseudoGUID>`) + связки `event_tags`: тег типа события плюс company-теги всех бумаг эмитента.

### Планируется

#### loaders/moex_dividends.py *(планируется)*
Источник: ISS Мосбиржи, ручка `/iss/securities/{security}/dividends`. Что грузит: дивидендные события c полями `announcement_date` и `payment_date`. Заменяет `data/stocks/dividends_all.csv` от dohod.ru. Перед заменой — cross-validation.

#### loaders/moex_currencies.py *(планируется)*
Источник: ISS Мосбиржи, ручка истории на `/iss/history/engines/currency/markets/selt/securities/{ticker}`. Что грузит: курсы валют (USD/RUB, EUR/RUB). Cross-validation не выполняется — в БД пока нет валютных данных, сверять не с чем.
