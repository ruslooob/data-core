# Загрузчики данных из внешних источников

Документ описывает архитектуру и принципы скриптов, забирающих данные из внешних источников и кладущих их в БД проекта. Цель — единые правила, по которым устроен каждый загрузчик: где живёт состояние, как избежать повторных запросов за уже скачанные данные, как ловить сбои источника и парсинга, как заменять один источник другим.

## Принципы

### Двухступенчатая архитектура: парсер → файл → загрузчик в БД

Парсер источника (`scripts/load_<source>.py`) ходит во внешний API, кладёт snapshot в `data/<подпапка>/`. Скрипт `scripts/load_data_to_postgres.py` читает локальные файлы и заливает строки в БД.

Зачем разделение:

- **Обязанности раздельны.** Источник недоступен → правим парсер; схема БД изменилась → правим загрузчик; формат файла — стабильный контракт между ними.
- **Файл как побочный артефакт** даёт возможность аудита (что именно пришло из источника) и переналив БД с нуля без нового похода во внешнюю систему.

### Идемпотентность

- На уровне БД — `INSERT ... ON CONFLICT DO NOTHING` в `load_data_to_postgres.py`. Повторная заливка тех же строк — no-op.
- На уровне парсера — повторный запуск с тем же диапазоном дат не плодит мусор и не повреждает существующие записи.

### Инкрементальная загрузка

БД — источник правды о том, что у нас уже есть. Алгоритм парсера:

1. `last_date = SELECT MAX(...) FROM <table> WHERE <key>`.
2. Если `last_date IS NULL` — **initial load**: запрос во внешний источник без нижней границы. Источник сам отдаёт всю доступную историю по бумаге. Файл создаётся с нуля.
3. Иначе — **incremental load**: запрос с нижней границей, охватывающей последние 7 торговых дней по версии БД (см. overlap-проверку ниже) и далее до сегодня. Дельта дописывается в существующий файл, имя обновляется с новой till-датой.
4. `load_data_to_postgres.py` подхватывает файл; дубли уходят в no-op через `ON CONFLICT DO NOTHING`.

### Cross-validation при замене источника

Перед первой заменой существующего источника новым делается **разовая** сверка двух источников на одной выборке. Это **отдельный скрипт** в `scripts/`, не часть парсера. После успешного прохождения скрипт удаляется отдельным коммитом — история остаётся в git.

Правила сверки:

- **Акции (ISS vs Finam):** ~10 sample-дат равномерно по истории, ~10 тикеров. Допуск **0.5%** по `open` и `close` одновременно. Превышение в любой точке — стоп, диагностика пользователю.
- **Дивиденды (ISS vs `dividends_all.csv`):** жёсткое сравнение по количеству выплат на тикер, суммам и датам. Любое расхождение — стоп, полный diff пользователю; пользователь сам решает, какой источник считать каноном.

При стопе парсер новый файл не пишет; решение «принимать или нет» принимает пользователь после анализа diff.

### Sanity-проверки на каждом запуске

Парсер проверяет качество дельты перед записью в файл:

- `open / high / low / close ≤ 0` → ошибка. NULL допускается.
- `high < low` → ошибка (нарушение OHLC-инварианта).
- Для **акций** дополнительно: `close > 10⁷` или `close < 10⁻⁴` → ошибка (защита от сдвига порядков). Для индексов и валют не применяется — у них шире диапазон по природе.
- Нет дублей по ключу (например, `(ticker, date)`).
- Все даты дельты лежат в окне `(last_date - overlap, today]` (для incremental) или `(-∞, today]` (для initial).

При любой ошибке парсер останавливается, файл не пишется.

### Overlap-проверка связности на incremental-запуске

Каждый incremental-запрос захватывает **7 последних торговых дней по версии БД** (читаются как `ORDER BY date DESC LIMIT 7`). Эти 7 точек **уже есть в БД**. Парсер сверяет значения, отдаваемые источником сейчас, со значениями в БД. Несовпадение хотя бы в одной точке — стоп, диагностика.

Защищает от двух классов сбоев:

- Корректировка истории на стороне источника (сплит, делистинг, реорганизация, переоценка).
- Ошибка парсинга в нашем коде.

## Загрузчики

### load_mfd_rates.py
Источник: [mfd.ru/credits/centrobank](https://mfd.ru/credits/centrobank/). Что грузит: дневные overnight-ставки межбанковского рынка (MIBID / MIBOR / MIACR, тенор 1 день).

### load_moex_indices.py
Источник: ISS Мосбиржи, ручка [`/iss/history/engines/stock/markets/index/securities/{ticker}`](https://iss.moex.com/iss/reference/439). Что грузит: исторические значения индексов (RGBITR, RGBI, MCFTR, RTSI).

### load_moex_stocks.py *(планируется)*
Источник: ISS Мосбиржи, та же ручка истории на `/iss/history/engines/stock/markets/shares/securities/{ticker}`. Что грузит: дневные котировки акций.

**Не заменяет Finam-выгрузки**, а **дополняет** их. У ISS физически нет старых данных по большинству бумаг — Мосбиржа начала торговать многими акциями в 2003-2013 годах, а до этого они торговались на тогдашней РТС, и эта история есть только в Finam-файлах. Финам-файлы остаются как исторический фундамент.

ISS-загрузчик пишет результат в отдельный файл (с маркером `ISS` в имени, чтобы отличать от Finam) рядом с существующим Finam-файлом. `load_data_to_postgres.py` обрабатывает оба, дубли уходят в no-op через `ON CONFLICT DO NOTHING`.

Initial load (тикер не существовал ни в БД, ни в Finam) — работает только для новых тикеров после IPO.

**Двухфайловое состояние временное.** Cross-validation подтвердил эквивалентность Finam и ISS в overlapping-окне, поэтому отдельный учёт источников информации не несёт. Для слияния используется одноразовый скрипт `scripts/merge_stock_files.py`: для каждого тикера объединяет Finam-файл и ISS-файл в один `<TICKER>_<имя>_1day_<from>_<till>.txt` (при конфликте дат — приоритет ISS), проверяет инвариант «данных не теряем», затем удаляет оба исходника. После прогона скрипт удаляется отдельным коммитом, история остаётся в git — по тому же принципу, что и скрипты cross-validation. После миграции `load_moex_stocks.py` работает с единственным файлом по тикеру.

### load_moex_dividends.py *(планируется)*
Источник: ISS Мосбиржи, ручка `/iss/securities/{security}/dividends`. Что грузит: дивидендные события c полями `announcement_date` и `payment_date`. Заменяет `data/stocks/dividends_all.csv` от dohod.ru.

### load_cb_rates.py
Источник: cbr.ru, страница `/hd_base/KeyRate/` (GET с параметрами `UniDbQuery.Posted=True&UniDbQuery.From=...&UniDbQuery.To=...`, кодировка cp1251). Что грузит: историю ключевой ставки ЦБ РФ (с 13.09.2013). Страница отдаёт посуточный ряд значений; парсер дедуплицирует подряд равные значения и оставляет только **даты изменения ставки**. Записывает в `data/macro/cb_rates.csv` со столбцами `effective_date, rate_pct, rate_type='key'`.

Затем `load_data_to_postgres.py` читает CSV и создаёт события `CB_RATE_DECISION` в `events` с приближением `announcement_date = effective_date - 1 business day`. В payload — `rate_pct`, `rate_pct_prev`, `change_bp`, `direction` (hike/cut/hold/initial), `effective_date`. Тег: `CB_RATE_DECISION` (без тегов-тикеров — макрособытие).

Ставка рефинансирования (1992–2015) в первой итерации **не грузится**: cbr.ru через `hd_base/` эту страницу больше не отдаёт. Альтернативный источник — отдельной итерацией, см. `todo.md`.

### load_moex_currencies.py *(планируется)*
Источник: ISS Мосбиржи, ручка истории на `/iss/history/engines/currency/markets/selt/securities/{ticker}`. Что грузит: курсы валют (USD/RUB, EUR/RUB). Cross-validation не выполняется — в БД пока нет валютных данных, сверять не с чем.

### load_moex_securities_list.py *(планируется)*
Источник: ISS Мосбиржи, ручка `/iss/engines/stock/markets/shares/securities`. Что грузит: текущий список торгуемых акций (metadata, не котировки). Используется для обнаружения новых тикеров.
