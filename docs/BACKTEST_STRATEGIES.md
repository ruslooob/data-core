# Журнал стратегий бэктеста

Этот файл — рабочий журнал поиска наилучшей стратегии. Цикл:
1. Сформулировать гипотезу (что должно дать преимущество и над чем).
2. Реализовать стратегию через `trigger_sql` + `action_quantity_sql`, прогнать на окружении.
3. Записать результат в раздел «Гипотезы». Неудачные тоже фиксируем — чтобы не повторять.
4. Сделать вывод и перейти к следующей.

---

## Жизненный цикл стратегии

Если после анализа журнала сделок выяснилось, что стратегия работала не так, как задумывалась (например, из-за неточностей в SQL триггера или quantity — пропущенный фильтр, ошибка в окне дат, использование функции с неожиданной семантикой):

1. Подкорректировать SQL и **выкатить новую стратегию рядом со старой** (новое имя, новый прогон). Не переписывать старую in-place — её результат уже зафиксирован в `backtest_results` и в этом журнале как «как было».
2. Прогнать новую версию на том же окружении и сравнить.
3. **Старую стратегию и её backtest_result удаляем только после того, как убедились, что новая лучше** (или однозначно эквивалентна, если правка чисто косметическая). До этого момента обе живут параллельно — это страховка от регрессии в правке.
4. В журнале запись о гипотезе обновляется: старая версия упоминается коротко («v1, удалена, причина: …»), новая описывается полностью с актуальными метриками.

## Доступные функции и таблицы

**TA-функции** (PL/Python в Postgres, см. `scripts/init_postgres_*_udfs.py`):
`close_price`, `open_price`, `volume`, `avg_price`, `volume_ratio`, `vol_ratio`, `sma`, `volume_sma`, `volatility`, `return_n_days`, `car`.

Все TA-функции читают session-GUC `backtest.max_date` — движок выставляет его на каждом тике для no-lookahead.

**Runtime-таблицы** (TEMP в сессии прогона):
- `run_context(current_tick, index, date_start, date_end, starting_capital)` — `index` начинается с 0.
- `portfolio_state(cash, equity)` — одна строка с текущим состоянием.
- `portfolio_positions(lot_id, ticker, quantity, buy_price, buy_date)` — лоты, FIFO.
- `trade_journal(...)`, `equity_curve(tick_date, equity)`.

**Persistent-таблицы**: `tagged_events`, `tags`, `events`, `event_tags`.

## Стиль SQL правил

`trigger_sql` и `action_quantity_sql` — **всегда многострочные с отступами**. Никаких однострочников по 200 символов и склеенных через `+` Python-кусков. SQL правила пишется как обычный читаемый SQL: `WHERE`, `AND`, `JOIN`, подзапросы — на отдельных строках с выравниванием. Это нужно и для diff-обзора в редакторе правил, и для будущих ревью.

```sql
-- ✓ так
SELECT 'SAVINGS_MIACR' AS ticker
FROM portfolio_state s
WHERE s.cash < close_price('LKOH', :tick - 1)
  AND s.cash + COALESCE(
        (SELECT SUM(p.quantity * close_price('SAVINGS_MIACR', :tick - 1))
         FROM portfolio_positions p
         WHERE p.ticker = 'SAVINGS_MIACR'),
        0
      ) >= close_price('LKOH', :tick - 1)
  AND close_price('LKOH', :tick - 1) IS NOT NULL

-- ✗ не так
SELECT 'SAVINGS_MIACR' AS ticker FROM portfolio_state s WHERE s.cash < close_price('LKOH', :tick - 1) AND s.cash + COALESCE((SELECT SUM(p.quantity * close_price('SAVINGS_MIACR', :tick - 1)) FROM portfolio_positions p WHERE p.ticker = 'SAVINGS_MIACR'), 0) >= close_price('LKOH', :tick - 1)
```

При создании новых правил скриптом — использовать triple-quoted строки, не конкатенацию. При правке существующих — отформатировать.

## Антипаттерны (так НЕ писать)

### A1. `(SELECT index FROM run_context) = 0` + `open_price(:tick)` или `close_price(:tick)` в quantity

Не работает. На первом тике `prev_date is None`, движок ставит `backtest.max_date = 1990-01-01`, любой UDF возвращает NULL → quantity NULL → пропуск. Стратегия делает **0 сделок** молча.

**Правильно:** триггер на `index = 1`, в quantity `close_price(<ticker>, :tick - 1)`.

```sql
-- ✗ НЕ работает
WHERE (SELECT index FROM run_context) = 0
SELECT FLOOR(s.cash / open_price('LKOH', :tick)) FROM portfolio_state s

-- ✓ Работает
WHERE (SELECT index FROM run_context) = 1
SELECT FLOOR(s.cash / close_price('LKOH', :tick - 1)) FROM portfolio_state s
```

### A2. `open_price(<t>, :tick)` где-либо в trigger/quantity

В trigger-фазе движок ставит `max_date = prev_date`, поэтому `open_price(:tick)` всегда NULL. `:tick`-цены доступны только в `_execute_buy/_sell`, которые движок вызывает сам. В SQL правил используем `close_price(:tick - 1)` как proxy — реальная покупка пройдёт по `open(:tick)`, движок сам ограничит объём через `affordable = floor(cash / open)`.

### A3. quantity без проверки на NULL от TA-функции

Если `sma(t, :tick - 1, 50)` ещё не накопила окно — она вернёт NULL. `FLOOR(cash / NULL) = NULL` → пропуск. Защищаем через `WHERE sma(...) IS NOT NULL` в триггере.

## Валидные шаблоны

### Buy-and-hold одного актива

```sql
-- trigger
SELECT '<TICKER>' AS ticker FROM portfolio_state
WHERE (SELECT index FROM run_context) = 1

-- quantity
SELECT FLOOR(s.cash / close_price('<TICKER>', :tick - 1)) FROM portfolio_state s
```

### DCA / «вкладывай весь cash каждый день»

```sql
-- trigger
SELECT '<TICKER>' AS ticker FROM portfolio_state
WHERE cash >= close_price('<TICKER>', :tick - 1)

-- quantity (большой лимит, движок сам ограничит affordable)
SELECT 999999999
```

### Sell всю позицию по сигналу

```sql
-- trigger
SELECT pp.ticker FROM portfolio_positions pp
WHERE close_price(pp.ticker, :tick - 1) < avg_price(pp.ticker) * 0.95
GROUP BY pp.ticker

-- quantity
SELECT SUM(quantity) FROM portfolio_positions WHERE ticker = :ticker
```

`actionType=sell`, `priority=300` (стопы исполняются раньше входов).

### Триггер по событию

```sql
SELECT te.tag AS ticker
FROM tagged_events te
JOIN tags t ON t.code = te.tag AND t.type = 'company'
WHERE EXISTS (
  SELECT 1 FROM tagged_events te2
  WHERE te2.event_id = te.event_id
    AND te2.tag = 'DIVIDEND_ANNOUNCEMENT'
    AND te2.date_start = :tick - 1
)
```

## Гипотезы и проверки

### H0 — Базовый фон (benchmark)

> Прежде чем сравнивать активные стратегии, надо понять, что даёт пассивное поведение. Это нижний бар.

**Окружение:** `LKOH full history 2002-2025` (5779 торговых дней), стартовый капитал 1М ₽.

| Стратегия | Σ доход. | Год.% | maxDD | Sharpe | Сделок | Комментарий |
|---|---:|---:|---:|---:|---:|---|
| Buy LKOH all available | **+6346%** | 19.3% | 72% | 0.50 | 71 | весь cash в LKOH каждый день |
| Gold buy-and-hold (CBR fixing) v3 | +3268% | 16.0% | 49% | 0.51 | 1 | купил золото на 2-м тике, держим |
| Buy LKOH each day | +2091% | 13.9% | 72% | 0.37 | 3029 | DCA по 1 акции в день |
| Market baseline: IMOEX buy-and-hold | +981% | 10.6% | 74% | 0.28 | 1 | price-return индекс (без дивидендов) |
| Накопит. счёт SAVINGS_MIACR | +286% | 9.0% | 0% | 0.98 | 1 | капитализация под MIACR overnight, окружение 2010-2025 |

**Вывод H0:** на длинной истории все «активные» базы (LKOH/Gold/IMOEX) дают близкий Sharpe 0.28–0.51 при maxDD 49–74%, тогда как накопительный счёт под MIACR — Sharpe 0.98 при нулевой просадке (но он же — R_f, поэтому Sharpe формально завышен из-за остаточной несинхронности дневной доходности equity и R_f, см. ниже). Среди рисковых активов золото чуть обогнало LKOH (0.51 vs 0.50) — направление: проверить mix LKOH+Gold.

### H1 — Mix LKOH/Gold даёт лучший Sharpe, чем чистый LKOH или чистое золото

> Гипотеза: совместное хранение золота и акций уменьшает максимальную просадку и поднимает Sharpe.

**Стратегии:** `Mix LKOH/Gold 30/70`, `50/50`, `70/30` — простая ребалансировка по близости к целевой доле.

**Окружение:** `LKOH full history 2002-2025`.

| Стратегия | Σ доход. | Год.% | maxDD | Sharpe | Сделок |
|---|---:|---:|---:|---:|---:|
| Mix 30/70 (gold heavy) | +3125% | 15.8% | **41%** | **0.55** | 36 |
| Mix 50/50 | +2990% | 15.6% | 52% | 0.52 | 36 |
| Mix 70/30 (lkoh heavy) | +2854% | 15.4% | 59% | 0.47 | 36 |

**Вывод H1:** **подтвердилась.** 30/70 даёт лучший Sharpe (0.55 vs 0.51 у чистого золота, vs 0.50 у Buy LKOH all available) — небольшой, но устойчивый перевес. MaxDD упал с 72% до 41%. Чем больше доля золота, тем лучше риск-скорректированная.

### H2 — Технические сигналы на одной фишке (LKOH) улучшают risk-adj vs DCA

> Гипотеза: вход по техническому сигналу (просадка, momentum) даёт более высокий Sharpe, чем слепое DCA.

**Стратегии:** `LKOH dip-buy (SMA20)`, `LKOH dips/spikes vs SMA50`, `Golden Cross LKOH 50/200`, `Mini-scalper LKOH`.

**Окружение:** `LKOH full history 2002-2025`.

| Стратегия | Σ доход. | Год.% | maxDD | Sharpe | Сделок |
|---|---:|---:|---:|---:|---:|
| LKOH dip-buy (SMA20) | +824% | 9.9% | 47% | 0.25 | 1078 |
| LKOH dips/spikes vs SMA50 | +434% | 7.3% | 68% | 0.16 | 55 |
| Golden Cross 50/200 | +335% | 6.4% | 46% | 0.10 | 40 |
| Mini-scalper LKOH | +198% | 4.7% | 61% | −0.02 | 823 |

Сравнение с baseline: `Buy LKOH each day` (+2091%, Sharpe 0.37).

**Вывод H2:** **отвергнута.** Все 4 технические стратегии проиграли простому DCA — и по абсолютной доходности, и по Sharpe. Mini-scalper даже даёт **отрицательный** Sharpe — проигрывает безрисковому. На тренде вверх активный выход и пере-вход теряет capital appreciation. Не копать дальше в эту сторону на одной фишке без принципиально нового сигнала.

### H3 — Дивидендный capture (announce-aware)

> Гипотеза: цена «накапливает» дивиденд перед выплатой и сбрасывает после — на этом можно играть. Правильная реализация требует двухдатной модели события: покупаем **только когда дивиденды уже объявлены** (`announce_date <= tick`), а до фактической выплаты осталось ≤ 7 дней. Продаём через 5 торговых дней после payment — расчёт на частичное закрытие дивидендного гэпа.

**Стратегия:** `H3 v2: LKOH dividend capture (announce-aware)`. 2 правила:
- Buy LKOH (priority=100): `te.tag = 'DIVIDEND_PAYMENT'` для LKOH, `te.announce_date <= :tick - 1`, `te.date_start BETWEEN :tick + 1 AND :tick + 7`. На весь cash: `FLOOR(s.cash / close_price('LKOH', :tick - 1))`.
- Sell LKOH (priority=100): `te.date_start = :tick - 5`. Продаём всю позицию.

**Окружение:** `Gold ETF Era 2022-2025` (783 дня).

**Предыстория.** Первая версия (`H3 v1: LKOH dividend capture`, удалена) на том же окне дала **−29%**. Причина — `WHERE te.date_start BETWEEN :tick + 3 AND :tick + 7` без проверки `announce_date <= tick`: до миграции на двухдатную модель события имели только одну дату, и формальный no-lookahead соблюдался, но фактически правило использовало знание о будущих выплатах, которые в реальности на тех тиках ещё не были объявлены. После добавления `announce_date` в `events` правило получило явный фильтр.

| Стратегия | Σ доход. | Год.% | maxDD | Sharpe | Сделок |
|---|---:|---:|---:|---:|---:|
| H3 v2 (announce-aware) | **+23.4%** | 6.98% | 26.3% | **−0.09** | 9 |
| H3 v1 (look-ahead bug, удалена) | −29.4% | −10.6% | 30% | (старая формула) | 10 |

**Вывод H3 v2:** **не подтвердилась.** Стратегия даёт положительную абсолютную доходность (+23%) и годовых 6.98%, но это **ниже** безрисковой ставки за тот же период — отсюда отрицательный Sharpe (−0.09). На этом окне проигрывает и `GOLDCB buy-and-hold` (+188%) почти в 8 раз. Журнал сделок (9 trades, 4 цикла buy→dividend→sell):
- 2022-12: −123k (gap не закрылся за 5 дней).
- 2023-05: +254k 🚀 (хорошее восстановление цены до выплаты + дивиденд).
- 2024-05: dividend получен, но **sell-триггер не сработал** — `te.date_start = :tick - 5` не попал ни на один торговый день (праздники/выходные в окне), позиция держится открытой до конца окна.
- 2025-06: ещё один dividend на той же открытой позиции.

Точечная правка sell-триггера на `BETWEEN :tick - 7 AND :tick - 5` решит проблему пропуска. См. идею H17.

Тема дивидендной капчи остаётся открытой: проверить на полной истории `LKOH 2002-2025` (см. идею H11) и с улучшенным sell-триггером (H17).

### H5 — Trailing stop −15% поверх Buy LKOH all-in спасает от просадки

> Гипотеза: добавить защитный механизм поверх лидера лидерборда — `Buy LKOH all available` (+6346%, maxDD 72%). Trailing stop должен срезать большие просадки. Вход разрешён только когда close > SMA50 (классический трендовый фильтр) — чтобы не покупать в нисходящем тренде после стопа.
>
> Параметры взяты как стандартные значения risk-management/trend-following: 15% trailing — общепринятый защитный порог; SMA50 — стандартный medium-term трендовый фильтр. Не подгонка.

**Стратегия:** `H9: LKOH all-in + 15% trailing + SMA50 trend filter`.

- Buy (priority=10): cash хватает на 1 акцию AND `close_price(:tick-1) > sma(:tick-1, 50)`. Quantity = 999999999 (движок ограничит affordable).
- Sell (priority=300): equity упал на ≥15% от своего исторического пика → продать всю позицию LKOH.

**Окружение:** `LKOH full history 2002-2025`.

| Метрика | H9 | Базовый Buy LKOH all-in |
|---|---:|---:|
| Σ доход. | +833% | +6346% |
| Год.% | 9.9% | 19.3% |
| **maxDD** | **43%** | **72%** ⬇️ −29 п.п. |
| Sharpe | 0.25 | 0.50 |
| Profit factor | 1.18 | — |
| Win rate | 50.0% | — |
| Сделок | 2122 | 71 |

**Вывод H5:** **подтвердилась частично.**
- ✓ **Trailing stop работает как защита**: maxDD снижен с 72% до 43% (в 1.7 раза).
- ✗ **Доходность упала почти в 8 раз** (833% vs 6346%). Trailing-stop срезает просадки, но и срезает большую часть восходящего движения: после стопа SMA50-re-entry часто запаздывает и пропускает ралли. На сильном долгосрочном тренде вверх (LKOH 2002→2025) это критично.
- ✗ **Sharpe упал в 2 раза** (0.25 vs 0.50) — defensive overlay не дал выигрыша на риск-скорректированной.

Это типичный артефакт trend-following overlay на высоковолатильной фишке. Возможные направления: (1) более широкий trailing (20–25%) — реже срабатывать; (2) более чувствительный re-entry (SMA20 вместо SMA50) — раньше возвращаться в тренд. Но это уже подгонка параметров — менять только при наличии экономической мотивации, не «потому что так лучше на LKOH».

### H6 — Ежеквартальная ребалансировка существенно улучшает Mix 30/70

> Параметры универсальные: 63 торговых дня — стандартный «торговый квартал» (252/4). Доли 30/70 — те же, чтобы сравнение чистое.

|---|---:|---:|---:|

| Год.% | 15.82% | **18.34%** | +2.5 п.п. |
| MaxDD | 41.3% | 41.3% | — |
| **Sharpe** | 0.55 | **0.68** | +23% |
| Profit factor | — | 2.26 | — |

**Вывод H6:** **подтвердилась.** Ежеквартальная ребалансировка дала **+69%** к абсолютной доходности и **+23%** к Sharpe при той же максимальной просадке. Это **лучший Sharpe на полной истории LKOH 2002-2025 среди рисковых стратегий** (0.68) — обогнал чистое золото (0.51) и Buy LKOH all-in (0.50).

### H7 — Cash на накопительный счёт между ребалансами поднимет доходность Mix

> Гипотеза: в Mix с ребалансом (H6) свободный cash и дивиденды LKOH между ребалансами лежат «мёртвым грузом». Если каждый день автоматически покупать SAVINGS_MIACR на весь свободный cash — деньги работают непрерывно, доходность поднимется.

**Стратегии:** `H7: LKOH 30/70/50/50/70/30 / GOLDCB ... ребаланс + cash на SAVINGS_MIACR`. К H6-логике добавлено 4-е правило (priority=5): каждый день, если cash >= цены 1 единицы SAVINGS_MIACR, покупает на весь cash. На ребаланс-тике sell-rule продаёт всё (включая накопит. счёт) → buy LKOH/GOLDCB по target долям → buy SAVINGS_MIACR на остаток.

**Также — расширение H6 на 50/50 и 70/30** (проверяем устойчивость эффекта ребалансировки на разных пропорциях).

**Окружение:** `LKOH full history 2002-2025`.

| Пропорции | H6 (без накопит.) | H7 (cash в накопит. счёте) | Δ доходности |
|---|---|---|---:|
| **30/70** | tot=5275%, ann=18.34%, dd=41.3%, Sharpe=**0.68** | tot=5409%, ann=18.47%, dd=41.9%, Sharpe=0.68 | +134 п.п. |
| **50/50** | tot=6308%, ann=19.23%, dd=46.0%, Sharpe=0.67 | tot=**6536%**, ann=19.40%, dd=43.1%, Sharpe=0.67 | +228 п.п. |
| **70/30** | tot=6679%, ann=19.51%, dd=59.2%, Sharpe=0.59 | tot=**6988%**, ann=**19.74%**, dd=55.1%, Sharpe=0.60 | **+310 п.п.** |

**Вывод H7:** **частично подтвердилась.**
- ✓ Накопит.-cash добавляет 1.3-3.1 п.п. к абсолютной доходности — тем больше, чем больше доля LKOH (и значит больше дивидендов в cash).
- ✓ MaxDD у H7 чуть лучше или равен H6 (защитное свойство сохранено).
- ≈ **Sharpe фактически равен H6 без накопит. счёта** — приток в R_f-актив и приток к R_f одинаково взвешиваются в excess return = strategy − R_f, поэтому добавка не виден на риск-скорректированной (логично, раз накопит. счёт — это и есть R_f).
- ✓ **H7 LKOH 70/30 + cash в SAVINGS_MIACR (+6988%, Sharpe 0.60, ann 19.74%) — лидер по абсолютной доходности на полной истории**, обогнал даже `Buy LKOH all available` (+6346%, Sharpe 0.50) — при этом с меньшим maxDD (55% vs 72%).

**Sanity-check адекватности цифр:**

1. **H1 70/30 (buy-and-hold) +2854% vs ожидаемое weighted blend (0.7×LKOH + 0.3×Gold = 5422%)** — H1 проигрывает blend'у потому, что дивиденды LKOH копятся в cash и не реинвестируются. Это **точно объясняет** почему ребалансировка даёт огромный буст.
2. **H6 70/30 (+6679%) > weighted blend (5422%)** — это alpha ребалансировки в чистом виде. Sell-buy в моменты расхождения долей реализует «sell high, buy low» автоматически.
3. **H7 70/30 (+6988%) > H0 LKOH all-in (+6346%)** — парадокс «mix с 70% LKOH обогнал 100% LKOH». Математически возможен из-за: (а) ребаланс-альфы, (б) Gold-defensive offset в кризисах LKOH, (в) cash в накопит. счёте даёт ~7% годовых вместо 0%.
4. **Sharpe: 0.60 (70/30) < 0.68 (30/70)** — больше LKOH-доли = больше волатильности = меньше Sharpe. Логично.

Все цифры **внутренне консистентны**. Главная осторожность — это **in-sample результат на одной эпохе одного тикера**: гениальная стратегия 2002-2025 на LKOH+Gold может не повториться на других активах или другом окне. Это направление для следующих гипотез — out-of-sample проверка.

### H8 — LKOH all-in + cash на SAVINGS_MIACR между покупками

> Гипотеза: в `H0: весь cash в LKOH ежедневно` cash, недостаточный для 1 акции LKOH (между дивидендными выплатами), просто лежит мёртвым грузом. Если этот «остаток» сразу класть в SAVINGS_MIACR — деньги работают непрерывно, и доходность поднимется.
>
> Это аналог H7 для одиночного тикера: чистый LKOH + накопит.-cash, без mix с золотом и без ребалансировки.

**Стратегия:** `H8: LKOH all-in + cash на SAVINGS_MIACR`. 3 правила:
- Sell SAVINGS_MIACR (priority=300): срабатывает только когда cash сам по себе недостаточен для 1 акции LKOH, но cash + depo_value хватит. Освобождает накопит. счёт.
- Buy LKOH (priority=10): cash >= close_price LKOH → купить максимум.
- Buy SAVINGS_MIACR (priority=5): остаток cash → накопит. счёт.

**Окружение:** `LKOH full history 2002-2025`.

| Метрика | H8 | Baseline `Buy LKOH all available` |
|---|---:|---:|
| Σ доход. | +6006% | **+6346%** |
| Год.% | 18.98% | 19.26% |
| MaxDD | 72.4% | 72.4% |
| Sharpe | 0.49 | 0.50 |
| Сделок | 76 | 71 |

**Вывод H8:** **отвергнута.** SAVINGS_MIACR-buffer на остатке cash **не помогает**: доходность даже чуть ниже baseline (−340 п.п.), Sharpe идентичен. Дивиденды LKOH составляют слишком малую долю капитала, чтобы их «работа» в накопит. счёте давала заметный эффект — а накладные расходы на дополнительные buy/sell SAVINGS_MIACR накапливаются. На полной истории идея инкрементальна и в данных случаях не окупается.

### H10 — Take-profit +10% от avg_price поверх LKOH all-in

> Гипотеза: активный take-profit на +10% от средневзвешенной цены входа улучшает риск-скорректированную доходность простого buy-and-hold. Цикл «купил весь cash в LKOH → ждём пока `close(:tick - 1) > avg_price * 1.10` → продали всё → завтра снова купили».
>
> Цель — не «обыграть baseline по доходности», а **проверить, как ведёт себя `avg_price`** в реальной стратегии (он динамически пересчитывается после каждой покупки/продажи по FIFO-лотам). Бонус: если на восходящем тренде take-profit-цикл хотя бы не уступает buy-and-hold, у нас есть базис для усложнённых вариаций.

**Стратегия:** `H10: LKOH all-in + тейк-профит +10% от avg_price`. 2 правила:
- Buy LKOH (priority=10): `cash >= close_LKOH(:tick - 1)` → купить максимум.
- Sell всю позицию (priority=300): `close_LKOH(:tick - 1) > avg_price('LKOH') * 1.10` → продать всё.

**Окружение:** `LKOH full history 2002-2025`.

| Метрика | H10 | Baseline `H0: весь cash в LKOH ежедневно` |
|---|---:|---:|
| Σ доход. | +6201% | **+6346%** |
| Год.% | 19.14% | 19.30% |
| MaxDD | 72.2% | 72.0% |
| Sharpe | 0.498 | 0.500 |
| Win rate | 100% | — |
| Сделок | 133 | 71 |

**Вывод H10:** **отвергнута.** Take-profit +10% от `avg_price` **не даёт преимущества** относительно buy-and-hold:
- Доходность *чуть ниже* baseline (−145 п.п.) при тех же maxDD и Sharpe — slippage между `close(:tick - 1)` и `open(:tick)` накопительно стачивает результат при 133 сделках.
- Win rate 100% — артефакт триггера: sell вообще срабатывает только когда позиция в плюсе на ≥10%. Это не сигнал качества стратегии, а тавтология.
- На сильном долгосрочном тренде вверх «продал → завтра купил» не извлекает выгоду — цена редко падает после +10% движения, продажа просто перезапускает счётчик `avg_price`.

**`avg_price` сам работает корректно** — после каждой полной продажи позиции `avg_price → NULL`, при следующей покупке принимает новое значение цены входа. Триггер `close > avg_price * 1.10` срабатывает строго в нужные моменты. Функцию можно использовать в более содержательных стратегиях (например: pyramiding на просадке от средней + take-profit на росте от средней).
