# Язык поиска прецедентов (Precedent Query Language, PQL)

SQL-подобный язык для поиска интересных событий в истории и анализа их влияния на цены акций. Поиск аномалий — один из частных случаев применения языка.

---

## 1. Зачем нужен язык

Аналитик исследует, как события (дивиденды, санкции, аварии и т.п.) влияют на котировки. Чтобы быстро находить нужные события и сравнивать их по объективным метрикам, нужен инструмент:

- декларативный — указывается, **что** нужно найти (не как искать);
- знакомый — основан на стандартном SQL, отдельного обучения не требует;
- объединяющий — в одном запросе можно фильтровать по сырым данным (теги, даты) **и** по вычисляемым метрикам событийного анализа (CAR).

Это и есть PQL.

---

## 2. Прецедент

`Precedent` — одна строка результата поиска: пара *(событие, тикер)* с посчитанными на ней метриками реакции. Это не само событие из БД, а событие в связке с акцией, на которой измерен эффект. Один и тот же `Event` порождает разные прецеденты для разных тикеров.

Запрос пишется на стандартном SQL по таблице событий и связанной с ней системой тегов. Колонка `car` (см. ниже) появляется в результате через вызов одноимённой функции.

---

## 3. Видимая схема

Эти объекты доступны пользователю в запросе.

### Таблица `events`

Сырые исторические события.

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | TEXT | первичный ключ |
| `event_date` | DATE | дата события (момент = `t=0` для событийного анализа) |
| `announce_date` | DATE | дата, с которой о событии известно рынку (граница no-lookahead); по умолчанию совпадает с `event_date`. Для выплат дивидендов — дата объявления (раньше даты выплаты), что и позволяет бэктесту видеть будущую выплату как заранее известную. |
| `event` | TEXT | описание события |
| `payload` | JSONB \| NULL | дополнительная структурированная информация, специфичная для типа события (например, для дивидендов — `ticker`, `dividend_per_share`, `year`). Доступно через JSON-операторы Postgres (`payload->>'ticker'`). |

### Таблица `tags`

Справочник тегов: страны, отрасли, темы, компании.

| Колонка | Тип | Назначение |
|---|---|---|
| `code` | TEXT | первичный ключ; буквенный код тега (`LKOH`, `SANCTIONS`, `OIL`, ...) |
| `name` | TEXT \| NULL | человекочитаемое название |
| `type` | TEXT \| NULL | тип тега: `company`, `country`, `topic`, `sector` и т.п. |

### Таблица `event_tags`

Связь событий и тегов (M2M).

| Колонка | Тип | Назначение |
|---|---|---|
| `event_id` | TEXT | ссылка на `events.id` |
| `tag_code` | TEXT | ссылка на `tags.code` |

### Таблица `saved_queries`

Сохранённые пользователем запросы поиска прецедентов — как PQL, так и fuzzy. Доступна для метазапросов (например, «все запросы, где упоминается LKOH»). Записи добавляются и читаются через виджеты поиска.

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | TEXT | первичный ключ (UUID) |
| `name` | TEXT | уникальное имя, заданное пользователем |
| `source` | TEXT | текст запроса (PQL или строка fuzzy) |
| `kind` | TEXT | вид запроса: `FUZZY` или `PQL` |
| `created_at` | TEXT | ISO-timestamp создания |

### Представление `tagged_events`

Удобная обёртка для запросов «события с тегом X». Одна строка на каждую пару *(событие, тег)*.

| Колонка | Тип | Источник |
|---|---|---|
| `event_id` | TEXT | `events.id` |
| `event_date` | DATE | `events.event_date` |
| `announce_date` | DATE | `events.announce_date` |
| `event` | TEXT | `events.event` |
| `payload` | JSONB \| NULL | `events.payload` |
| `tag` | TEXT | `tags.code` |
| `tag_name` | TEXT \| NULL | `tags.name` |
| `tag_type` | TEXT \| NULL | `tags.type` |

Без `tagged_events` запросы по тегам пишутся через явный JOIN. С `tagged_events` они становятся короче.

### Функция `car(...)`

Возвращает кумулятивную аномальную доходность для конкретного прецедента.

| Параметр | Тип | Дефолт | Назначение |
|---|---|---|---|
| `ticker` | TEXT | обязательный | тикер акции |
| `event_date` | DATE | обязательный | дата события |
| `model` | TEXT | `'market_model'` | модель ожидаемой доходности: `'mean_adjusted'` / `'market_model'` / `'capm'` |
| `window_before` | INT | `5` | торговых дней до события (положительное — окно начинается до события; ноль или отрицательное — окно начинается с самой даты события или позже) |
| `window_after` | INT | `5` | торговых дней после события (положительное — окно заканчивается после события; ноль или отрицательное — окно заканчивается на самой дате события или раньше) |
| `estimation` | INT | `200` | длина оценочного окна в торговых днях |
| `outlier_threshold` | DOUBLE \| NULL | `NULL` | σ-порог фильтрации выбросов; `NULL` — без фильтра |

Окно события — это интервал `[-window_before, +window_after]` относительно даты события. Оба поля принимают любые целые при условии непустого интервала (`window_after ≥ -window_before`); это позволяет считать CAR только до события (`window_after => -1`) или только после (`window_before => -1`).

Возвращает `DOUBLE`. Если по тикеру нет данных, окно пустое или данных недостаточно для расчёта — возвращает `NULL` (не ошибка). Это позволяет писать одинаковый запрос для тикеров с разной полнотой истории.

### Функции `vol_ratio(...)` и `volume_ratio(...)`

Простые меры реакции акции на событие — отношение характеристики *после* к характеристике *до*.

| Параметр | Тип | Дефолт | Назначение |
|---|---|---|---|
| `ticker` | TEXT | обязательный | тикер акции |
| `event_date` | DATE | обязательный | дата события |
| `window_before` | INT | `5` | сколько торговых дней до события включить в окно «до» |
| `window_after` | INT | `5` | сколько торговых дней после события включить в окно «после» |

Окно «до» — `[event_date - window_before, event_date - 1]`, окно «после» — `[event_date + 1, event_date + window_after]`. Сама дата события в окна **не** входит.

- `vol_ratio(...)` — `std(дневных логдоходностей в окне «после»)` ÷ `std(дневных логдоходностей в окне «до»)`. Метрика «во сколько раз выросла волатильность».
- `volume_ratio(...)` — `mean(объёма в окне «после»)` ÷ `mean(объёма в окне «до»)`. Метрика «во сколько раз вырос дневной объём».

Обе возвращают `DOUBLE` или `NULL`, если данных недостаточно (нет тикера, окно выходит за пределы истории, в окне «до» получился нулевой знаменатель).

### Контракт TA-функций

Все TA-функции (`car`, `vol_ratio`, `volume_ratio`) реализованы в Postgres как PL/Python-функции и читают цены напрямую из таблицы котировок. No-lookahead устроен через session-GUC `backtest.max_date`: функции читают цены только до этой даты включительно. В редакторе PQL GUC не выставлен — доступна вся история; в прогоне бэктеста GUC переключается на каждом тике, и те же SQL-запросы автоматически перестают видеть будущее без правок самих запросов.

## 5. Примеры запросов

### 5.1. Все события с тегом LKOH

```sql
SELECT e.event_date, e.event
FROM events e
JOIN event_tags et ON et.event_id = e.id
JOIN tags t        ON t.code      = et.tag_code
WHERE t.code = 'LKOH'
ORDER BY e.event_date DESC
LIMIT 50;
```

То же через `tagged_events`:

```sql
SELECT event_date, event
FROM tagged_events
WHERE tag = 'LKOH'
ORDER BY event_date DESC
LIMIT 50;
```

### 5.2. Дивидендные события LKOH с положительным CAR

Здесь нужны **два** условия по тегам — стандартный SQL делает это через self-join:

```sql
SELECT te1.event_date,
       car('LKOH', te1.event_date) AS car
FROM tagged_events te1
JOIN tagged_events te2 ON te2.event_id = te1.event_id
WHERE te1.tag = 'LKOH'
  AND te2.tag = 'DIVIDEND_ANNOUNCEMENT'
  AND car('LKOH', te1.event_date) > 0.03
ORDER BY car DESC
LIMIT 20;
```

### 5.3. Все санкции по России

```sql
SELECT DISTINCT event_date, event
FROM tagged_events
WHERE tag = 'SANCTIONS'
  AND event_id IN (
    SELECT event_id FROM tagged_events WHERE tag = 'RUS'
  )
ORDER BY event_date DESC;
```

### 5.4. Сравнение CAR трёх моделей для одного события

```sql
SELECT car('LKOH', DATE '2022-12-16', model => 'mean_adjusted') AS car_mean,
       car('LKOH', DATE '2022-12-16', model => 'market_model')  AS car_market,
       car('LKOH', DATE '2022-12-16', model => 'capm')          AS car_capm;
```

### 5.5. Топ-10 крупнейших падений GAZP с расширенным окном

```sql
SELECT te.event_date,
       te.event,
       car(te.tag, te.event_date, window_before => 5, window_after => 30) AS car
FROM tagged_events te
WHERE te.tag = 'GAZP'
  AND car(te.tag, te.event_date, window_before => 5, window_after => 30) < -0.05
ORDER BY car ASC
LIMIT 10;
```

## 6. Формат результата

Результат запроса — таблица. API возвращает её в универсальном виде:

```
{
  "columns": [{ "name": "...", "type": "..." }, ...],
  "rows":    [[v1, v2, ...], ...],
  "stats":   { "truncated": false, "duration_ms": 123, ... }
}
```

- `columns` — упорядоченный список колонок результата (имя + тип). Имена и типы определяются `SELECT`-списком запроса.
- `rows` — массив строк; в каждой строке значения в порядке `columns`.
- `stats.truncated` — флаг, что результат был усечён жёстким серверным потолком (см. раздел 7).
- `stats.duration_ms` — время исполнения запроса в миллисекундах.

Пустой результат — `rows: []`. Колонки всегда заполнены, чтобы виджет мог отрисовать заголовки даже на пустой выдаче.

---

## 7. Жёсткий лимит выборки

Сервер всегда применяет жёсткий потолок на количество строк в ответе — даже если пользовательский `LIMIT` не задан или превышает потолок. При срабатывании лимита `stats.truncated` равно `true`. Это защита от случайных запросов вида `SELECT * FROM events`, которые иначе вернули бы всю историю.

---

## 8. Поведение при ошибках

**Синтаксические и семантические ошибки запроса** (неверная грамматика, неизвестная колонка, неизвестная функция) — сервер возвращает ошибку с указанием строки и колонки в исходном тексте запроса плюс сообщение от движка БД. Сообщение пробрасывается пользователю как есть, без перевода.

**Ошибки данных** в `car()` (нет цен по тикеру, недостаточно данных в оценочном окне) — функция возвращает `NULL`, не падает. Запрос исполняется, в колонке стоит `NULL`. Это позволяет писать запросы по большому набору тикеров, включая те, где данных недостаточно.

**Транспортная ошибка** (бэкенд недоступен) — обрабатывается клиентом виджета как «Сервер недоступен».

## 9. Что не входит в MVP

В MVP **умышленно не включено**:

- Интеграция с логической группой виджетов (трансляция результатов в группу).
- Параметры расчёта на уровне запроса (общие для всего запроса значения окна, модели и т.п.) — пока задаются только аргументами `car()`.
- **Пользовательские функции** (`CREATE FUNCTION ... LANGUAGE SQL`) — основа будущего расширения языка: аналитик сможет задавать собственные композиции метрик и порогов и сохранять их между сессиями.
- Дополнительные встроенные метрики (`drawdown`, `post_event_drift` и т.п.) — будут добавлены как PL/Python-UDF в Postgres по аналогии с `vol_ratio` / `volume_ratio` либо реализованы пользователем через `CREATE FUNCTION`.

## 10. Сохранение запросов

Пользователь может сохранять часто используемые запросы как именованные шаблоны. Имя должно быть уникальным; повторное сохранение под существующим именем — ошибка. Удаление и переименование в MVP не поддерживаются. Список сохранённых запросов отсортирован по дате создания (новые первыми). Загрузка запроса заполняет редактор без авто-исполнения. Сохранённые запросы видны через `SELECT * FROM saved_queries` — это обычная таблица в видимой схеме.

## 11. Стартовые рецепты

При первом запуске движок засевает в `saved_queries` несколько системных шаблонов с префиксом `★` в имени — типовые сценарии анализа аномалий и реакции на события. Шаблоны видны в дропдауне «Загрузить» рядом с пользовательскими записями и могут быть отредактированы / удалены пользователем. На следующем старте движок проверяет наличие записей по имени и засевает только отсутствующие — повторного дублирования не происходит.

Префикс `★` зарезервирован: попытка пользователя создать запрос с именем, начинающимся на `★`, отклоняется (400). Это защищает системные имена от случайной перезаписи.
