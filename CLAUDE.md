# Kairos

Рабочее место финансового аналитика: событийный анализ, поиск аномалий, исследование влияния событий на котировки акций. Магистерская дипломная работа.

## Раскладка репозитория

Монорепо: Python и JS в отдельных директориях.

- `backend/` — вся Python-часть: `core/` (доменная логика), `main.py` (FastAPI), `notebooks/`, `tests/`, `pyproject.toml`. Это **директория, а не Python-пакет** (нет `__init__.py` на верхнем уровне).
- `frontend/` — React-приложение.
- `data/`, `docs/`, `scripts/`, `models/` — общие ресурсы в корне.

## Команды

Все команды, работающие с Python, запускаются из директории `backend/`.

```bash

C:/Users/Ruslan/anaconda3/envs/data-core/python.exe

# Установка (editable-режим) — один раз после клона/переезда
cd backend && C:/Users/Ruslan/anaconda3/envs/data-core/python.exe -m pip install -e .

# Тесты
cd backend && C:/Users/Ruslan/anaconda3/envs/data-core/python.exe -m pytest tests/ -v

# Загрузка референсных данных в Postgres после миграций (идемпотентно).
```

Запуск, остановка, перезапуск и smoke-проверка стека (Postgres + backend + frontend) — `.claude/skills/run-data-core/` (slash-команда `/run-data-core`).

Импорты внутри Python-кода остаются короткими: `from core.event_study import EventStudy`.

## Правила работы

- Не коммитить без явного подтверждения пользователя. После выполнения задачи — спросить «коммитим?»
- Всегда тестировать код перед отдачей — не давать непроверенный код
- Если команда не работает после 3 попыток — останавливаться и передавать пользователю для выполнения напрямую
- Dash в ноутбуках: `jupyter_mode='inline'` (по умолчанию) или `jupyter_mode='external'` (только ссылка)
- Запускать сервисы и команды самостоятельно — пользователь только кликает на ссылки и проверяет
- Git-команды должны отрабатывать мгновенно — таймаут не более 10 секунд
- Windows: для Vite использовать `host: '127.0.0.1'` (localhost не биндится). Для остановки/перезапуска занятых портов — `python scripts/ops/run_services.py --stop` или `--restart` (см. skill)
- Windows: если `Get-NetTCPConnection -LocalPort N` показывает PID, а `Get-Process -Id <PID>` его не находит — сокет «застрял» в ядре после форсированного убийства процесса. `taskkill /F /PID` также не поможет. Единственный надёжный фикс — перезагрузка. Не углубляться в попытки убить зомби — сразу запрашивать у пользователя перезагрузку
- Не плодить новые порты — переиспользовать те, что в спецификации (backend 8080, frontend 5173)

## Процесс разработки

- **Бэклог** — `todo.md` в корне проекта, поддерживать актуальным. После коммита выполненной задачи — удалять её из бэклога (история в git).
- **Спецификация** — писать перед реализацией фичи (`docs/SPEC_*.md`). пишутся на языке глоссария и описывают **что** и **зачем**, а не **как**. В них не должно быть имён функций/файлов/библиотек, чисел-констант, описаний алгоритмов и UI-деталей вроде «кнопка с курсором pointer». Всё реализационное находится в коде. Цель — спека должна оставаться валидной после любого рефакторинга. Если приходится править спеку при чисто внутреннем рефакторинге — это признак, что в спеке слишком много «как».
- **Критерии приёмки** — определять до начала работы (например: «ноутбуки 21 и 22 запускаются»)
- **Техдолг** — контролировать, не накапливать
- **Документация** — `docs/` (архитектура, метрики, спецификации и др.)
- **Глоссарий** — `docs/GLOSSARY.md` — единый словарь сущностей проекта (методология + сущности приложения). Источник правды для именования. При добавлении новой сущности в код:
  1. Сначала проверь, есть ли подходящий термин в глоссарии — используй его (с поправкой на соглашения языка: PascalCase для классов, snake_case для Python-переменных, camelCase для TS).
  2. Если концепт новый — добавь в глоссарий ДО того, как он растечётся по коду.
- **Переименование сущности** — перед началом сделать **полный grep по всему репо** (а не только по «очевидно затронутому файлу»). Особенно проверять цепочки вызовов с `**kwargs` и параметры, которые прокидываются между слоями: легко получить асимметрию «снаружи новое имя, внутри старое». Если на разных слоях один и тот же концепт зовётся по-разному — это смелл, а не аккуратность.

## Соглашения по коду

- **Разделение ответственности:** данные, аналитика и визуализация — в разных функциях. Функция либо готовит данные, либо отображает. Не оба.
- **Размер функций:** не более 70 строк. Если больше — разбивать.
- **Модульность:** не дублировать логику, выносить в переиспользуемые функции.
- **Именование файлов:** `<сущность>_<что_делает>.py` (например `stock_data_provider.py`)
- **Именование функций:** глагол + существительное (`load_dividends`, `get_log_returns`)
- **Приватные функции:** `_` префикс для внутренних функций модуля
- **Типизация:** указывать типы в сигнатурах публичных функций (параметры + return)
